This repo IS the ASD framework's source, not a consumer project. `tests/run.js` (zero-dependency runner, no package.json/build) covers both the Node sources (`.asd/sync.js`, `update.js`, `.asd/runtime.js`, migrations, hooks) and content contracts over rules/templates/agents/skills/workflows/README, and since sprint 017 also agent memory (a removed-mechanism sweep over `.claude/agent-memory/<roster agent>/`). Content sweeps are the norm here, not disproportionate: each one derives its file set from disk and exempts only a line naming the term as legacy, or (memory only) a negation in the same clause right before the term — a whole-line negation-word skip is too broad (it would exempt a line whose unrelated clause says "not").

Suite gate here = three commands: `node tests/run.js` (test), `git diff --check` (lint), `node .asd/sync.js --check` (build). `sync.js --check` always exits 0 with `ok:true` for non-orphan drift (stale/missing/modified-foreign) — only a marked orphan flips `ok:false`/exit 1. Any assertion trusting bare `ok`/`items` shape alone is a vacuous-pass risk for everything except orphans. This pattern recurred: one fix added a `status === 'current'` per-item assertion; a later review found *that* still passed vacuously if the plan-builder silently dropped a whole canon directory from enumeration (shrinking the item list rather than marking anything stale) — fixed by independently enumerating canon sources from disk and asserting each expected target string appears in the plan before filtering for drift.

`.asd/release-manifest.json`'s `upstream_hashes` ledger is a separate, easy-to-miss drift source: it is NOT recomputed by editing canon alone, only by running `node .asd/sync.js --apply <file...>` afterward (the mechanical hash-ledger recompute step). A canon edit landed without that follow-up reads green on `sync.js --check` (exit 0, `ok:true`) yet fails the dedicated `tests/run.js` integrity assertion — recurred at least twice in one sprint (once for a managed-block target, once for four rule/template/workflow files after an unrelated fix cycle). Route it to the orchestrator's sync (once per wave or fix round; `--apply AGENTS.md` when no view changed), never to a dev, who never runs `sync.js --apply` (`sprint-lifecycle.md` "Self-hosting"). Never something this agent's write scope covers (`.asd/release-manifest.json` is outside the tester's write scope).

**How to apply**: when reviewing/extending drift-detection or "everything green" style assertions in this codebase, always ask "can this pass if the checked collection is empty or a subset?" — that's the exact defect class recurring in this repo's own test suite. When asked to verify such an assertion's own logic (not just its pass/fail), independently confirm the field names/string construction it relies on rather than trusting a green run alone. When the full suite goes red on a canon-hash-ledger assertion right after unrelated production fixes landed, check first whether the orchestrator's sync on the touched canon files was simply never re-run — report it for the orchestrator's sync, don't hand-fix the ledger.
