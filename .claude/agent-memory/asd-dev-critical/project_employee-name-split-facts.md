Task 17 (2026-10-07), EF Core 10.0.12 / Npgsql 10.0.3 / PostgreSQL 18.6:

- **EF scaffolds this change wrongly**: `HasComputedColumnSql(..., stored: true)` on an existing column and a new `HasGeneratedTsVectorColumn` source list give `AlterColumn(computedColumnSql)` plus `AlterColumn` of `search_vector` and `AddColumn(nullable:false, defaultValue:"")` for the new columns - none of it runs. Hand-write: add nullable, `Sql` backfill, `AlterColumn` NOT NULL, `DropIndex`x2, `DropColumn search_vector`, `DropColumn full_name`, `AddColumn full_name(computedColumnSql, stored:true)`, `AddColumn search_vector` with the `TsVectorConfig`/`TsVectorProperties` annotations, `CreateIndex`x2. The scaffolded snapshot and Designer are correct as generated; `has-pending-model-changes` stays clean.
- A generated column cannot reference another generated column, so `search_vector` must be rebuilt from the base columns when `full_name` becomes generated. Virtual generated columns (PG 18 default) cannot be indexed, so `STORED` is required for the trigram GIN index.
- **Down**: `ALTER TABLE ... ALTER COLUMN full_name DROP EXPRESSION;` keeps the derived values as a plain column, then `ALTER COLUMN full_name TYPE character varying(200)` (fails loudly above 200 chars, no `USING left()` truncation); drop the vector first. With 10k rows Up/Down/Up gave an identical row hash and schema identical to the pre-migration one.
- Backfill split: `array_remove(regexp_split_to_array(full_name, '\s+'), '')` then `parts[1]`, `parts[2]`, `nullif(array_to_string(parts[3:], ' '), '')` (slice with omitted upper bound is valid); one word -> `-` first name, blank -> `-`/`-`. A part over 100 chars raises 22001 inside the migration transaction: nothing changes (checked: history stays at the previous migration).
- **Wider heap cost**: the stored generated duplicate of the name made the table 2864 kB -> 3584 kB at 10k rows; the unfiltered `ORDER BY full_name LIMIT 20` seq-scan+top-N went 2.8 -> 4.0 ms in SQL, +1.3 ms p50 through the API (6.6 -> 7.9). Search (`q`), unit lists with a filter and the tree are unchanged within noise.
- **API shapes**: an optional `string? MiddleName { get; init; }` that is absent/null/""/blank all become null; PUT without it clears it. A client that still sends only `fullName` gets a bare 400 `Bad Request` (missing `required` members, no `errors`); `fullName` next to the three fields is ignored. `HasComputedColumnSql` on a property with `private set` works, EF reads it back with RETURNING, and the audit allow-list ignores it simply by lacking `[Audited]`. `UserManagement` needed no change because it reads the name through `IEmployeeDirectory`.
- **Scratch method that worked**: seed the OLD database through the git-archive baseline API (real audit rows with `fullName`) plus raw SQL for odd rows (leading space, blank, one word); `CREATE DATABASE x TEMPLATE old` (needs zero connections to `old`, kill the baseline API first) gives identical copies for old-vs-new timings and Down/Up round trips; the app applies the migration at startup (`MigrateAsync`), `ef database update <migration> --connection` does Down. For a UI smoke on such data, delete the 10k bulk rows in a copy first, or the unit list renders thousands of cards.
- UI smoke ids: Form `employee` gives `#employee_lastName|firstName|middleName|position|orgUnitId`, unit form `#org-unit_headEmployeeId`, user form `#user_employeeId`; a required label carries `ant-form-item-required` (middle name has none); clearing an input via CDP is `focus+select` then a `Delete` keyDown, not `insertText("")`.

**Why:** each cost a decision or would have cost a failed migration/run.
**How to apply:** any later change that turns a stored column into a derived one, splits a column, or needs old-vs-new DB timings (see also [[migration-scratch-verification-recipe]], [[email-on-account-facts]], [[web-cdp-real-backend-smoke-facts]], [[pg-behaviour-facts]]).
