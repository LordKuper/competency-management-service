Verified on EF Core 10.0.12 / Npgsql 10.0.3 / Identity 10.0.12 / PostgreSQL 18.6 with scratch databases (removed):

- **Reading another module's table without referencing its type**: OrgStructure maps a keyless `EmployeeAccount` with `HasNoKey().ToSqlQuery("SELECT employee_id, email FROM users WHERE employee_id IS NOT NULL")`, and the employee projection uses `accounts.Where(a => a.EmployeeId == employee.Id).Select(a => a.Email).FirstOrDefault()` with `accounts = context.Set<EmployeeAccount>()` captured in the lambda. EF pushes paging into an inner select (`LIMIT/OFFSET` on employees), so the correlated subquery runs only for the page rows, and `CountAsync` over the projection is `SELECT count(*) FROM employees` (no join). The snapshot records it as `ToTable(null)` + `ToSqlQuery`; no table in the migration; `has-pending-model-changes` stays clean. 10 000 employees + 300 accounts, N=40: list p50/p95 8.0/9.7 ms new vs 8.6/10.4 old; the old code's e-mail/personnel `q` (ILIKE over three columns) was 20-24 ms, now 3.5-7 ms.
- **Identity with e-mail as login**: keep `UserName` = `Email` through one method (`AppUser.SetEmail`), not a property setter (EF may set a base-class backing field directly, bypassing a setter side effect). `options.User.AllowedUserNameCharacters = string.Empty` turns the character check off (Cyrillic e-mail verified). `RequireUniqueEmail` is not needed: the user-name validator already answers `DuplicateUserName` for the same string, case-insensitively through `normalized_user_name`; `UserManager.CreateAsync/UpdateAsync` fill `NormalizedEmail` themselves (invariant upper case). `FindByEmailAsync` is the login lookup. Map `Email`/`NormalizedEmail` columns and a unique index on `NormalizedEmail`; the `[Audited]` override of `Email` works like the old `UserName` one.
- **Duplicate e-mail response**: `Rejections.From` turns `DuplicateUserName` into a 409 `HttpValidationProblemDetails` carrying `errors.email` plus `detail` (the typed client's `ApiError` reads `errors` for any status, `showFieldErrors` then marks the field). 24 parallel creates of one e-mail: 1 x 201, 23 x 409, of which 2 hit the unique index (`23505`, the platform handler answers a bare English "Conflict" 409 with no `errors`): the Russian reason exists only on the validator path; adding a `catch (DbUpdateException)` in create/update is the upgrade if wanted.
- **Migration `EmailOnUserAccount`**: EF scaffolds `AddColumn(nullable: false, defaultValue: "")`, which breaks the unique index; rewrite as nullable add, `Sql` UPDATE, `AlterColumn` NOT NULL, index. A single UPDATE reads old values on every right-hand side, so `user_name = user_name || '@local.invalid'` next to `email = user_name || ...` is safe. The backfill `name || '@local.invalid'` is injective (names are unique), so it cannot collide. Dropping the stored generated column `normalized_email` must precede dropping `email` (EF's scaffold already orders it). Down must strip the suffix again, otherwise Down then Up double-suffixes (`admin@local.invalid@local.invalid`); with the strip, a hash of the legacy rows is identical before and after Up/Down.
- **Git Bash + curl**: Cyrillic in `--data "..."` or in the URL reaches Kestrel mis-encoded (`DecoderFallbackException`, a bare 400 "Bad Request" with no errors); send bodies with `--data-binary @file` (printf into a file) and percent-encode query text (`jq -rn --arg s ... '$s|@uri'`).
- **Scratch reset**: several databases in one scratch container, `DROP DATABASE x WITH (FORCE)` then `CREATE DATABASE x` between runs; a baseline of the previous code (`git archive HEAD` into the scratchpad, Release build with `-p:OpenApiGenerateDocumentsOnBuild=false`) runs against a database migrated only to the previous migration, so old and new run side by side on identical seeds.

**Why:** each decided a design choice in the account/e-mail change or cost a failed run.
**How to apply:** a later change to accounts, sign-in, employee reads, or a cross-module read (see also [[identity-efcore-store-gotchas]], [[ef-left-join-count-and-visibility-facts]], [[migration-scratch-verification-recipe]], [[vs-debug-build-lock-and-release-config]]).
