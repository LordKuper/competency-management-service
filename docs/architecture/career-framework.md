# Карьерная модель (`career-framework`)

## Purpose

Справочники карьерной модели — профессиональные направления, карьерные треки с упорядоченными карьерными уровнями, категории компетенций, каталог компетенций с историей версий, шкалы — и версионируемые матрицы компетенций подразделений с фиксированным маршрутом согласования (руководитель вышестоящего подразделения, затем ответственный HR) и публикацией; публикация версии матрицы или записи справочника каскадно делает действующими черновые записи, на которые она ссылается, или целиком отказывает; здесь же закрепление HR за подразделениями, вычисление ролей процесса «руководитель подразделения» и «ответственный HR» и письма-напоминания участникам согласования. «Карьерный уровень» — уровень трека (`CareerLevel`, `/api/v1/career/levels`), а не должность сотрудника из справочника `org-structure` (`Position`, `/api/v1/positions`); уровни треков связываются с должностями, которые им соответствуют. Модуль ссылается на `Competency.Platform`, `org-structure` (порт `IEmployeeDirectory`) и `user-management` (порт `IUserDirectory`), обратных ссылок нет; в журнал пишет через `[Audited]` и `IAuditWriter` из Platform (события — `audit.md`), письма отправляет через `MailSender` из Platform, находки рабочего стола отдаёт через `IDeskSource` из Platform.

## Key paths

- `src/Competency.CareerFramework/`: корень модуля; типы `internal`, наружу выходят только `AddCareerFrameworkModule` и `MapCareerFrameworkEndpoints`, опубликованных портов нет; хост регистрирует модуль после `OrgStructure` и `UserManagement`. Все endpoints — под `/api/v1/career/…`.
- `src/Competency.CareerFramework/CareerFrameworkEntityConfiguration.cs`: таблицы `org_unit_hr`, `career_directions`, `career_tracks`, `career_levels`, `career_level_positions`, `competency_categories`, `competencies`, `competency_versions`, `competency_scales`, `competency_matrices`, `matrix_versions`, `matrix_version_variants`, `matrix_version_decisions`; статусы и типы хранятся именами под CHECK; внешние ключи без каскадов (`ON DELETE RESTRICT`), на `org_units`, `positions` и `users` — по имени сущности другого модуля. Страховочные уникальные индексы: один HR на подразделение (ключ `org_unit_hr`), одна матрица на пару «подразделение — трек», номер уровня в треке, одна опубликованная (`ux_matrix_versions_published`) и одна версия в работе (`ux_matrix_versions_in_work`) у матрицы, одна шкала по умолчанию (`ux_competency_scales_default`). Уникальный индекс проверяется на каждой строке сразу (`tech-reference/sql-postgresql-18.6.md`), поэтому публикация архивирует прежнюю версию отдельным `SaveChanges`, а перестановка уровней (`CatalogStore.MoveLevelsAsync`) сначала уводит номера перемещаемых уровней в отрицательные и сохраняет каждый отдельно.
- `src/Competency.CareerFramework/ProcessRoles.cs`, `ProcessRoleEndpoints.cs`, `CatalogViewer.cs`: роли процесса вычисляются в момент запроса из оргструктуры (`IEmployeeDirectory`: руководители, предки, поддеревья), учётных записей (`IUserDirectory`; участвует только учётная запись, которая может действовать, — `UserStatus.IsActive`) и закреплений HR и нигде не хранятся, поэтому смена руководителя или HR действует сразу; неактивные подразделения в ролях не участвуют. Кто действует на основании ролей, держит блокировку дерева (разделяемую или эксклюзивную) до фиксации. `CatalogViewer` — права пользователя в справочниках на один запрос. `GET /api/v1/career/me` отдаёт роли SPA для меню и действий; сервер проверяет права при каждом действии заново. Ближайший ответственный HR, согласующий шага 1 и «может ли учётная запись руководителя действовать» — чистые функции, вынесенные из `ProcessRoles` и `MatrixRoute`: путь действия вызывает их на прочитанной цепочке предков, источник стола и экраны сценариев — на снимке оргструктуры (`IEmployeeDirectory.FindOrgSnapshotAsync`, `org-structure.md`). Правило одно, способов загрузки два, поэтому стол не расходится с правами действий; второй копии правил нет.
- `src/Competency.CareerFramework/OrgUnitHr.cs`, `OrgUnitHrEndpoints.cs`: `/api/v1/career/org-units/{id}/hr` — закреплённый HR подразделения и унаследованный от ближайшего вышестоящего с закреплением. Чтение — любой аутентифицированный (признак `isActive` учётной записи — только администратору); закрепление (`PUT`) и снятие (`DELETE`, удаление строки) — `GlobalAdmin`, без `If-Match`, под эксклюзивной блокировкой дерева (`IEmployeeDirectory.BeginExclusiveAsync`; её же берёт блокировка учётной записи), закрепить можно только учётную запись, которая может действовать.
- `src/Competency.CareerFramework/CatalogEntry.cs`, `CatalogEndpoints.cs`, `CatalogStore.cs`, `CatalogListQuery.cs`: общая модель шести справочников (направление, трек, уровень, категория, компетенция, шкала) — статус `Draft` / `Active` / `Inactive`, автор, `Version`; подразделение (`owner_org_unit_id`) есть только у трека, уровень принадлежит треку. Общие шаги endpoints: недоступное для чтения — 404, изменение видимого без прав — 403; изменение — под `CatalogStore.BeginWriteAsync` (порядок блокировок — `stack.html`) и с `If-Match`, кроме создания; дубль названия — 409 с ошибкой поля (`Rejection.Taken`), область уникальности учитывает черновики автора и проверяется заново при утверждении черновика (`POST …/{id}/approve`); ответы записей несут `canEdit` и `canDelete`; списки — серверные страницы, поиск `q` и фильтры (`CatalogListQuery`, пределы — `ListRequest`), `inWork=true` исключает неактивные записи для выпадающих списков с поиском по вводу.
- Endpoints справочников: `CareerDirectionEndpoints.cs` (`/api/v1/career/directions`), `CareerTrackEndpoints.cs` (`/tracks`; `PUT /tracks/{id}/level-order` — порядок уровней, `If-Match` трека), `CareerLevelEndpoints.cs` (`/levels`, права — по треку), `CompetencyCategoryEndpoints.cs` (`/categories`), `CompetencyEndpoints.cs` (`/competencies`; каждое изменение добавляет строку `competency_versions`, история — `GET …/{id}/versions`; без `scaleId` — шкала по умолчанию), `CompetencyScaleEndpoints.cs` (`/scales`; баллы — `jsonb` на строке шкалы; `POST …/{id}/make-default`; шкала, использованная опубликованной версией матрицы, не меняется — 409, проверку и публикацию разделяет блокировка справочников), `CatalogDraftEndpoints.cs` (`/drafts` — черновики, ожидающие утверждения текущим пользователем; у трека — `readiness`: «нет уровней» или уровни без действующей должности).
- `src/Competency.CareerFramework/CareerLevelPosition.cs` (связь уровня трека с должностью `org-structure`): таблица `career_level_positions` — `level_id` (→ `career_levels`), `position_id` (→ `positions` по имени сущности `Competency.OrgStructure.Position`), `track_id` (→ `career_tracks`; копия `TrackId` уровня, который после создания не меняется), все внешние ключи `RESTRICT`. Ключ `(level_id, position_id)`; уникальный индекс `(track_id, position_id)` — в треке должность связана не больше чем с одним уровнем; индекс `position_id` — для вопроса «в каких треках моя должность». Колонки `Version` нет (строка-связь, как `org_unit_positions`); сущность `[Audited]` — события `audit.md`. `org-structure` о связи не знает: деактивация должности и исключение её из перечня связь не снимают и не блокируются; должности не удаляются, поэтому `RESTRICT` на `positions` не срабатывает; должности, перечни и численность модуль читает только через снимок оргструктуры. Отклонено: уровень колонкой у должности — должность входит в треки разных подразделений, а `org-structure` пришлось бы ссылаться на `career-framework` (направление зависимостей, `stack.html`).
- Методы связей (`/api/v1/career/…`):
  - `GET /tracks/{id}/positions` — уровни в порядке трека, у каждого `version`, связанные должности (название, активность, число работающих сотрудников в поддереве подразделения трека, `canUnlink` — по тому же правилу, что `DELETE`) и признак «нет действующей должности»; плюс `canEdit` трека. Читает тот, кто видит трек, иначе 404;
  - `GET /tracks/{id}/available-positions?q=&page=&pageSize=` — серверные страницы (`ListRequest`) с числом сотрудников: действующие должности, доступные подразделению трека или любому его дочернему (собственные перечни поддерева плюс собственные перечни предков подразделения трека), ещё не связанные ни с одним уровнем трека;
  - `POST /levels/{id}/positions { positionId }` — повтор той же пары ничего не меняет; должность неактивна или недоступна треку — 400 с ошибкой поля `positionId`; должность уже связана с другим уровнем трека — 409;
  - `DELETE /levels/{id}/positions/{positionId}` — если трек действующий и снимается последняя действующая должность уровня (статус самого уровня не важен) — 409 `PublicationRefusal` с этим уровнем.
  Изменение связи — с `If-Match` уровня и увеличивает его `Version`, как перестановка уровней увеличивает `Version` трека; ответ — строка уровня с новым `ETag`, открытая форма правки уровня после этого получит 412. Права — права правки трека (`CatalogViewer.CanEdit`): хранители всегда, руководитель — черновой трек своего подразделения; остальным 403. Удаление уровня или трека удаляет их связи построчно в той же транзакции, каждая строка — событие журнала. Блокировки — `CatalogStore.BeginWriteAsync` (дерево разделяемо, справочники эксклюзивно), новой блокировки нет: под разделяемой блокировкой дерева должности и перечни не меняются, а утверждение трека и снятие связи сериализует блокировка справочников. Тесты гонок: два параллельных снятия двух последних действующих должностей уровня действующего трека — одно получает 409; снятие связи против утверждения того же чернового трека — утверждение видит итог снятия; одна должность параллельно связывается с двумя уровнями трека — одна попытка получает 409.
- Готовность трека — одна функция: проверяет уровни трека, кроме неактивных, и отвечает «нет уровней» либо перечнем уровней без связанной действующей должности (`positions.is_active`). Её используют утверждение и «Вернуть в работу» трека (409 `PublicationRefusal`), запрет снятия связи, проверка полноты версии («у уровня «X» трека «Y» нет связанной действующей должности» — везде, где проверяется полнота, и при публикации), источник стола, `readiness` очереди черновиков, экраны связывания и мастер. `POST /tracks` всегда создаёт черновик, у хранителей тоже: у нового трека нет уровней, а трек без уровней действующим не становится.
- `src/Competency.CareerFramework/MatrixVersion.cs`, `MatrixContent.cs`, `MatrixVariant.cs`, `MatrixDecision.cs`, `MatrixEntries.cs`: содержимое версии (уровни с порогами, блоки, компетенции, коэффициенты блоков, требования) — один `jsonb`-документ на строке `matrix_versions`, поэтому любая правка меняет `Version` строки и защищена `If-Match`; варианты автора и согласующего — копии документа (`matrix_version_variants`), правки согласующего — разница двух копий; решения (`matrix_version_decisions`) только добавляются. При публикации в `snapshot` пишутся названия и поля уровней, компетенций и шкалы на этот момент; опубликованная и архивная версии читаются только из снимка. Документ в журнал не пишется. Отображение `jsonb` — `tech-reference/npgsql-entityframeworkcore-postgresql-10.0.3.md`.
- `src/Competency.CareerFramework/MatrixWorkflow.cs`, `MatrixRoute.cs`, `MatrixCatalog.cs`, `MatrixEndpoints.cs`, `MatrixVersionEndpoints.cs`, `MatrixApprovalEndpoints.cs`: `/api/v1/career/matrices` (матрицы, их версии, создание новой версии копией опубликованной), `/api/v1/career/matrix-versions/{id}` (чтение, `PUT …/content`, `submit`, `approve`, `return`, `accept-changes`, `accept-and-revise`, `rollback-changes`, история, варианты и их разница), `/api/v1/career/approvals` (версии, ждущие согласования текущим пользователем). Статусы `Draft` → `OnReview` (→ `Returned`) → `Approved` → `Published` → `Archived`; маршрут и согласующий вычисляются в момент действия (`MatrixRoute`); полнота версии и допустимость её записей справочников проверяются при отправке, согласовании обоих шагов, возврате с правками и принятии правок (`MatrixCatalog`). Блокировки переходов и правки содержимого — `stack.html` («Целостность на уровне данных»). Публикация версии архивирует прежнюю опубликованную и делает действующими черновики по правилу публикации (ниже). Ответ версии несёт `actions` — действия, доступные пользователю сейчас; строки списков матриц и черновиков несут `version` для `If-Match`. `POST /matrices` принимает действующий трек своего или вышестоящего подразделения либо черновой трек, принадлежащий подразделению матрицы; направление — только действующее. Черновые уровни трека матрицы пригодны для содержимого независимо от автора; публикация такой версии делает трек и его уровни действующими каскадом либо отказывает.
- Шаг мастера: колонка `matrix_versions.builder_step` (`smallint`, `NULL`; без журнала — это состояние сценария, а не модели). `PUT …/content?builderStep=2..6` сохраняет шаг и без изменения содержимого: `Version` растёт, `If-Match` — как у правки содержимого. `MatrixVersionResponse.builderStep` равен `null`, если версия создана вне мастера; мастер тогда открывает шаг 2.
- Методы чтения сценариев (`/api/v1/career/…`):
  - `GET /matrix-versions/{id}/completeness` → `{ problems: [{ code, message, levelId?, competencyId? }] }` — та же функция полноты, что у переходов; коды `NoLevels`, `LevelWithoutRequirements`, `BlockWeights`, `CriticalWithoutScore`, `InactiveEntry`, `ForeignCompetency`, `ScoreOutOfScale`, `LevelWithoutActivePosition`. Переходы по-прежнему отвечают 409 со строками в `errors.content` с теми же `message`. Читает тот, кто читает версию, иначе 404;
  - `GET /matrix-versions/{id}/changes` → `MatrixDiffResponse` (`MatrixChange.Between`): `Before` — содержимое действующей опубликованной версии матрицы (для первой версии — пустое содержимое и `previousNumber = null`), `After` — эта версия;
  - `GET /{directions|tracks|levels|categories|competencies|scales}/{id}/matrices` — матрицы и версии, которые используют запись: трек — по матрице; уровень и компетенция — `MatricesUsing`; категория — через компетенции; шкала — по версиям; направление — по матрицам. Только читаемые пользователем (`MatrixRoute.ReadableAsync`): скрытые не называются и не считаются;
  - `GET /unused-entries?kind=&page=&pageSize=` — неиспользуемые компетенции, шкалы и категории и направления без треков; та же функция, что у источника стола. HR и администратор, иначе 403. Отдельный метод нужен потому, что администратору стол эти находки не выводит;
  - `GET /org-units/{id}/setup` (только `GlobalAdmin`) → `{ unit (путь), employees, head, headAccount, hr, hrAccount, positions, rows }`: у `hr` указано, свой он или унаследованный и откуда; `headAccount`, `hrAccount` — `{ id, email, state: None | Invited | Blocked | Active, version }`; `positions` — `{ own, inherited }`; `rows` — `[{ row, status: Ready | Missing | Waiting, reason }]`. Статусы считает сервер по тем же определениям, что источник стола: снимок оргструктуры, ближайшее закрепление HR, `UserStatus.IsActive`. Пустой перечень отмечается и у подразделения без сотрудников. Метод описывает готовность подразделения, но живёт здесь: только этот модуль видит закрепление HR, оргструктуру и учётные записи;
  - `GET /me/place` → `{ employee | null, unit (путь), position, head, responsibleHr (свой или унаследованный и откуда), tracks, publishedMatrices, noTrack }`. Элемент `tracks` — трек, направление, текущий уровень, следующие уровни с требованиями из `snapshot` опубликованной версии матрицы своего подразделения по этому треку либо без требований. Только опубликованные версии собственного подразделения; пользователь без привязки получает 200 с `employee = null`.
- Публикация — одна функция для всех публикаций: утверждение и «Вернуть в работу» (`approve`, `activate`) записи справочника и публикация версии любым действием из `publishingActions`; создание записи каскадом не публикует. Функция строит транзитивное замыкание черновых ссылок:
  - версия → трек матрицы и все его уровни, уровни и компетенции содержимого, шкала версии; через действующие компетенции содержимого — к их черновым категориям, направлениям и шкалам (такие ссылки остаются в прежних данных);
  - трек → направление и черновые уровни трека;
  - компетенция → категория, направление, шкала.
  Действующие и неактивные ссылки не публикуются; неактивная запись в версии остаётся проблемой полноты. Для каждой сущности замыкания функция проверяет право утвердить (`CanManage`), повтор названия с учётом всего, что публикуется вместе (`ChangeTracker`), у трека — готовность; у версии сначала полнота (прежний 409 со строками), затем каскад. Дальше она либо публикует всё в транзакции действия под уже взятыми блокировками (у записи — дерево разделяемо и справочники эксклюзивно, у версии — ещё строка матрицы `FOR UPDATE`; новых блокировок нет, отдельный `SaveChanges` — только архивирование прежней опубликованной версии), либо откатывает всё и отвечает 409 `PublicationRefusal`. Это ProblemDetails с `blockers` (вид — направление, трек, уровень, категория, компетенция, шкала; id, название, причина `NoRight` | `NoLevels` | `NoActivePosition` | `NameTaken`, контекст) и `moreCount`: видимых не больше 5, невидимые пользователю — только в числе; `detail` — русская фраза для заголовка отказа. Каждая опубликованная каскадом сущность получает `<Тип>.Approved` со ссылкой на корень в `Reason` (`audit.md`), компетенции — строку истории версий. Право: публикация записи — право действующего пользователя; публикация версии — право ответственного HR подразделения матрицы (`ProcessRoles.ResponsibleHrAsync`), чей шаг засчитывается согласованным, каким бы действием из `publishingActions` и кем бы она ни была запущена. Права этого HR строит `CatalogViewer` по его учётной записи; ответственного HR нет — каждая черновая сущность каскада получает `NoRight`. Глубина замыкания — три ссылки (версия → компетенция → категория).
- Предпросмотр публикации — только чтение, без блокировок:
  - `GET /matrix-versions/{id}/publication` → `{ publishingActions, entries, blockers, moreCount, cascadeTag }`. `publishingActions` — единственный перечень действий, публикующих версию: какие из доступных пользователю сейчас `actions` её опубликуют. Это `approve` на шаге HR; `accept-changes`, если версию вернул шаг HR; `submit`, `approve` шага 1 и `accept-changes` после возврата с шага 1, если следующим шагом будет автосогласование HR (автор и есть ответственный HR; `MatrixWorkflow.ToHrAsync`). SPA этого сама не вычисляет. `NoRight` считается по праву ответственного HR, поэтому предпросмотр одинаков для любого действия из перечня. Читает тот, кто читает версию, иначе 404;
  - `GET /{directions|tracks|categories|competencies|scales}/{id}/publication` → `{ entries, blockers, moreCount, cascadeTag }`; невидимая запись — 404, без права утверждать — 403.
  `cascadeTag` — хэш корня (id, version) и упорядоченных пар (id, version) сущностей перечня; передаётся параметром `?cascade=<tag>`. `If-Match` корня ловит изменения самого корня, тег — изменения вокруг него. Публикует ли переход версии (`submit`, `approve`, `accept-changes`), решается под блокировками в момент исполнения: публикующее исполнение без тега или с тегом, не совпавшим с пересчитанным, — 412, ничего не меняется; непубликующее тег не проверяет. `approve` и `activate` записи с непустым каскадом — то же правило; если публикуется только сама запись, тег не проверяется. В 412 из-за тега поле `publication` — адрес свежего предпросмотра корня, по нему SPA отличает этот 412 от 412 по `If-Match`; SPA заново показывает перечень для подтверждения, без автоповтора. Тег в SPA передают только экраны сценариев стола (переходы версии — с действием из `publishingActions`, перечень которого пользователь подтвердил) и утверждение записей (`/desk/drafts` и окна утверждения раздела «Карьерная модель» — всегда, в том числе при пустом перечне, после предпросмотра). `web/src/features/career/MatrixPage.tsx` публикующих переходов не выполняет: `submit`, `approve` и `accept-changes` убраны из `TRANSITION_BUTTONS`, вместо них ссылки на сценарии (`desk.md`); `transitMatrixVersion` (`matrixApi.ts`) остаётся общим клиентом переходов.
- Запись хранителем: действующая запись не получает черновых ссылок в обход каскада. `POST` направления, категории, компетенции или шкалы, которую `CatalogViewer.StatusOfNew` создал бы действующей, проверяет ссылки каскада: есть черновые — запись создаётся черновиком (`status = Draft` в ответе 201, SPA предлагает «Утвердить» через предпросмотр записи), нет — действующей, как прежде. `PUT` действующей записи: ссылка, которую правка задаёт заново, должна быть действующей, черновая — 400 с ошибкой поля, запись не меняется; проверка — в `ReferenceProblemAsync`, которая для действующей записи требует от `CatalogStore.IsUsableAsync` действующую ссылку (у черновика правило прежнее — действующая или черновик автора).
- Отклонено решениями пользователя 2026-10-13 (не пересматривать без нового решения):
  - публикация без каскада, то есть простой запрет публиковать запись со ссылками на черновики;
  - право действующего пользователя при публикации версии: руководитель черновики не утверждает, и публикация, запущенная не HR, отвечала бы `NoRight`;
  - каскад при создании записи с предпросмотром несохранённой записи: понадобился бы метод предпросмотра по телу запроса;
  - тег с результатом маршрута и ответственным HR при каждом переходе версии: смена HR отклоняла бы непубликующие переходы;
  - необязательный тег у переходов версии: переход, ставший публикующим после предпросмотра, опубликовал бы неподтверждённый перечень;
  - перевод действующей записи в черновик при правке с черновой ссылкой: компетенция выпала бы из опубликованных матриц;
  - публикующие переходы на `MatrixPage` через предпросмотр и тег: перечень, подтверждение и обработка 412 повторились бы рядом с экранами сценариев.
- `src/Competency.CareerFramework/CareerMailQueue.cs`: письма-напоминания. После `CommitAsync`, когда блокировки сняты, действие определяет получателей по состоянию после действия (ход уже вычислен для ответа, `StateAsync`) и кладёт готовые письма в ограниченный `Channel` на 1 000; при переполнении письмо отбрасывается с предупреждением в лог. Элемент очереди — id получателя, вид, тема, текст, кто совершил действие, `request_id` исходного запроса. Один читатель — `BackgroundService` модуля, по одному письму, в своём scope: перечитывает учётную запись и сотрудника, отправляет через `MailSender.SendAsync`, при `false` пишет `Mail.SendFailed` через `IAuditWriter.WriteAsync` (`audit.md`); исключения ловятся внутри цикла и пишутся в лог типом. Ответ действия не ждёт SMTP, отказ отправки действие не откатывает. **Принятый риск (решение пользователя 2026-10-13):** письма теряются при перезапуске процесса и при переполнении очереди, как у `PasswordResetQueue`; outbox не делается, пользователь не видит, ушло ли письмо. Получатели:
  - `submit`, версия ушла на шаг 1 или 2 — согласующий хода (шаг 1 — вышестоящий руководитель, шаг 2 — ответственный HR); письма нет при автосогласовании и публикации;
  - согласование шага 1, версия ушла на шаг HR — ответственный HR; письма нет при автосогласовании (автор и есть HR) и публикации;
  - `accept-changes`, версия пошла дальше по маршруту — согласующий следующего хода (HR); письма нет при публикации;
  - `return` — текущие руководители подразделения матрицы (`HeadAccountAsync`; отклонено: `AuthorId` версии — автором по требованиям считается текущий руководитель подразделения матрицы);
  - руководитель, не хранитель записи, создал черновое направление, трек, категорию, компетенцию или шкалу — ответственные HR подразделений, которыми автор руководит сейчас, без повторов; для трека — HR подразделения трека. Письма нет для уровней, при отсутствии HR, если автор больше не руководит и если запись создал хранитель (в том числе черновой трек HR или администратора).
  Письмо не уходит тому, кто совершил действие, а также заблокированной, приглашённой (без пароля) учётной записи и учётной записи уволенного сотрудника — это проверяется при отправке по `UserStatus.IsActive` и по тому, работает ли привязанный сотрудник. Тексты — строковые константы, как в `AccountMail`. Ссылка — `App:PublicBaseUrl` плюс маршрут SPA `/desk/review/{versionId}`, `/desk/rework/{versionId}` или `/desk/drafts/{kind}/{entryId}` (`desk.md`); комментария согласующего, разницы и состава версии, токенов и адресов в письме нет. Других писем модуль не шлёт.
- Источник стола (внутренний класс `IDeskSource`, регистрируется в `AddCareerFrameworkModule`): находки по данным модуля — версии матриц (ждут согласования на шаге 1 или HR, возвращены, в работе, задержались на шаге 1), подразделения без опубликованной матрицы, без ответственного HR и, для HR, без руководителя, черновики на утверждение и собственные черновики автора, проверки связей и треков (должность без трека, трек без должностей, уровень без должности, трек без уровней или с одним уровнем), расхождения опубликованной матрицы с треком и каталогом, неиспользуемые записи каталога, «для вашей должности нет трека». Здесь же подавления, которым нужны данные модуля: версия в работе подавляет находки «нет опубликованной матрицы» и об опубликованной матрице, даже если о самой версии пользователю ничего не показано; черновой трек на утверждении получает пометку «утверждать рано» вместо отдельных находок о треке. Видимость — `MatrixRoute.ReadableAsync` и `CatalogViewer.Sees`, ход и роли — `ProcessRoles`, `MatrixRoute`, правило `/drafts`. Данные (версии, решения, черновики, треки, уровни, связи, закрепления HR, учётные записи руководителей и HR) читают несколько наборных запросов на источник, без запросов внутри циклов.
- `src/Competency.CareerFramework/DeletionBlockers.cs`, `DeletionRefusal.cs`, `CatalogStore.cs` (`MatricesUsing`, `RemoveHistoryRow`): физическое удаление записей справочников и матриц без опубликованных версий (`DELETE`, `If-Match`; у матрицы — версии в работе, проверяется до удаления зависимых строк). Ссылки по столбцам держат внешние ключи `RESTRICT`, ссылки из `content` версий, их вариантов и `snapshot` — запрос `jsonb @>`. Отказ — 409 `DeletionRefusal`: `blockers` (до 5 мешающих записей, видимых пользователю: вид, id, название, контекст) и `moreCount` (остальные, невидимые включительно). Удаление строк истории (`competency_versions`, варианты, решения) журналирует `RemoveHistoryRow` (`audit.md`).
- `src/Competency.Platform/Migrations/` (общая линия миграций): `OrgUnitHr`, `CareerCatalogues` (начальные данные — общие категории компетенций и базовая шкала 0–4 с фиксированными Guid, без событий журнала), `CompetencyMatrices`, `CatalogOwnership`, `RemoveCareerLevelSalary`, `SimplifyCareerLevels`, `WidenMatrixDecisionKind`, `CareerLevelPositions` (только схема: связи не заполняются, опубликованные матрицы и действующие треки не трогаются; `Down` удаляет таблицу) и миграция колонки `matrix_versions.builder_step` (без заполнения).
