Область: SQL-диалект и функции PostgreSQL 18, которыми пользуется проект (FTS, `pg_trgm`, очереди `SKIP LOCKED`). Образ/эксплуатация `db` (workload, PVC, probes) — в `postgresql-18.6.md` и `postgres-image-18.6-trixie.md`.

## API surface used in project
- Полнотекстовый поиск, конфигурация `russian` (`pg_catalog.russian`, Snowball; присутствует в стандартной поставке — пример `\dF russian` в документации psql):
  `to_tsvector('russian', name || ' ' || description)`, `websearch_to_tsquery('russian', :q)` / `plainto_tsquery`, оператор `@@`, `ts_rank`; индекс GIN по `tsvector`. Из EF Core — через Npgsql (`HasGeneratedTsVectorColumn`, `Matches`), см. `npgsql-entityframeworkcore-postgresql-10.0.3.md`.
- `pg_trgm`: `CREATE EXTENSION pg_trgm;` операторы/функции `%`, `similarity()`, `word_similarity()`; индексы `USING GIN (col gin_trgm_ops)` (поддерживают `LIKE`/`ILIKE`/`~`/`~*`) и `gist_trgm_ops` (быстрее для `ORDER BY ... <->  LIMIT`); пороги по умолчанию: `pg_trgm.similarity_threshold` 0.3, `word_similarity_threshold` 0.6, `strict_word_similarity_threshold` 0.5; сравнение регистронезависимое в стандартной сборке.
- Очереди/outbox: `SELECT … FROM job WHERE status = 'pending' ORDER BY id LIMIT :n FOR UPDATE SKIP LOCKED` в той же транзакции, что и фиксация результата. Синтаксис: `FOR lock_strength [OF …] [NOWAIT | SKIP LOCKED]`.
- Доступные в PG 18 (используются только при явном решении design): `uuidv7()` (+ алиас `uuidv4()`); `RETURNING OLD/NEW` для INSERT/UPDATE/DELETE/MERGE; виртуальные generated-колонки (`GENERATED ALWAYS AS (...) VIRTUAL`, теперь значение по умолчанию); skip scan для многоколоночных B-tree.
- Сырой SQL из приложения — только параметризованный (`FromSql`/`ExecuteSql` с интерполяцией EF Core), без конкатенации значений.

## Version-specific notes
- FTS и `pg_trgm` (PG 18, формулировка release notes): «Change full text search to use the default collation provider of the cluster to read configuration files and dictionaries, rather than always using libc». Для кластеров с не-libc провайдером по умолчанию (ICU, builtin) поведение некоторых FTS-функций и `pg_trgm` может измениться; после `pg_upgrade` таких кластеров рекомендуется переиндексировать индексы FTS и `pg_trgm`. Официальный образ по умолчанию инициализируется с локалью `en_US.utf8`; русская сортировка/ICU (`POSTGRES_INITDB_ARGS="--locale-provider=icu --icu-locale=ru-RU"` показан в README для Alpine; для образа Debian доступность ICU-локалей проверять spike'ом в `pg_collation`) — открытый пункт design (`stack.html`).
- 18.6 (2026-08-13) — минор с исправлениями безопасности (в числе затронутых компонентов: ограничение длины `tsvector`/`tsquery`, `contrib/pg_trgm` GiST, `to_char()`, regexp-функции; полный список CVE — в release notes). Требуемые действия после обновления с любого 18.x по release notes: проверить `reltuples` у GIN-индексов (запрос в release notes), при использовании `btree_gist`/`ltree` — возможна переиндексация; при обновлении с версий < 18.2 — дополнительные шаги (раздел E.4 release notes).
- Docker-образ PG 18: `PGDATA=/var/lib/postgresql/18/docker`, объявленный `VOLUME` — `/var/lib/postgresql` (изменено относительно ≤17); PVC монтировать в `/var/lib/postgresql`. Для `--user` с произвольным UID `initdb` требует записи пользователя в `/etc/passwd` (варианты: `nss_wrapper`, bind-mount `/etc/passwd`, предварительный `chown` тома). Секреты: суффикс `_FILE` (`POSTGRES_PASSWORD_FILE`).
- Минорные релизы выходят не реже раза в 3 месяца; сообщество рекомендует всегда работать на текущем миноре (обновление без dump/restore) — синхронизировано с регламентом патчей в `stack.html`.
- Виртуальные generated-колонки (PG 18, по умолчанию `VIRTUAL`): выражение только из встроенных иммутабельных функций и типов, без пользовательских типов/функций, без ссылок на другие generated-колонки, без default/identity. Для tsvector под GIN Npgsql создаёт STORED-колонку (документация Npgsql).
- `SKIP LOCKED`: даёт «несогласованный» срез данных — подходит для очередей, не для общих запросов; блокировка строк, но `ROW SHARE` на таблицу берётся как обычно; `ORDER BY` + блокирующее предложение на `READ COMMITTED` может вернуть строки не по порядку (обход из документации — подзапрос с `FOR UPDATE`, но он блокирует все строки).

## Deprecations and breaking changes from prior version (PG 17 → 18)
- `initdb` включает контрольные суммы данных по умолчанию (`--no-data-checksums` отключает; `pg_upgrade` требует совпадения настроек).
- FTS/`pg_trgm` читают конфигурацию и словари через провайдер коллации кластера по умолчанию (см. выше).
- MD5-пароли объявлены устаревшими (предупреждение при `CREATE/ALTER ROLE`; `md5_password_warnings`) — использовать SCRAM.
- `VACUUM`/`ANALYZE` по умолчанию обрабатывают потомков наследования (`ONLY` — прежнее поведение).
- `COPY FROM` в CSV больше не трактует `\.` как конец данных (`\.` должна стоять отдельной строкой); старые клиенты psql могут давать проблемы с `\copy`.
- Запрещены unlogged-партиционированные таблицы; AFTER-триггеры выполняются от роли, поставившей событие в очередь; убраны неработающие привилегии на rules; `pg_backend_memory_contexts`: убрана колонка `parent`, `level` — с единицы; приоритет сокращений часовых поясов сессии над `timezone_abbreviations`.
- Generated-колонки по умолчанию виртуальные (раньше всегда stored).

## Project conventions
- SQL — через EF Core; сырой SQL точечно (FTS-запросы, claim-запрос очереди `SKIP LOCKED`), всегда параметризованный; значения параметров и PII не логируются.
- Схема и расширения (`pg_trgm`) создаются миграциями EF Core (`HasPostgresExtension`), не ручным DDL; применяет их само приложение при старте (см. `efcore-10.0.12.md`).
- Очередь/outbox в той же БД: claim и результат — в одной транзакции; обработчики идемпотентны; параметры lease/повторов — design.
- Время хранить в `timestamptz` (UTC); кластер — UTF-8; локаль/collation для русской сортировки фиксируется при `initdb` (design, открытый пункт `stack.html`).
- Целевая версия функций — PG 18; приложение не должно требовать функций новее 18.x.

## Known issues and workarounds
- Поведение FTS/`pg_trgm` для кириллицы (регистр, `ё`/`е`, морфология `russian`) в документации PG не расписано — проверить на тестовых данных проекта до фиксации индексов; после смены локали/провайдера коллации — `REINDEX` FTS/trgm-индексов.
- PVC монтируется **только** в `/var/lib/postgresql` (на образах PG 18 `VOLUME` изменён, `PGDATA=/var/lib/postgresql/18/docker`, README docker-library). При монтировании в иной путь (в т.ч. прежний `/var/lib/postgresql/data` или `/data`) кластер создаётся вне PVC — в записываемом слое контейнера — и теряется при пересоздании pod'а (следствие из ENV; ошибка монтирования из docker-library/postgres#1370 — симптом Docker, не режим отказа Kubernetes).

### Advisory-блокировки уровня транзакции
Источники: https://www.postgresql.org/docs/18/functions-admin.html (9.28.10 Advisory Lock Functions), https://www.postgresql.org/docs/18/explicit-locking.html (13.3.4 Deadlocks, 13.3.5 Advisory Locks), https://www.postgresql.org/docs/18/view-pg-locks.html, https://www.postgresql.org/docs/18/runtime-config-locks.html, https://www.postgresql.org/docs/18/transaction-iso.html, https://www.postgresql.org/docs/18/errcodes-appendix.html
- `pg_advisory_xact_lock(bigint)` — эксклюзивная, `pg_advisory_xact_lock_shared(bigint)` — разделяемая блокировка уровня транзакции; обе при конфликте ждут («waiting if necessary») и возвращают `void`. Без ожидания — `pg_try_advisory_xact_lock[_shared]` → `boolean`.
- Совместимость на одном ключе (документация): «a shared lock does not conflict with other shared locks on the same resource, only with exclusive locks»; exclusive конфликтует и с shared, и с exclusive. Сессионные и транзакционные запросы на один ключ блокируют друг друга обычным образом. Повторный запрос уже удерживаемой блокировки той же сессией всегда успешен, даже если другие ждут.
- Освобождение: транзакционная блокировка держится до конца транзакции (`COMMIT` или `ROLLBACK`), ручного снятия нет (`pg_advisory_unlock*` — только для сессионных). В EF Core — до `Commit` либо до `Dispose` незафиксированной транзакции (откат).
- Ключ `bigint` и пара `integer` — непересекающиеся пространства ключей (`5001001` как `bigint` и `(0, 5001001)` — разные блокировки). Блокировки локальны для БД. В `pg_locks`: `locktype = 'advisory'`, старшая половина `bigint` в `classid`, младшая — в `objid`, `objsubid = 1`; кто кого держит — `pg_blocking_pids()`. Advisory и обычные блокировки делят общий пул (`max_locks_per_transaction`, по умолчанию 64, × `max_connections`) — при нескольких фиксированных ключах неактуально.
- Взаимоблокировки. Документация: deadlock обнаруживается автоматически, прерывается одна из транзакций (какая — «difficult to predict and should not be relied upon»), SQLSTATE `40P01 deadlock_detected`; проверка запускается после ожидания блокировки дольше `deadlock_timeout` (по умолчанию `1s`). Пока deadlock не обнаружен, ожидание не ограничено (в проекте его ограничивает таймаут команды, комментарий `OrgTree.BeginExclusiveAsync`). Ожидание строки видно в `pg_locks` как ожидание `transactionid` её держателя, ожидание advisory — как `advisory`; про обе записи `pg_locks` сказано «sleep until the other lock is released (or a deadlock situation is detected)». Вывод (отдельно для advisory в документации не оговорено): смешанный цикл «A держит advisory и ждёт строку ↔ B держит строку и ждёт advisory» разрывается так же, `40P01`.
- Правило порядка (документация: «acquire locks on multiple objects in a consistent order», «the first lock acquired on an object in a transaction is the most restrictive mode that will be needed»): advisory-блокировки — первыми командами транзакции и во всех путях в одном порядке (дерево → прочие ключи → `FOR UPDATE` строк); не повышать shared → exclusive на том же ключе внутри транзакции — две транзакции, держащие shared и запросившие exclusive, ждут друг друга (`40P01`).
- Изоляция: на `READ COMMITTED` каждая команда видит снимок на момент своего старта, поэтому команды после получения блокировки видят то, что зафиксировал предыдущий держатель. На `REPEATABLE READ` снимок берётся на старте первой не-управляющей команды транзакции — если это сам `SELECT pg_advisory_xact_lock(…)`, снимок сделан до ожидания и изменения предыдущего держателя не видны. Блокировки — только на `READ COMMITTED` (умолчание PostgreSQL и проекта).
- Проект: ключ `5001001` — блокировка дерева оргструктуры, первой командой после `BEGIN`: эксклюзивно — `OrgTree.BeginExclusiveAsync`, разделяемо (`pg_advisory_xact_lock_shared(5001001)`) — `OrgTree.BeginSharedAsync` (`src/Kalibr.OrgStructure/OrgTree.cs`); ключ `5003001` — справочники карьерной модели, в обоих режимах (`src/Kalibr.CareerFramework/CatalogStore.cs`). По правилам выше разделяемые захваты одного ключа идут параллельно друг другу и ждут эксклюзивного, эксклюзивный ждёт всех. Порядок ключей и строк в проекте — `stack.html`, «Целостность на уровне данных».

### Частичные и выражательные уникальные индексы
Источники: https://www.postgresql.org/docs/18/indexes-partial.html (пример 11.3), https://www.postgresql.org/docs/18/indexes-expressional.html, https://www.postgresql.org/docs/18/sql-createindex.html, https://www.postgresql.org/docs/18/sql-createtable.html (`DEFERRABLE`; Compatibility → Non-Deferred Uniqueness Constraints), https://www.postgresql.org/docs/18/index-unique-checks.html
- Частичный уникальный индекс `CREATE UNIQUE INDEX … ON t (cols) WHERE predicate` «enforces uniqueness among the rows that satisfy the index predicate, without constraining those that do not». В предикате — только колонки таблицы, без подзапросов и агрегатов; функции в предикате и выражениях индекса — `IMMUTABLE`. `UNIQUE`-ограничение в `CREATE TABLE` предиката не принимает: частичная уникальность — только индексом (или `EXCLUDE … WHERE (predicate)`, который создаёт частичный индекс внутри).
- Использование частичного индекса для поиска: условие запроса должно на этапе планирования «mathematically imply» предикат; параметр вместо литерала из предиката этому не удовлетворяет. На проверку уникальности это не влияет.
- NULL: по умолчанию `NULLS DISTINCT` (несколько NULL допустимы), `NULLS NOT DISTINCT` — запрет.
- Индекс по выражению: `CREATE UNIQUE INDEX … ON t (lower(name))` запрещает значения, отличающиеся только регистром («indexes on expressions can be used to enforce constraints that are not definable as simple unique constraints»). Выражение вычисляется при каждой вставке и не-HOT обновлении; поиск через индекс — запросом с тем же выражением (пример документации: `WHERE lower(col1) = 'value'` по индексу `(lower(col1))`). Скобки вокруг выражения можно опустить, если это вызов функции.
- Момент проверки: неотложенный `UNIQUE`/`PRIMARY KEY` проверяется «immediately whenever a row is inserted or modified», а не в конце команды, как требует стандарт SQL («this makes a difference when, for example, a single command updates multiple key values»); уникальный индекс проверяется так же (`UNIQUE_CHECK_YES`: «the uniqueness check must be done immediately»). `DEFERRABLE` принимают только ограничения `UNIQUE`, `PRIMARY KEY`, `EXCLUDE`, `REFERENCES`; у `CREATE INDEX` такой опции нет — частичный уникальный индекс отложить нельзя. Отложенное ограничение не может быть арбитром `ON CONFLICT`, и документация предупреждает, что такая проверка «can be significantly slower».
- Следствие для смены «опубликованной» строки: одна команда, меняющая обе строки (`UPDATE … SET status = CASE …` по двум id), может получить `23505 unique_violation` в зависимости от порядка обработки строк. Две команды в одной транзакции в порядке «старую строку вывести из-под предиката → новую ввести» конфликта не дают: при второй команде старая версия строки уже удалена текущей транзакцией («If a conflicting valid row has been deleted by the current transaction, it's okay»; `UPDATE` удаляет старую версию строки). Обратный порядок — `23505` сразу.
- Гонка: если конфликтующую строку вставила или изменила ещё не зафиксированная транзакция, вставка ждёт её завершения и повторяет проверку — после фиксации первой `23505`, после отката — успех. Поэтому индекс остаётся страховкой и без advisory-блокировки.

### `lower()`/`upper()` и кириллица
Источники: https://www.postgresql.org/docs/18/functions-string.html, https://www.postgresql.org/docs/18/locale.html, https://www.postgresql.org/docs/18/collation.html, https://www.postgresql.org/docs/18/functions-matching.html, https://raw.githubusercontent.com/postgres/postgres/REL_18_STABLE/src/backend/utils/adt/like.c (`Generic_Text_IC_like`); для сравнения с .NET — https://learn.microsoft.com/en-us/dotnet/api/system.string.trim (`Trim()` удаляет символы, для которых `Char.IsWhiteSpace` истинно)
- `lower`/`upper` — «according to the rules of the database's locale». При провайдере `libc` это `LC_CTYPE` БД («Character classification (What is a letter? Its upper-case equivalent?)»); `LC_COLLATE`/`LC_CTYPE` фиксируются при создании БД и не меняются. Явный `COLLATE` в выражении переопределяет: коллации учитываются `lower`, `upper`, `initcap`, сопоставлением с образцом и `to_char`.
- Кластер проекта: `datctype = datcollate = en_US.utf8`, `datlocprovider = c` (libc), UTF8 (spike, `postgres-image-18.6-trixie.md`, «Локаль и поиск»; в образе сгенерирована только `en_US.UTF-8`) — регистр кириллицы преобразуется по glibc-локали `en_US.UTF-8`.
- `ё`/`Ё`. `ILIKE` в многобайтовой кодировке вызывает `lower()` для образца и строки и затем сравнивает с учётом регистра (`like.c`, REL_18_STABLE), поэтому проверенное spike'ом поведение `ILIKE` — это поведение `lower()` в кластере проекта: `'ЁЖ' ILIKE '%ёж%'` — истина (`lower('Ё') = 'ё'`, регистровая пара Unicode U+0401/U+0451), `'Пётр' ILIKE '%петр%'` — ложь (`lower` не сводит `ё` к `е`). Следствие для уникального индекса по `lower(name)`: «Ёлка» и «ёлка» — дубликаты, «Ёлка» и «Елка» — разные значения. Отдельным `SELECT lower(…)` не проверялось.
- `casefold()` (PG 18): при `libc` «identical to lower». Провайдер `builtin` (`C.UTF-8` — простая конверсия регистра Unicode, `PG_UNICODE_FAST` — полная) выбирается только при создании БД/коллации; в проекте не используется.
- `btrim(s)`/`trim(s)` без второго аргумента удаляют только пробел («a space by default»): табуляция, переводы строк, неразрывный пробел остаются. .NET `string.Trim()` удаляет все пробельные символы Unicode — нормализация в SQL (миграция) и в приложении расходится на строках с такими символами, если набор символов в `btrim` не задан явно.

### `WITH RECURSIVE`: порядок цепочки предков
Источник: https://www.postgresql.org/docs/18/queries-with.html (7.8.2 Recursive Queries, 7.8.2.1 Search Order, 7.8.2.2 Cycle Detection)
- Порядок строк рекурсивного запроса не гарантирован: реализация выдаёт результат в порядке обхода в ширину, но это «an implementation detail and it is perhaps unsound to rely on it»; порядок внутри уровня не определён. Порядок задаёт только внешний `ORDER BY` по вычисляемой колонке — глубине (`0` в нерекурсивной части, `depth + 1` в рекурсивной). У цепочки предков на каждом уровне одна строка, поэтому `ORDER BY depth` даёт полный порядок «от ближайшего». Встроенный вариант — `SEARCH BREADTH FIRST BY id SET ordercol` (или `DEPTH FIRST`) и `ORDER BY ordercol`.
  ```sql
  WITH RECURSIVE chain(id, parent_id, depth) AS (
      SELECT u.id, u.parent_id, 0 FROM org_units u WHERE u.id = {unitId}
    UNION ALL
      SELECT p.id, p.parent_id, c.depth + 1
      FROM org_units p JOIN chain c ON p.id = c.parent_id
  )
  SELECT id, depth FROM chain ORDER BY depth;
  ```
- Циклы: `UNION` отбрасывает только полностью совпадающие строки; с колонкой глубины строки различаются, и при цикле в `parent_id` запрос не завершится («just changing UNION ALL to UNION would not eliminate the looping»). Защита — `CYCLE id SET is_cycle USING path` либо массив пройденных id. БД цикл в `org_units.parent_id` не запрещает (ацикличность держит приложение под блокировкой дерева); существующие запросы `OrgTree` без глубины завершаются за счёт `UNION`.
- `LIMIT` во внешнем запросе останавливает вычисление CTE, только если результат не сортируется: с `ORDER BY depth` CTE вычисляется целиком, так что `LIMIT` — не защита от цикла.

### `jsonb`: хранение документа и сравнение
Источники: https://www.postgresql.org/docs/18/datatype-json.html (8.14, 8.14.4 jsonb Indexing), https://www.postgresql.org/docs/18/functions-json.html (9.16.1), https://www.postgresql.org/docs/18/collation.html
- `jsonb` хранится в разобранном двоичном виде: пробелы и порядок ключей не сохраняются, из дублирующихся ключей остаётся последний (`json` хранит текст как есть). Порядок ключей при выводе — порядок хранения (короткие ключи раньше длинных), а не исходный. Числа — по правилам `numeric`: `1.230e-5` выводится как `0.00001230`, хвостовые нули дробной части сохраняются.
- Сравнение: «the usual comparison operators … are available for `jsonb`, though not for `json`» и следуют правилам упорядочения B-tree для `jsonb`: Object > Array > Boolean > Number > String > null; объект с большим числом пар больше; объекты с равным числом пар сравниваются по ключам и значениям в порядке хранения, массивы — поэлементно с учётом порядка. Примитивы — по правилам базового типа: числа как `numeric` (`1.0` = `1`, хотя выводятся по-разному), строки — по коллации БД по умолчанию (`en_US.utf8`, детерминированная: равны только побайтно совпадающие строки, без нормализации Unicode). Следствие: два документа с одинаковым содержимым и разным порядком ключей равны (`=`), разный порядок элементов массива — не равны.
- B-tree и hash-индексы на `jsonb` «usually useful only if it's important to check equality of complete JSON documents»; для сравнения двух значений в одной строке индекс не нужен.
- Содержание `@>` (8.14.3): «the contained object must match the containing object as to structure and data contents, possibly after discarding some non-matching array elements or object key/value pairs from the containing object»; порядок элементов массива не важен, повторы считаются один раз. Поэтому `content -> 'levels' @> jsonb_build_array(jsonb_build_object('levelId', '<id>'))` истинно, если в массиве есть объект с таким полем, какие бы ещё поля у него ни были; вложенность должна совпадать уровень в уровень. Так проект ищет ссылки на уровень или компетенцию в документах версий матриц, их вариантах и снимках (`CatalogStore.MatricesUsing`) — внешний ключ такие ссылки не держит. `@>` поддерживают оба GIN-класса (`jsonb_ops` по умолчанию и `jsonb_path_ops`, 8.14.4); проект индекс не создаёт — версий матриц немного.
