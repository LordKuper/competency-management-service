# Рабочий стол (`desk`)

## Purpose

Ожидаемые действия пользователя из всех подсистем: сбор находок модулей, правило «один объект — один пункт», поглощение и порядок причин, группы, счётчик и API стола. Стол вычисляется на сервере при каждом запросе; собственных таблиц, миграций и кэша нет. Модуль зависит только от `Competency.Platform`, модули о нём не знают: находки они отдают через контракт `IDeskSource` из Platform.

## Key paths

- `src/Competency.Desk/`: корень модуля; наружу выходят только `Add…Module` и `Map…Endpoints`, хост регистрирует модуль вместе с остальными. Модуль собирает все `IDeskSource` и сливает находки строго в этом порядке: 1) убирает повтор одной находки, пришедшей по нескольким ролям; 2) применяет явные пары поглощения, в том числе через «предмет» находки; 3) применяет общее правило «действие поглощает справочное по тому же объекту»; 4) упорядочивает причины; 5) относит пункт к группе по первой видимой причине; 6) считает пункты-действия. Шаги 2 и 3 не переставляются: иначе действие «подразделение без руководителя» поглотит справочное «пустое подразделение», которое по явной паре поглощает его само. Таблицы поглощения и порядка причин занимают одно место в коде модуля.
- Методы `src/Competency.Desk/` (только аутентифицированному и только про себя; параметра «чей стол» нет, чужой стол не получить по построению):
  - `GET /api/v1/desk` → `{ actionCount, groups: [{ group, isReference, total, items }] }` — только непустые группы, в `items` первые 10 пунктов;
  - `GET /api/v1/desk/items?group=…&group=…&limit=` → `{ items, total }` — «Показать ещё» перечитывает группы с начала на 10 + 20·k строк: пункты исчезают по мере выполнения, поэтому смещения нет. Предел `limit` — константа модуля, 2 000 строк, а не `ListRequest`; `limit` меньше 1 — 400 с ошибкой поля, больше предела — отдаётся предел. Это документированный потолок стола, а не страница: строки группы за пределом на столе недостижимы, хвост справочной группы доступен только в очередях сценариев и разделах. Строк меньше и запрошенного, и `total` — группа усечена: SPA пишет об этом под таблицей и прячет «Показать ещё»;
  - `GET /api/v1/desk/count` → `{ actionCount }`.
  `DeskItem`: объект (тип, id, название, контекст), `group`, `isReference`, причины в порядке таблицы (вид, момент события — только у событийных видов, типизированные параметры), идентификаторы переходов, встроенное действие (учётная запись и её `version` для `resend-invitation`). Тексты причин и названия групп SPA рисует по виду, сервер отдаёт данные, а не фразы. Строки группы упорядочены по моменту события по возрастанию, затем по названию, затем по id. Блок «Что можно сделать» SPA строит по ролям сессии (`/auth/me`, `/career/me`) и `total` групп; своего API у него нет.
- Вычисление: стол и счётчик пересчитываются из текущих данных на каждый запрос; счётчик — та же выборка, отданная числом, второго алгоритма подсчёта нет. Хранимых задач нет — действия вычисляются из данных и вручную не закрываются (отклонено: таблица действий, которую обновляют события модулей). Серверного кэша нет: собственное действие сразу меняет счётчик, а сбрасывать кэш по изменениям трёх модулей сложнее, чем пересчитать. Источники читают данные наборными запросами с постоянным числом обращений к БД (снимок оргструктуры — `org-structure.md`) и считают правила в памяти теми же функциями, которыми модуль проверяет действие. Бюджет на сиде `tests/perf/seed-10k.sql` (10 000 работающих сотрудников) для администратора, HR с закреплением на корне, руководителя верхнего подразделения и сотрудника: `GET /desk/count` — p95 ≤ 300 мс, `GET /desk` — p95 ≤ 600 мс, не больше 25 SQL-команд на запрос независимо от объёма данных, самая большая группа каждого меньше 2 000. Вычисление дольше 1 с пишет в лог предупреждение: роль и время по источникам, без ПДн. Пересмотр: бюджет не выполнен (тогда короткая память результата на пользователя со сбросом после его мутаций), организация выросла на порядок или группа упёрлась в предел.
- `src/Competency.Platform/`: контракт находок — `IDeskSource.FindAsync(CancellationToken)` возвращает `IReadOnlyList<DeskFinding>` вошедшего пользователя (`ICurrentActor`). `DeskFinding`: вид (`DeskKind` — по члену на вид, а варианты одного вида с разным поглощением — отдельными членами); объект (`DeskObjectType`, id, название, контекст); необязательный «предмет» — объект другого типа, к которому относится находка, для поглощения поперёк объектов; признак «действие» или «справочно»; момент события (только у событийных видов); типизированные параметры причины; идентификаторы перехода и встроенного действия. Реализации — внутренние классы `org-structure`, `user-management` и `career-framework`, каждый регистрирует свою в `Add…Module`; какие находки считает модуль — в его `<id>.md`. Источник сам ограничивает область видимости ролями пользователя и берёт те же функции прав, которыми модуль проверяет действие; неопубликованное попадает только к тем, кто читает его по правилам `career-framework`. Новый вид — правка `DeskKind` в Platform и таблиц `desk`. Нужны тесты согласия: что стол показывает, сервер не отклоняет 403/409, и наоборот.
- `web/src/features/desk/`: стол и экраны сценариев. Маршруты регистрирует `routes.ts` по соглашению фич:
  - `/` — перенаправление на `/desk` (вместо `LandingPage`);
  - `/desk` — рабочий стол;
  - `/desk/review/:versionId` — «Согласовать версию», ссылка в письме;
  - `/desk/rework/:versionId` — «Доработать возвращённую версию», ссылка в письме;
  - `/desk/drafts`, `/desk/drafts/:kind/:entryId` — «Утвердить черновые записи», `kind` ∈ `direction`, `track`, `category`, `competency`, `scale`; ссылка в письме;
  - `/desk/matrix-builder` — «Построить матрицу», новая матрица; `?unitId=&trackId=` — предвыбор из пункта стола;
  - `/desk/matrix-builder/:versionId` — продолжение: `?step=3` или `?step=5` — вход из «Доработать», иначе шаг `builderStep` версии (так открывают и мастер, и ссылка «Перейти к отправке в мастере» со страницы матрицы);
  - `/desk/connect-unit`, `/desk/connect-unit/:unitId` — «Подключить подразделение»;
  - `/desk/onboard-employee` — «Принять сотрудника»;
  - `/desk/my-place` — «Моё место в компании»;
  - `/desk/track-positions`, `/desk/track-positions/:trackId` — «Связать должности с треком»; кнопка возврата выбирается по состоянию навигации, а не по адресу;
  - `/desk/catalog-cleanup` — «Привести каталог в порядок»;
  - `/desk/org-cleanup` — «Навести порядок в оргструктуре» (та же выборка `/desk/items` по группам оргструктуры).
  Адреса из писем (`/desk/review/…`, `/desk/rework/…`, `/desk/drafts/…/…`) — публичный контракт: переименовать их можно только с перенаправлением со старого адреса. Прежние адреса работают. Пункт «Рабочий стол» со счётчиком стоит в меню первым; группа «Справочники» — поле `featureContract.NavItem.group`; раздел меню определяется по началу адреса. Экраны переиспользуют компоненты `career`, `org-structure` и `users`, копий нет. Счётчик в клиенте — ключ `['desk']`: сброс после любой успешной мутации, перечитывание при смене адреса и при возврате фокуса, без опроса по таймеру и push; до первого ответа и при ошибке метки нет (`tech-reference/tanstack-react-query-5.104.1.md`).
- **Переход на контракт API 3.1.0**: методы `/api/v1/desk*` новые, изменение аддитивное; остальные изменения контракта — `career-framework.md`.
