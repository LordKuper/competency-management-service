# Рабочий стол (`desk`)

## Purpose

Ожидаемые действия пользователя из всех подсистем: сбор находок модулей, правило «один объект — один пункт», поглощение и порядок причин, группы, счётчик и API стола. Стол вычисляется на сервере при каждом запросе; собственных таблиц, миграций и кэша нет. Модуль зависит только от `Competency.Platform`, модули о нём не знают: находки они отдают через контракт `IDeskSource` из Platform.

## Key paths

- `src/Competency.Desk/`: корень модуля; наружу выходят только `Add…Module` и `Map…Endpoints`, хост регистрирует модуль вместе с остальными. Модуль собирает все `IDeskSource` и сливает находки строго в этом порядке: 1) убирает повтор одной находки, пришедшей по нескольким ролям; 2) применяет явные пары поглощения, в том числе через «предмет» находки; 3) применяет общее правило «действие поглощает справочное по тому же объекту»; 4) упорядочивает причины; 5) относит пункт к группе по первой видимой причине; 6) считает пункты-действия. Шаги 2 и 3 не переставляются: иначе действие «подразделение без руководителя» поглотит справочное «пустое подразделение», которое по явной паре поглощает его само. Таблицы поглощения и порядка причин занимают одно место в коде модуля.
- Методы `src/Competency.Desk/` (только аутентифицированному и только про себя; параметра «чей стол» нет, чужой стол не получить по построению):
  - `GET /api/v1/desk` → `{ actionCount, groups: [{ group, isReference, total, items }], prerequisites }` — только непустые группы, в `items` первые 10 пунктов; `prerequisites` — выполненные сейчас предпосылки сценариев, массив членов `DeskPrerequisite` без повторов в порядке перечисления, пустой, если не выполнена ни одна: `ActiveUnit` — в системе есть действующее подразделение, `ActivePosition` — есть действующая должность справочника, `WorkingEmployee` — есть работающий сотрудник, уволенные не считаются (три знает `org-structure`), `VisibleTrack` — есть трек, который пользователь вправе открыть (`career-framework`), `HrAccount` — есть учётная запись с ролью HR, не заблокированная и зарегистрированная (`user-management`, только администратору), `WaveUnitAvailable` — в новую карьерную сессию можно включить хотя бы одно подразделение, за которое пользователь отвечает (`promotion`, HR и администратору);
  - `GET /api/v1/desk/items?group=…&group=…&limit=` → `{ items, total }` — «Показать ещё» перечитывает группы с начала на 10 + 20·k строк: пункты исчезают по мере выполнения, поэтому смещения нет. Предел `limit` — константа модуля, 2 000 строк, а не `ListRequest`; `limit` меньше 1 — 400 с ошибкой поля, больше предела — отдаётся предел. Это документированный потолок стола, а не страница: строки группы за пределом на столе недостижимы, хвост справочной группы доступен только в очередях сценариев и разделах. Строк меньше и запрошенного, и `total` — группа усечена: SPA пишет об этом под таблицей и прячет «Показать ещё»;
  - `GET /api/v1/desk/count` → `{ actionCount }`.
  `DeskItem`: объект (тип, id, название, контекст), `group`, `isReference`, причины в порядке таблицы (вид, момент события — только у событийных видов, типизированные параметры), идентификаторы переходов, встроенное действие (учётная запись и её `version` для `resend-invitation`). Тексты причин и названия групп SPA рисует по виду, сервер отдаёт данные, а не фразы. Строки группы упорядочены по моменту события по возрастанию, затем по названию, затем по id. Блок «Что можно сделать» SPA строит по ролям сессии (`/auth/me`, `/career/me`), `total` групп и `prerequisites`; своего API у него нет. Условия карточек по предпосылкам (требования AC-204…AC-210): «Подключить подразделение» — `ActiveUnit` и `WorkingEmployee`; «Принять сотрудника» — `ActiveUnit` и `ActivePosition`; «Связать должности с треком» — `ActivePosition` и `VisibleTrack`; «Добавить первое подразделение» (администратору, на создание подразделения в `/org-structure`) — нет `ActiveUnit`; «Добавить первую должность» (администратору, на `/positions`) — нет `ActivePosition`; «Назначить HR» (администратору, на `/users`; требования AC-218) — нет `HrAccount`; «Объявить карьерную сессию» (HR и администратору, на экран объявления `promotion`; требования AC-224) — `WaveUnitAvailable`. До ответа стола и при его ошибке предпосылки неизвестны, и ни одна из этих карточек не показывается: иначе «Добавить первое…» мелькает при каждой загрузке; по той же причине пустой блок (AC-211) определяется только по полученному ответу. Остальные карточки предпосылок не имеют. Предпосылки скрывают только карточки: маршруты сценариев их не проверяют, переходы из пунктов стола и очередей остаются.
- Вычисление: стол и счётчик пересчитываются из текущих данных на каждый запрос; счётчик — та же выборка, отданная числом, второго алгоритма подсчёта нет. Хранимых задач нет — действия вычисляются из данных и вручную не закрываются (отклонено: таблица действий, которую обновляют события модулей). Серверного кэша нет: собственное действие сразу меняет счётчик, а сбрасывать кэш по изменениям трёх модулей сложнее, чем пересчитать. Источники читают данные наборными запросами с постоянным числом обращений к БД (снимок оргструктуры — `org-structure.md`) и считают правила в памяти теми же функциями, которыми модуль проверяет действие. Бюджет на сиде `tests/perf/seed-10k.sql` (10 000 работающих сотрудников) для администратора, HR с закреплением на корне, руководителя верхнего подразделения и сотрудника: `GET /desk/count` — p95 ≤ 300 мс, `GET /desk` — p95 ≤ 600 мс, не больше 25 SQL-команд на запрос независимо от объёма данных, самая большая группа каждого меньше 2 000. Матрицы должности и общие блоки добавляют источнику `career-framework` не больше одной команды на запрос (`career-framework.md` «Источник стола»), бюджет прежний; сид замера содержит общие блоки, версии с ними и матрицы должности. Предпосылки SQL-команд не добавляют: `org-structure` берёт их из снимка оргструктуры, запомненного на запрос (его читает и источник `career-framework`), `career-framework` — из треков и `CatalogViewer`, уже прочитанных для находок, `user-management` — из запроса учётных записей, уже читаемого для находок. Вычисление дольше 1 с пишет в лог предупреждение: роль и время по источникам, без ПДн. Пересмотр: бюджет не выполнен (тогда короткая память результата на пользователя со сбросом после его мутаций), организация выросла на порядок или группа упёрлась в предел.
- `src/Competency.Platform/`: контракт находок — `IDeskSource.FindAsync(CancellationToken)` возвращает `DeskReport(Findings, Prerequisites)`: `IReadOnlyList<DeskFinding>` вошедшего пользователя (`ICurrentActor`) и `IReadOnlyCollection<DeskPrerequisite>` — выполненные предпосылки, которые источник знает по своим данным (нет таких — `[]`). Предпосылки идут в том же вызове, потому что источник считает их по данным, прочитанным для находок; стол объединяет предпосылки всех источников. `DeskPrerequisite` — строковое перечисление, как `DeskKind`: новая предпосылка — член в Platform, источник, который её знает, и условие карточки в SPA. `DeskFinding`: вид (`DeskKind` — по члену на вид, а варианты одного вида с разным поглощением — отдельными членами); объект (`DeskObjectType`, id, название, контекст); необязательный «предмет» — объект другого типа, к которому относится находка, для поглощения поперёк объектов; признак «действие» или «справочно»; момент события (только у событийных видов); типизированные параметры причины; идентификаторы перехода и встроенного действия. Реализации — внутренние классы `org-structure`, `user-management`, `career-framework` и `promotion`, каждый регистрирует свою в `Add…Module`; какие находки считает модуль — в его `<id>.md`. Источник сам ограничивает область видимости ролями пользователя и берёт те же функции прав, которыми модуль проверяет действие; неопубликованное попадает только к тем, кто читает его по правилам `career-framework`. Новый вид — правка `DeskKind` в Platform и таблиц `desk`. Нужны тесты согласия: что стол показывает, сервер не отклоняет 403/409, и наоборот.
- Находки `promotion` (`promotion.md`, требования AC-221, AC-223): виды `Promotion*` по объектам «карьерная сессия» (даты формальной проверки) и «заявка» (итоговые оценки и решение, оценка, список оценивающих, артефакты, обратная связь) и `CommissionNotFormed`, `CommissionWithoutChair` по объекту «комиссия» с «предметом» — подразделением, поэтому пустое подразделение поглощает их (`DeskRules`); у каждого вида своя группа стола. Блок «Карьерные сессии» (`PromotionWavesBlock`, требования AC-222) читает `GET /api/v1/promotion/waves/open` и свои заявки и скрыт, пока открытых и предстоящих сессий нет; своих методов у стола для него нет.
- `web/src/features/desk/`: стол и экраны сценариев. Маршруты регистрирует `routes.ts` по соглашению фич:
  - `/` — перенаправление на `/desk` (вместо `LandingPage`);
  - `/desk` — рабочий стол;
  - `/desk/review/:versionId` — «Согласовать версию», ссылка в письме;
  - `/desk/rework/:versionId` — «Доработать возвращённую версию», ссылка в письме;
  - `/desk/drafts`, `/desk/drafts/:kind/:entryId` — «Утвердить черновые записи», `kind` ∈ `direction`, `track`, `competency`, `scale`, `block`; ссылка в письме;
  - `/desk/matrix-builder` — «Построить матрицу», новая матрица; `?unitId=&trackId=` — предвыбор из пункта стола;
  - `/desk/matrix-builder/:versionId` — продолжение: `?step=3` или `?step=5` — вход из «Доработать», иначе шаг `builderStep` версии (так открывают и мастер, и ссылка «Перейти к отправке в мастере» со страницы матрицы);
  - `/desk/connect-unit`, `/desk/connect-unit/:unitId` — «Подключить подразделение», только администратору; ссылки пунктов оргструктуры на этот экран строит `connectUnitTarget`, которая HR ведёт в карточку подразделения раздела «Оргструктура» (`?unit=`);
  - `/desk/onboard-employee` — «Принять сотрудника», администратору и HR (шаг учётной записи — только администратору); `?unitId=` и (или) `?positionId=` — предвыбор на шаге 1 из строки «Руководитель» экрана «Подключить подразделение» и из очереди оргструктуры, адрес строит одна функция `deskPaths`. Подразделение принимается, только если оно есть в `GET /org-units/tree` и действует, должность — только если `GET /positions/{id}` отдаёт её действующей; неизвестный, неактивный или непрочитанный id молча отбрасывается: поле пустое, страницы ошибки нет. Пока адрес несёт предвыбор, форма шага 1 ждёт этих чтений, потому что начальные значения формы задаются один раз. Предвыбранная должность остаётся вариантом при любом выбранном подразделении. Если её нет ни в перечне подразделения, ни в перечнях его предков, «Создать сотрудника и продолжить» сначала добавляет её в собственный перечень подразделения по id (`POST /org-units/{id}/positions`), затем создаёт сотрудника, и итог показывает должность добавленной. Quick-add по названию сюда не годится: переименованную тем временем должность он создал бы заново. Это два вызова, как у «Добавить должность» в форме: если сотрудник не создан, должность остаётся в перечне, а повтор её уже не добавляет (отклонено: флаг добавления в `POST /employees` — правка контракта, хотя данные и так не теряются);
  - `/desk/my-place` — «Моё место в компании»;
  - `/desk/track-positions`, `/desk/track-positions/:trackId` — «Связать должности с треком»; кнопка возврата выбирается по состоянию навигации, а не по адресу;
  - `/desk/catalog-cleanup` — «Привести каталог в порядок»;
  - `/desk/org-import` — «Импорт оргструктуры»: мастер фичи `web/src/features/org-import/` (`org-structure.md`), администратору и HR;
  - `/desk/org-cleanup` — «Навести порядок в оргструктуре», администратору и HR (та же выборка `/desk/items` по группам оргструктуры). Главные действия находок (требования AC-212…AC-215) идут через существующие методы и экраны, новых методов нет. «Восстановить должность» вызывает `POST /positions/{id}/activate` с `If-Match` версии, прочитанной перед вызовом. «Принять сотрудника» — ссылка `?unitId=` (пустое подразделение) или `?positionId=` (неиспользуемая должность) на экран сценария с состоянием навигации, которое возвращает в очередь. У неиспользуемой должности ссылка есть, только если в `GET /org-units/tree` (его же читает форма сценария) есть действующее подразделение; до ответа и при ошибке остаётся только деактивация. `prerequisites` стола здесь не берутся: `GET /desk` перечитывался бы после каждого действия очереди.
  Адреса из писем (`/desk/review/…`, `/desk/rework/…`, `/desk/drafts/…/…`) строит `CareerMailQueue` (`career-framework.md`): переименование маршрута меняет и текст письма. Пункт «Рабочий стол» со счётчиком стоит в меню первым; группы меню («Справочники», «Администрирование», «Управление карьерными переходами») — поле `featureContract.NavItem.group`; раздел меню определяется по началу адреса. Экраны переиспользуют компоненты `career`, `org-structure` и `users`, копий нет. Уход с несохранёнными правками, включая смену шага мастера, — общий механизм `stack.html` («Несохранённые правки в SPA»). Счётчик в клиенте — ключ `['desk']`: сброс после любой успешной мутации, перечитывание при смене адреса и при возврате фокуса, без опроса по таймеру и push; до первого ответа и при ошибке метки нет (`tech-reference/tanstack-react-query-5.104.1.md`).
- `docs/product/requirements/desk.html`: требования; `docs/ux/desk.html`: UX-спецификация.
