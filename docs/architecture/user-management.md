# Управление пользователями (`user-management`)

## Purpose

Локальные учётные записи с входом по e-mail и паролю (ASP.NET Core Identity без UI, cookie-сессия), две роли — глобальный администратор и пользователь — и необязательная привязка учётной записи любой роли к одному работающему сотруднику. Учётные записи заводит только администратор, приглашением: запись создаётся без пароля, пользователь задаёт его сам по одноразовой ссылке из письма. Пароли другим администратор не задаёт — он отправляет ссылку сброса, которую пользователь может запросить и сам («Не помню пароль»). Модуль ссылается на `Competency.Platform` и `org-structure` (читает сотрудника через `IEmployeeDirectory`, реализует порт `IEmployeeAccounts`), в журнал пишет через `IAuditWriter` и `[Audited]` из Platform, письма отправляет через `MailSender` из Platform.

## Key paths

- `src/Competency.UserManagement/`: корень модуля; типы `internal`, наружу выходят `AddUserManagementModule`, `MapUserManagementEndpoints`, `EnsureBootstrapAdminAsync`.
- `src/Competency.UserManagement/AppUser.cs`, `AppUserStore.cs`, `UserManagementEntityConfiguration.cs`: `AddIdentityCore` с собственным хранилищем; Identity отображён одной таблицей `users` (без таблиц ролей, claims, логинов, токенов); роль — колонка `role` (`GlobalAdmin` / `User`, CHECK `ck_users_role`); e-mail уникален без учёта регистра и одновременно служит внутренним `UserName`; один сотрудник — не более одной учётной записи (уникальный частичный индекс по `employee_id`, внешний ключ без каскада); учётные записи не удаляются, только блокируются. **«Приглашён»** = `password_hash IS NULL` (`AppUser.IsInvited`, отдельной колонки нет): такая запись войти не может. Колонки ссылки — `link_token_hash` (уникальный частичный индекс), `link_expires_at`, `link_issued_at`, `link_security_stamp`. Allow-list журнала: `email`, `role`, `isBlocked`, `employeeId` — хэш, stamp'ы, счётчики входа и колонки ссылки в журнал не попадают.
- `src/Competency.UserManagement/AppUser.cs` (`IssueLink`, `HasValidLink`, `ClearLink`), `AccountLinkOptions.cs`: **ссылки из писем** (приглашение и сброс пароля). Провайдеры токенов Identity не используются: `DataProtectorTokenProvider` не хранит состояния и не отменяет прежнюю ссылку без смены stamp, то есть без обрыва сессий, а DataProtection в проекте — только для cookie (Q4 `stack.html`). Токен — 32 случайных байта (256 бит, `RandomNumberGenerator`, Base64Url); в `users` хранятся только его SHA-256, срок, время выдачи и security stamp на момент выдачи. Одна действующая ссылка на запись, назначение — по состоянию записи: у приглашённой — приглашение, у зарегистрированной — сброс. Ссылка годна, только если хэш совпал (`FixedTimeEquals`), срок не истёк и stamp не менялся, поэтому её отменяют блокировка, смена роли, привязки или пароля и увольнение сотрудника; новая ссылка заменяет прежнюю; погашение и смена e-mail очищают её явно. Настройки `AccountLinks`: `InvitationLifetime` (7 дней), `PasswordResetLifetime` (1 час), `PasswordResetInterval` (5 минут — раньше этого времени после прежней ссылки анонимный запрос новую не выдаёт, без сообщения).
- `src/Competency.UserManagement/AccountMail.cs`: письма приглашения и сброса — русские тема и текст строковыми константами в коде; ссылка — `<App:PublicBaseUrl>/accept-invitation#token=…` или `/reset-password#token=…`, от настроенного адреса, не от `Host` запроса. Токен во фрагменте не уходит на сервер, в журналы прокси и в Referer (в `web/index.html` ещё и `<meta name="referrer" content="no-referrer">`); SPA читает его, убирает из адреса заменой записи истории и отправляет POST-запросом, поэтому открытие ссылки её не тратит. Письмо отправляется только после фиксации транзакции и снятия блокировок, никогда внутри транзакции или под блокировкой. События журнала — `audit.md`.
- `src/Competency.UserManagement/PasswordResetQueue.cs`: анонимный «Не помню пароль» обрабатывается вне запроса — ограниченная очередь в памяти (`Channel` на 1000 запросов, при переполнении новые отбрасываются) и `BackgroundService`, по одному запросу. Обработчик ищет запись по e-mail (для неизвестного адреса ничего не сохраняет), под блокировкой строки перечитывает её и выдаёт ссылку только записи, которой можно сбросить пароль: зарегистрирована, не заблокирована, привязанный сотрудник работает или привязки нет (`EmployeeBinding.MayResetPasswordAsync`, тот же признак у администратора), и не раньше `PasswordResetInterval`; фиксирует, затем отправляет письмо. **Принятый риск (решение пользователя):** очередь не переживает перезапуск процесса — пользователь запрашивает ссылку снова; outbox и повторы отправки не делаются.
- `src/Competency.UserManagement/SessionAuthentication.cs`: cookie `HttpOnly`, `SameSite=Strict`, `Secure` по настройке (`Authentication:Cookie`), скользящий срок; при каждом запросе `OnValidatePrincipal` проверяет, что учётная запись существует, не заблокирована, security stamp совпадает и привязанный сотрудник работает, поэтому блокировка, смена роли, привязки или пароля (в том числе по ссылке) и увольнение сотрудника обрывают действующую сессию сразу; без сессии — 401 (без redirect), недостаточно прав — 403.
- `src/Competency.UserManagement/AuthEndpoints.cs`, `ForgotPasswordRequest.cs`, `LinkPasswordRequest.cs`, `PasswordPolicyResponse.cs`: `/api/v1/auth`. Анонимны вход (rate limiter `login`), `POST /forgot-password`, `POST /accept-invitation`, `POST /reset-password` (rate limiter `password-reset`: `RateLimiting:PasswordReset`, 10 запросов за 60 с на адрес клиента, один счётчик на все три метода) и `GET /password-policy` (без лимита; `{ minLength }` из `Identity:Password:RequiredLength`, чтобы подсказка SPA не повторяла настройку). Выход, `me` и смена своего пароля доступны любому вошедшему и действуют только на учётную запись из сессии; смена своего пароля гасит и ссылку сброса. Любой отказ входа (неизвестная учётная запись, приглашённая без пароля, неверный пароль, lockout, блокировка, не работающий сотрудник) даёт один и тот же ответ 401, время ответа выравнивается (`SpendHashingTime` и для приглашённой); в журнал неуспешный вход пишется под id известной учётной записи или `unknown`, введённый текст не попадает. `forgot-password` сразу отвечает 202 на любой корректный адрес и ставит запрос в очередь: ни ответ, ни его время не выдают, есть ли такая запись. Задание пароля по ссылке: пароль проверяется политикой `Identity:Password` и хэшируется до блокировки, затем строка записи берётся `FOR UPDATE`, перечитывается, ссылка проверяется заново, и пароль, снятый lockout за перебор, очищенная ссылка, новый stamp (обрывает все сессии) и событие сохраняются вместе — ссылка тратится один раз. Сброс по ссылке не снимает блокировку администратором и не пускает уволенного сотрудника. Недействительная ссылка — 400 ProblemDetails с одним общим текстом для своего вида ссылки, без причины (не 401: SPA приняла бы его за конец сессии). Учёт неверных паролей — `VerifyPasswordAsync`: строка учётной записи читается `FOR UPDATE` и перечитывается, поэтому параллельные попытки считаются по очереди, а lockout (5 попыток, 15 минут) и событие `Auth.LockedOut` рождает только попытка, достигшая лимита; тот же учёт — у проверки текущего пароля при смене.
- `src/Competency.UserManagement/UserEndpoints.cs`, `EmployeeBinding.cs`: `/api/v1/users`, только `GlobalAdmin` (403 для любой иной роли независимо от запрошенной записи, 404 на неизвестную — только администратору), изменения с `If-Match`. Создание не принимает пароль: запись создаётся приглашённой, ссылка выдаётся в той же транзакции. Создание, правка, блокировка и разблокировка идут под блокировкой дерева (чтобы к увольняемому сотруднику не привязали и не разблокировали учётную запись); то, что может сократить набор администраторов, дополнительно блокирует его. `POST /{id}/resend-invitation` — только приглашённой незаблокированной записи, `POST /{id}/send-password-reset` — только записи, которой можно сбросить пароль (иначе 409); оба заменяют прежнюю ссылку, пароль не меняют. Письма по действиям администратора уходят синхронно сразу после фиксации, не дольше `Smtp:Timeout`; поле ответа `mailSent` (`UserResponse`; null, если запрос письма не отправлял) говорит, принял ли письмо SMTP-сервер: отказ изменение не откатывает, письмо можно отправить повторно. `UserResponse.isInvited` и фильтр `isInvited` у `ListUsers`. Привязка — к существующему работающему сотруднику, без второй учётной записи; разблокировка при не работающем привязанном сотруднике — 409. Смена роли или привязки и блокировка обрывают сессии.
- `src/Competency.UserManagement/ActiveAdministrators.cs`: **активный администратор** — `GlobalAdmin`, не заблокирован и зарегистрирован (`password_hash IS NOT NULL`); приглашённый не считается, иначе систему можно оставить без администратора, способного войти, а bootstrap бы не сработал. Признак одинаков в `LockAsync`, `IsActiveAdministrator`, `HasOtherAsync`, `AdminBootstrapper` и `EmployeeAccounts.IsLastActiveAdministratorAsync`. Правило «всегда есть хотя бы один активный глобальный администратор» (блокировка, понижение, смена роли и увольнение или удаление привязанного сотрудника — 409). **Порядок блокировок** (един для модулей, иначе возможны взаимные ожидания): 1) блокировка дерева `pg_advisory_xact_lock` (`org-structure`); 2) строки активных администраторов `SELECT … FOR UPDATE ORDER BY id`, только у операций, способных сократить их набор; 3) строка самой учётной записи при `SaveChanges`. Строку учётной записи отдельно и единственной (`AccountRowLock.BeginAccountLockAsync`) берут проверка пароля `VerifyPasswordAsync`, повторное приглашение, ссылка сброса от администратора и из очереди, принятие приглашения и сброс по ссылке; пока её держат, других блокировок не берут (сотрудник читается без блокировки дерева). Письмо не отправляется ни под одной блокировкой.
- `src/Competency.UserManagement/EmployeeAccounts.cs`: реализация порта `IEmployeeAccounts` из `org-structure` на общем `AppDbContext`: блокирует учётную запись уходящего сотрудника (и отвязывает при удалении), обрывает её сессии, отвечает, не последний ли она активный администратор; сохраняет вызывающий в своей транзакции.
- `src/Competency.UserManagement/AdminBootstrapper.cs`: первый глобальный администратор из `Bootstrap:AdminEmail` и `Bootstrap:AdminPassword` создаётся при старте с паролем, без письма, только если активного администратора нет (приглашённый не в счёт); существующая запись и её пароль не перезаписываются; без секрета при отсутствии администратора старт завершается понятной ошибкой; администратор из параметров развёртывания не привязан к сотруднику.
- `src/Competency.Platform/Migrations/` (общая линия миграций): таблица `users`; изменения контрактов данных этого модуля — миграции `UserManagement`, `EmailOnUserAccount`, `UnboundUserAccounts`, `AdminEmployeeBinding`, `UserRoleCheck`, `AccountLinks` (колонки ссылки и индекс; данные не переносятся — существующие записи остаются зарегистрированными со своими паролями).
- **Переход на контракт API 2.0.0** (`backward_compat: migration`; `info.version` — `ContractVersion` в `src/Competency.Api/Program.cs`, путь `/api/v1` прежний): удалён `POST /api/v1/users/{id}/reset-password` (`ResetPasswordRequest`), замена — `POST /api/v1/users/{id}/send-password-reset`; из `POST /api/v1/users` удалено поле `password` (лишнее поле старого клиента игнорируется, запись создаётся приглашённой). Остальное аддитивно: `isInvited`, `mailSent`, фильтр `isInvited`, анонимные методы `/api/v1/auth`. Записи с адресами `@local.invalid` писем не получат, пока адрес не заменён. Шаги оператора — `deploy/README.md`, «Поведение при старте».
- `docs/product/requirements/user-management.html`: требования; `docs/ux/user-management.html`: UX-спецификация.
