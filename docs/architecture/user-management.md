# Управление пользователями (`user-management`)

## Purpose

Локальные учётные записи с входом по e-mail и паролю (ASP.NET Core Identity без UI, cookie-сессия), набор ролей — глобальный администратор и HR, сочетаемые в любом составе; запись без ролей — пользователь — и необязательная привязка учётной записи к одному работающему сотруднику. Учётные записи заводит только администратор, приглашением: запись создаётся без пароля, пользователь задаёт его сам по одноразовой ссылке из письма. Пароли другим администратор не задаёт — он отправляет ссылку сброса, которую пользователь может запросить и сам («Не помню пароль»). Модуль ссылается на `Competency.Platform` и `org-structure` (читает сотрудника через `IEmployeeDirectory`, реализует порт `IEmployeeAccounts`), публикует порт `IUserDirectory`, через который учётные записи читает `career-framework`, в журнал пишет через `IAuditWriter` и `[Audited]` из Platform, письма отправляет через `MailSender` из Platform, находки рабочего стола отдаёт через `IDeskSource` из Platform, закрепления HR сотрудника читает через порт `IHrAssignments` из Platform (реализует `career-framework`).

## Key paths

- `src/Competency.UserManagement/`: корень модуля; типы `internal`, наружу выходят `AddUserManagementModule`, `MapUserManagementEndpoints`, `EnsureBootstrapAdminAsync` и порт ниже.
- `src/Competency.UserManagement/IUserDirectory.cs`, `UserDirectory.cs`, `UserStatus.cs`: порт чтения учётных записей для других модулей — `FindAsync`, `FindManyAsync` (по id учётной записи) и `FindByEmployeeIdsAsync` (по id привязанных сотрудников): id, e-mail, `employeeId`, заблокирована ли, зарегистрирована ли (`password_hash IS NOT NULL`), есть ли роль HR (`IsHr`), есть ли роль глобального администратора (`IsGlobalAdmin`), `Version` (для `If-Match` действий над учётной записью с экранов сценариев). `UserStatus.IsActive` (не заблокирована и зарегистрирована) — единственное определение учётной записи, которая может действовать в другом модуле. `UserStatus.CanBeHr` (`IsActive`, роль HR и привязка к сотруднику) — единственное определение записи, через которую привязанный сотрудник становится кандидатом в ответственные HR и действует по закреплению (требования career-framework AC-7, AC-9); отдельной проверки, что сотрудник работает, правило не требует: действующая привязанная запись бывает только у работающего (увольнение блокирует запись, разблокировка при неработающем сотруднике — 409, привязка — только к работающему). Его копию в SQL держит фильтр кандидатов `org-structure` (`org-structure.md`). `HasHrCandidateAsync` — есть ли хоть одна запись `CanBeHr`, тем же правилом в одном запросе. Реализация scoped, на том же `AppDbContext`, что и запрос, читает без блокировок. Читает его `career-framework`. Для `promotion`: `FindActiveAdministratorIdsAsync` — действующие глобальные администраторы, адресаты письма о подразделении без председателя комиссии, когда закреплённого HR нет; `EmailProblemAsync` — почему адрес нельзя дать новой учётной записи; `InviteEmployeeAsync` — учётная запись без ролей для работающего сотрудника без записи и письмо-приглашение (блокировку дерева берёт сама, вызывать вне транзакции) — так приглашаются оценивающие без учётной записи.
- `src/Competency.UserManagement/AppUser.cs`, `AppUserStore.cs`, `UserManagementEntityConfiguration.cs`, `UserRole.cs`: Identity без UI — `AddIdentityCore<AppUser>()`, `AddRoles<IdentityRole<Guid>>()`, `AddUserStore<AppUserStore>()` (наследник `UserStore<AppUser, IdentityRole<Guid>, AppDbContext, Guid>`) и `AddRoleStore<RoleStore<IdentityRole<Guid>, AppDbContext, Guid>>()`; `AddEntityFrameworkStores` не вызывается: `AppDbContext` не наследует `IdentityDbContext`, типы хранилищ задаются явно (`tech-reference/microsoft-aspnetcore-identity-entityframeworkcore-10.0.12.md`). Таблицы: `users`; `roles` (`IdentityRole<Guid>`: `id`, `name`, `normalized_name` с уникальным индексом, `concurrency_stamp`); `user_roles` (`IdentityUserRole<Guid>`: ключ `user_id, role_id`, внешние ключи на `users` и `roles` без каскада, индекс по `role_id`). Таблиц claims, логинов, токенов, claims ролей и passkeys нет. **Роли** — классические роли Identity, набор строк `user_roles` (решение пользователя 2026-10-21): имя роли = член `UserRole` = значение claim `role` = значение в API (`roles` — массив `UserRole`, пустой — пользователь, члена `User` нет); роли записи везде упорядочены по членам `UserRole` (ответ API, журнал, claims), потому что `GetRolesAsync` порядка не обещает. Строки `roles` создаёт миграция из `HasData` по всем членам `UserRole` с постоянными `id` и `concurrency_stamp`: штамп `IdentityRole` иначе случаен, и каждая `migrations add` давала бы `UpdateData`, а `has-pending-model-changes` не был бы чистым. Id ролей — константы модуля в одном месте; новая роль — член `UserRole`, его id, миграция и права в коде. `RoleManager` регистрирует `AddRoles`, приложение его не вызывает: ролей вне кода нет. Роли загруженной записи читает `UserManager.GetRolesAsync`; меняет их только функция смены ролей модуля — `UserManager.RemoveFromRolesAsync` и `AddToRolesAsync` с разностью наборов (повтор роли или снятие отсутствующей — ошибка Identity): каждый вызов проверяет запись и сохраняет её через `AppUserStore.UpdateAsync` в открытой транзакции вызывающего, поэтому `Version` растёт на число сохранений (ETag берётся из ответа); событие журнала о смене ролей (`audit.md`) функция добавляет до первого вызова. Навигация `AppUser.UserRoles` (без `AutoInclude`, схему не меняет) — только для LINQ: фильтр `ListUsers`, проекция `UserResponse`, активные администраторы, `UserDirectory`, источник стола. Цена: роли записи — отдельный запрос, их журнал пишется вручную, смена ролей сохраняет запись несколькими `SaveChanges` одной транзакции. Отклонено: одно значение роли с третьим членом `Hr` — администратор не мог бы быть HR, а у сотрудника не больше одной учётной записи; признаки `is_global_admin`, `is_hr` — каждая роль добавляла бы колонку; собственная таблица `user_roles (user_id, role text)` с CHECK — пользователь выбрал роли Identity; фабрика principal Identity (`IUserClaimsPrincipalFactory`) для сессии — она читает claims записи и claims ролей (`GetClaimsAsync`), а их таблиц нет; имена `AspNetRoles`, `AspNetUserRoles` — схема проекта в snake_case (`users`), сырой SQL модулей пишется без кавычек. E-mail уникален без учёта регистра и одновременно служит внутренним `UserName`; один сотрудник — не более одной учётной записи (уникальный частичный индекс по `employee_id`, внешний ключ без каскада); учётные записи не удаляются, только блокируются. **«Приглашён»** = `password_hash IS NULL` (`AppUser.IsInvited`, отдельной колонки нет): такая запись войти не может. Колонки ссылки — `link_token_hash` (уникальный частичный индекс), `link_expires_at`, `link_issued_at`, `link_security_stamp`. Allow-list журнала: `email`, `isBlocked`, `employeeId` — хэш, stamp'ы, счётчики входа и колонки ссылки в журнал не попадают; роли журналирует функция смены ролей.
- `src/Competency.UserManagement/AppUser.cs` (`IssueLink`, `HasValidLink`, `ClearLink`), `AccountLinkOptions.cs`: **ссылки из писем** (приглашение и сброс пароля). Провайдеры токенов Identity не используются: `DataProtectorTokenProvider` не хранит состояния и не отменяет прежнюю ссылку без смены stamp, то есть без обрыва сессий, а DataProtection в проекте — только для cookie (Q4 `stack.html`). Токен — 32 случайных байта (256 бит, `RandomNumberGenerator`, Base64Url); в `users` хранятся только его SHA-256, срок, время выдачи и security stamp на момент выдачи. Одна действующая ссылка на запись, назначение — по состоянию записи: у приглашённой — приглашение, у зарегистрированной — сброс. Ссылка годна, только если хэш совпал (`FixedTimeEquals`), срок не истёк и stamp не менялся, поэтому её отменяют блокировка, смена ролей, привязки или пароля и увольнение сотрудника; новая ссылка заменяет прежнюю; погашение и смена e-mail очищают её явно. Настройки `AccountLinks`: `InvitationLifetime` (7 дней), `PasswordResetLifetime` (1 час), `PasswordResetInterval` (5 минут — раньше этого времени после прежней ссылки анонимный запрос новую не выдаёт, без сообщения).
- `src/Competency.UserManagement/AccountMail.cs`: письма приглашения и сброса — русские тема и текст строковыми константами в коде; ссылка — `<App:PublicBaseUrl>/accept-invitation#token=…` или `/reset-password#token=…`, от настроенного адреса, не от `Host` запроса. Токен во фрагменте не уходит на сервер, в журналы прокси и в Referer (в `web/index.html` ещё и `<meta name="referrer" content="no-referrer">`); SPA читает его, убирает из адреса заменой записи истории и отправляет POST-запросом, поэтому открытие ссылки её не тратит. Письмо отправляется только после фиксации транзакции и снятия блокировок, никогда внутри транзакции или под блокировкой. События журнала — `audit.md`. Строка действия («Задать пароль:») стоит над адресом ссылки: HTML-версию письма с этой ссылкой строит `MailSender` (`stack.html`, «Почта»).
- `src/Competency.UserManagement/PasswordResetQueue.cs`: анонимный «Не помню пароль» обрабатывается вне запроса — ограниченная очередь в памяти (`Channel` на 1000 запросов, при переполнении новые отбрасываются) и `BackgroundService`, по одному запросу. Обработчик ищет запись по e-mail (для неизвестного адреса ничего не сохраняет), под блокировкой строки перечитывает её и выдаёт ссылку только записи, которой можно сбросить пароль: зарегистрирована, не заблокирована, привязанный сотрудник работает или привязки нет (`EmployeeBinding.MayResetPasswordAsync`, тот же признак у администратора), и не раньше `PasswordResetInterval`; фиксирует, затем отправляет письмо. **Принятый риск (решение пользователя):** очередь не переживает перезапуск процесса — пользователь запрашивает ссылку снова; outbox и повторы отправки не делаются.
- `src/Competency.UserManagement/SessionAuthentication.cs`: cookie `HttpOnly`, `SameSite=Strict`, `Secure` по настройке (`Authentication:Cookie`), скользящий срок. В сессии — claim `role` на каждую роль набора (`PlatformClaims.GlobalAdminRole`, `PlatformClaims.HrRole`; у записи без ролей claim нет), `ClaimsIdentity` с `roleType: role`; principal строит `CreatePrincipal(user, roles)` с ролями из `GetRolesAsync` при входе, фабрика principal Identity не вызывается, поэтому `IdentityOptions.ClaimsIdentity.RoleClaimType` не задаётся. Platform: `ICurrentActor.IsInRole(role)`, расширения `IsGlobalAdmin()`, `IsHr()` — ими заменены все сравнения `actor.Role == GlobalAdminRole`; `ICurrentActor.Role` остаётся только для журнала — роли через запятую (`GlobalAdmin,Hr`), у вошедшего без ролей — `User`. Политика `GlobalAdmin` (`RequireClaim(role, GlobalAdmin)`) выполняется, если любой claim `role` равен `GlobalAdmin` (`tech-reference/aspnetcore-10.0.12.md`). При каждом запросе `OnValidatePrincipal` проверяет, что учётная запись существует, не заблокирована, security stamp совпадает и привязанный сотрудник работает, поэтому блокировка, смена любой роли (права роли HR действуют с повторного входа), привязки или пароля (в том числе по ссылке) и увольнение сотрудника обрывают действующую сессию сразу; без сессии — 401 (без redirect), недостаточно прав — 403.
- `src/Competency.UserManagement/AuthEndpoints.cs`, `ForgotPasswordRequest.cs`, `LinkPasswordRequest.cs`, `PasswordPolicyResponse.cs`: `/api/v1/auth`. Анонимны вход (rate limiter `login`), `POST /forgot-password`, `POST /accept-invitation`, `POST /reset-password` (rate limiter `password-reset`: `RateLimiting:PasswordReset`, 10 запросов за 60 с на адрес клиента, один счётчик на все три метода) и `GET /password-policy` (без лимита; `{ minLength }` из `Identity:Password:RequiredLength`, чтобы подсказка SPA не повторяла настройку). Выход, `me` (`CurrentUserResponse.roles` — набор ролей) и смена своего пароля доступны любому вошедшему и действуют только на учётную запись из сессии; смена своего пароля гасит и ссылку сброса. Любой отказ входа (неизвестная учётная запись, приглашённая без пароля, неверный пароль, lockout, блокировка, не работающий сотрудник) даёт один и тот же ответ 401, время ответа выравнивается (`SpendHashingTime` и для приглашённой); в журнал неуспешный вход пишется под id известной учётной записи или `unknown`, введённый текст не попадает. `forgot-password` сразу отвечает 202 на любой корректный адрес и ставит запрос в очередь: ни ответ, ни его время не выдают, есть ли такая запись. Задание пароля по ссылке: пароль проверяется политикой `Identity:Password` и хэшируется до блокировки, затем строка записи берётся `FOR UPDATE`, перечитывается, ссылка проверяется заново, и пароль, снятый lockout за перебор, очищенная ссылка, новый stamp (обрывает все сессии) и событие сохраняются вместе — ссылка тратится один раз. Сброс по ссылке не снимает блокировку администратором и не пускает уволенного сотрудника. Недействительная ссылка — 400 ProblemDetails с одним общим текстом для своего вида ссылки, без причины (не 401: SPA приняла бы его за конец сессии). Учёт неверных паролей — `VerifyPasswordAsync`: строка учётной записи читается `FOR UPDATE` и перечитывается, поэтому параллельные попытки считаются по очереди, а lockout (5 попыток, 15 минут) и событие `Auth.LockedOut` рождает только попытка, достигшая лимита; тот же учёт — у проверки текущего пароля при смене.
- `src/Competency.UserManagement/UnicodePasswordValidator.cs`: проверка пароля Identity — наследник `PasswordValidator`, для которого буква любого алфавита, в том числе русская, засчитывается как заглавная, строчная и буквенно-цифровой символ, поэтому русская буква не считается специальным символом; длина и остальные параметры `Identity:Password` прежние.
- `src/Competency.UserManagement/UserEndpoints.cs`, `EmployeeBinding.cs`: `/api/v1/users`, только `GlobalAdmin` (403 для любой иной роли независимо от запрошенной записи, 404 на неизвестную — только администратору), изменения с `If-Match`. Создание не принимает пароль: запись создаётся приглашённой, ссылка выдаётся в той же транзакции. Создание, правка, блокировка и разблокировка идут под блокировкой дерева (чтобы к увольняемому сотруднику не привязали и не разблокировали учётную запись); то, что может сократить набор администраторов, дополнительно блокирует его. `POST /{id}/resend-invitation` — только приглашённой незаблокированной записи, `POST /{id}/send-password-reset` — только записи, которой можно сбросить пароль (иначе 409); оба заменяют прежнюю ссылку, пароль не меняют. Письма по действиям администратора уходят синхронно сразу после фиксации, не дольше `Smtp:Timeout`; поле ответа `mailSent` (`UserResponse`; null, если запрос письма не отправлял) говорит, принял ли письмо SMTP-сервер: отказ изменение не откатывает, письмо можно отправить повторно. `UserResponse.isInvited` и фильтр `isInvited` у `ListUsers`. Роли: `roles` в `CreateUserRequest`, `UpdateUserRequest` (обязательно, пустой массив — без ролей, повтор члена — тот же набор), `UserResponse` (в порядке членов `UserRole`); фильтр `role` у `ListUsers` — `UserRoleFilter`: `GlobalAdmin`, `Hr` — записи с этой ролью, в том числе вместе с другой, `User` — записи без ролей. Привязка — к существующему работающему сотруднику, без второй учётной записи; разблокировка при не работающем привязанном сотруднике — 409. Смена ролей или привязки и блокировка обрывают сессии.
  - Снятие роли HR (у записи она есть, в запросе нет): если сотрудник, к которому запись привязана после запроса, закреплён ответственным HR хотя бы за одним подразделением любого статуса (`IHrAssignments.UnitNamesAsync`), — 409 «Роль «HR» нельзя снять: сотрудник учётной записи закреплён ответственным HR подразделений «A», «B». Сначала закрепите за ними другого HR.» — до 5 названий по алфавиту, дальше «и ещё N» (требования AC-51). Блокировка записи проверку не отменяет. Запись без привязки снимает роль свободно; отвязка в том же запросе равна отвязке, затем снятию, а закрепления остаются за сотрудником и не действуют (AC-52). Проверка идёт под той же эксклюзивной блокировкой дерева, что закрепление HR, увольнение, удаление и блокировка, поэтому параллельное закрепление её не обходит (требования career-framework AC-158).
- `src/Competency.UserManagement/ActiveAdministrators.cs`: **активный администратор** — роль `GlobalAdmin` (строка `user_roles`), не заблокирован и зарегистрирован (`password_hash IS NOT NULL`); приглашённый не считается, иначе систему можно оставить без администратора, способного войти, а bootstrap бы не сработал. Признак одинаков в `LockAsync`, `IsActiveAdministrator`, `HasOtherAsync`, `AdminBootstrapper` и `EmployeeAccounts.IsLastActiveAdministratorAsync`. `LockAsync`: `SELECT u.id FROM users u WHERE NOT u.is_blocked AND u.password_hash IS NOT NULL AND EXISTS (SELECT 1 FROM user_roles ur JOIN roles r ON r.id = ur.role_id WHERE ur.user_id = u.id AND r.name = 'GlobalAdmin') ORDER BY u.id FOR UPDATE OF u` — блокируются только строки `users`; набор под блокировкой не меняется: смена ролей меняет и строку записи (stamp, `Version`), а каждая операция, сокращающая набор, сначала берёт эксклюзивную блокировку дерева. Правило «всегда есть хотя бы один активный глобальный администратор» (блокировка, снятие роли администратора, в том числе когда остаётся роль HR, и увольнение или удаление привязанного сотрудника — 409). Место этого модуля в едином порядке блокировок (`stack.html`, «Целостность на уровне данных»): строки активных администраторов `SELECT … FOR UPDATE ORDER BY id` берут только операции, способные сократить их набор, после блокировки дерева; строка самой учётной записи — при `SaveChanges`. Строку учётной записи отдельно и единственной (`AccountRowLock.BeginAccountLockAsync`) берут проверка пароля `VerifyPasswordAsync`, повторное приглашение, ссылка сброса от администратора и из очереди, принятие приглашения и сброс по ссылке; пока её держат, других блокировок не берут (сотрудник читается без блокировки дерева). Письмо не отправляется ни под одной блокировкой.
- `src/Competency.UserManagement/EmployeeAccounts.cs`: реализация порта `IEmployeeAccounts` из `org-structure` на общем `AppDbContext`: блокирует учётную запись уходящего сотрудника (и отвязывает при удалении), обрывает её сессии, отвечает, не последний ли она активный администратор; сохраняет вызывающий в своей транзакции.
- Источник стола (внутренний класс `IDeskSource`, регистрируется в `AddUserManagementModule`), только администратору: приглашение не принято — приглашённая незаблокированная учётная запись, чья ссылка истекла (в том числе отменена сменой stamp или очищена сменой e-mail) или скоро истечёт, со встроенным действием «Отправить приглашение повторно» (`POST /users/{id}/resend-invitation`, id и `version` учётной записи из пункта стола; итог — по `mailSent`); незаблокированная учётная запись без сотрудника — без роли администратора или с ролью HR, в том числе вместе с ролью администратора (запись только с ролью администратора не привязана по замыслу; требования desk AC-146), у записи с ролью HR — `Details.HasHrRole = true`, по нему SPA добавляет, что без привязки её нельзя закрепить ответственным HR; учётная запись руководителя действующего подразделения — нет, приглашена или заблокирована (руководителей источник берёт из `IEmployeeDirectory`). Определение «может действовать» — то же `UserStatus.IsActive`. Предпосылка стола `HrAccount` (`desk.md`, требования desk AC-218) — есть учётная запись с ролью HR, не заблокированная и зарегистрированная, привязка не нужна; источник отдаёт её только администратору (карточка «Назначить HR» — только ему) из того же запроса учётных записей: в его условие добавлены такие записи (их единицы–десятки), отдельной SQL-команды нет.
- `web/src/features/auth/returnTo.ts` (проверка цели, построение адреса входа с целью и чтение цели), `web/src/app/router.tsx` (установка обработчика 401), `web/src/api/client.ts` (его регистрация), `web/src/features/auth/LoginPage.tsx`: возврат на цель после входа — только в SPA, сервер не меняется. Обработчик 401 переводит на `/login?returnTo=<pathname+search>` текущего адреса, кроме страниц входа; после входа `LoginPage` переходит на цель, если она прошла проверку, иначе на `/desk`; подсказка о цели на экране входа — только когда цель есть. Проверка: `new URL(value, location.origin)` — тот же origin, путь начинается с одного «/» (не «//»), без «\» и управляющих символов; `/login`, `/forgot-password`, `/accept-invitation`, `/reset-password` целью быть не могут. Переход — по разобранным `pathname + search`, а не по исходной строке. Основание — [OWASP Unvalidated Redirects and Forwards Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html), «Validating URLs» (проверено 2026-10-13); запрет «//», «\» и управляющих символов — решение проекта. Цель видна в адресе страницы входа.
- `src/Competency.UserManagement/AdminBootstrapper.cs`: первый глобальный администратор из `Bootstrap:AdminEmail` и `Bootstrap:AdminPassword` создаётся при старте с паролем, без письма, только если активного администратора нет (приглашённый не в счёт); запись и её роль `GlobalAdmin` сохраняются в одной транзакции — иначе сбой между ними оставил бы запись без роли, а следующий старт упал бы на занятом e-mail; существующая запись и её пароль не перезаписываются; без секрета при отсутствии администратора старт завершается понятной ошибкой; администратор из параметров развёртывания не привязан к сотруднику.
- `src/Competency.Platform/Migrations/` (общая линия миграций — `stack.html`, «Контракт из кода»): таблицы `users`, `roles` (строки ролей — `HasData`) и `user_roles`, целиком из модели.
- `docs/product/requirements/user-management.html`: требования; `docs/ux/user-management.html`: UX-спецификация.
