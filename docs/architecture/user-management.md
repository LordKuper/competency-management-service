# Управление пользователями (`user-management`)

## Purpose

Локальные учётные записи с входом по e-mail и паролю (ASP.NET Core Identity без UI, cookie-сессия), две роли — глобальный администратор и пользователь — и необязательная привязка учётной записи любой роли к одному работающему сотруднику; управляет ими только администратор. Модуль ссылается на `Competency.Platform` и `org-structure` (читает сотрудника через `IEmployeeDirectory`, реализует порт `IEmployeeAccounts`), а в журнал пишет через `IAuditWriter` и `[Audited]` из Platform.

## Key paths

- `src/Competency.UserManagement/`: корень модуля; типы `internal`, наружу выходят `AddUserManagementModule`, `MapUserManagementEndpoints`, `EnsureBootstrapAdminAsync`.
- `src/Competency.UserManagement/AppUser.cs`, `AppUserStore.cs`, `UserManagementEntityConfiguration.cs`: `AddIdentityCore` с собственным хранилищем; Identity отображён одной таблицей `users` (без таблиц ролей, claims, логинов, токенов); роль — колонка `role` (`GlobalAdmin` / `User`, CHECK `ck_users_role`); e-mail уникален без учёта регистра и одновременно служит внутренним `UserName`; один сотрудник — не более одной учётной записи (уникальный частичный индекс по `employee_id`, внешний ключ без каскада); учётные записи не удаляются, только блокируются. Allow-list журнала: `email`, `role`, `isBlocked`, `employeeId` — хэш, stamp'ы, счётчики входа в журнал не попадают.
- `src/Competency.UserManagement/SessionAuthentication.cs`: cookie `HttpOnly`, `SameSite=Strict`, `Secure` по настройке (`Authentication:Cookie`), скользящий срок; при каждом запросе `OnValidatePrincipal` проверяет, что учётная запись существует, не заблокирована, security stamp совпадает и привязанный сотрудник работает, поэтому блокировка, смена роли, привязки или пароля и увольнение сотрудника обрывают действующую сессию сразу; без сессии — 401 (без redirect), недостаточно прав — 403.
- `src/Competency.UserManagement/AuthEndpoints.cs`: `/api/v1/auth`. Вход анонимен под rate limiter `login`; выход, `me` и смена своего пароля доступны любому вошедшему и действуют только на учётную запись из сессии. Любой отказ входа (неизвестная учётная запись, неверный пароль, lockout, блокировка, не работающий сотрудник) даёт один и тот же ответ 401, время ответа выравнивается; в журнал неуспешный вход пишется под id известной учётной записи или `unknown`, введённый текст не попадает. Учёт неверных паролей — `VerifyPasswordAsync`: строка учётной записи читается `FOR UPDATE` и перечитывается, поэтому параллельные попытки считаются по очереди, а lockout (5 попыток, 15 минут) и событие `Auth.LockedOut` рождает только попытка, достигшая лимита; тот же учёт — у проверки текущего пароля при смене.
- `src/Competency.UserManagement/UserEndpoints.cs`, `EmployeeBinding.cs`: `/api/v1/users`, только `GlobalAdmin` (403 для любой иной роли независимо от запрошенной записи, 404 на неизвестную — только администратору), изменения с `If-Match`. Создание, правка, блокировка и разблокировка идут под блокировкой дерева (чтобы к увольняемому сотруднику не привязали и не разблокировали учётную запись); то, что может сократить набор администраторов, дополнительно блокирует его. Привязка — к существующему работающему сотруднику, без второй учётной записи; разблокировка при не работающем привязанном сотруднике — 409. Сброс пароля, смена роли или привязки и блокировка обрывают сессии.
- `src/Competency.UserManagement/ActiveAdministrators.cs`: правило «всегда есть хотя бы один активный глобальный администратор» (блокировка, понижение, смена роли и увольнение или удаление привязанного сотрудника — 409). **Порядок блокировок** (един для модулей, иначе возможны взаимные ожидания): 1) блокировка дерева `pg_advisory_xact_lock` (`org-structure`); 2) строки активных администраторов `SELECT … FOR UPDATE ORDER BY id`, только у операций, способных сократить их набор; 3) строка самой учётной записи при `SaveChanges`. Строку учётной записи при проверке пароля `VerifyPasswordAsync` берёт отдельно и ничего другого не запрашивает, пока её держит.
- `src/Competency.UserManagement/EmployeeAccounts.cs`: реализация порта `IEmployeeAccounts` из `org-structure` на общем `AppDbContext`: блокирует учётную запись уходящего сотрудника (и отвязывает при удалении), обрывает её сессии, отвечает, не последний ли она активный администратор; сохраняет вызывающий в своей транзакции.
- `src/Competency.UserManagement/AdminBootstrapper.cs`: первый глобальный администратор из `Bootstrap:AdminEmail` и `Bootstrap:AdminPassword` создаётся при старте, только если активного администратора нет; существующая запись и её пароль не перезаписываются; без секрета при отсутствии администратора старт завершается понятной ошибкой; администратор из параметров развёртывания не привязан к сотруднику.
- `src/Competency.Platform/Migrations/` (общая линия миграций): таблица `users`; изменения контрактов данных этого модуля — миграции `UserManagement`, `EmailOnUserAccount`, `UnboundUserAccounts`, `AdminEmployeeBinding`, `UserRoleCheck`.
- `docs/product/requirements/user-management.html`: требования; `docs/ux/user-management.html`: UX-спецификация.
