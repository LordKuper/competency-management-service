Формат результата — только JSON ({ProjectName}.json); каталог — свойство OpenApiDocumentsDirectory. Генерация запускает entry point приложения с заглушкой сервера, поэтому выполняется весь код старта (DI, конфигурация): старт не должен обращаться к БД, строкам подключения и миграциям (обход — проверка entry assembly GetDocument.Insider); сборка не должна требовать доступа к PostgreSQL.
Microsoft.AspNetCore.Identity.EntityFrameworkCore10.0.12Локальная аутентификация: учётные записи ведёт сам сервис, корпоративный IdP не используется (Q2 решён). ASP.NET Core Identity — UserManager (SignInManager не используется), встроенный PasswordHasher (PBKDF2, HMAC-SHA512), блокировка при переборе пароля (lockout), cookie-сессия; хранилище на EF Core в PostgreSQL (MIT; зависимости по nuspec — только Microsoft.Extensions.Identity.Stores 10.0.12 и Microsoft.EntityFrameworkCore.Relational 10.0.12). Базовый пакет Microsoft.AspNetCore.Identity входит в shared framework ASP.NET Core. Razor-UI Identity не используется (экран входа — в SPA). Подключение — AddIdentityCore + cookie-аутентификация и собственные /api/v1/auth/*; MapIdentityApi не используется: саморегистрации нет, а «Не помню пароль», принятие приглашения и сброс по ссылке — собственные анонимные методы /api/v1/auth. Ссылки в письмах — собственный одноразовый токен (256 бит, в БД только SHA-256, привязка к security stamp); провайдеры токенов Identity (AddDefaultTokenProviders, DataProtectorTokenProvider) не подключаются. Схема — одна таблица users (без таблиц ролей, claims, логинов, токенов), роль — колонка; вход по e-mail, он же внутренний UserName; сессия проверяется на каждом запросе (блокировка, смена роли и пароля, увольнение сотрудника обрывают её сразу). Подробности — docs/architecture/user-management.md. Сторонних auth-библиотек и библиотек OIDC/SAML/Kerberos не добавляется (см. «Рассмотрено / не принято»).

Рантайм / инфраструктура

Топология: платформа — Kubernetes (решение пользователя, Q9); два workload'а — app (ASP.NET Core 10, раздаёт статику React SPA; один экземпляр на старте) и db (официальный образ PostgreSQL без доработок; stateful-нагрузка с одной репликой и PersistentVolumeClaim). Тип ресурса для db (StatefulSet или Deployment), Service и Ingress — в design. Состояние и перезапуск обеспечивает Kubernetes: проверки готовности и живости — пробы (readiness/liveness/startup) вместо Docker healthcheck; конфигурация и секреты — ConfigMap и Secret; перезапуск при сбое — политика контроллера. Порядок запуска app/db Kubernetes не гарантирует — app ждёт готовности БД (повторы подключения/проба), детали — в design. Строка подключения app → db настраивается (внешняя БД — позже, без пересборки). Процесс-супервизор внутри контейнера не нужен (см. «Рассмотрено / не принято»).

Доставка и патчи (процесс, не технология). Образы собираются вне контура на машине с интернетом и переносятся в контур готовыми; манифесты Kubernetes доставляются вместе с образами (формат — plain YAML, Kustomize или Helm — выбирается в design и в стек не входит). Образы попадают на узлы кластера двумя возможными путями: через внутренний container registry (push → pull с узлов) либо импортом tar-архивов на узлы (docker save/podman save → перенос → импорт средствами container runtime узла; для containerd — ctr -n k8s.io images import); выбор зависит от наличия registry в контуре (открытый вопрос Q11; подробности — в «Ограничениях»). Регламент обновления: пересборка → сканирование (уязвимости + SBOM) → перенос → развёртывание (применение манифестов с новыми digest). Он привязан к циклу патчей: .NET — ежемесячно, PostgreSQL — минорные релизы не реже раза в квартал; каждый цикл даёт новые digest образов, которые фиксируются в манифестах. Версии меняются только через спринт.

У образов PG 18 PGDATA=/var/lib/postgresql/18/docker, объявленный VOLUME — /var/lib/postgresql (изменено относительно ≤17): PersistentVolumeClaim монтируется только в /var/lib/postgresql (данные кластера — в подкаталоге PGDATA, а не в корне тома); PGDATA не переопределять. При монтировании тома в любой другой путь (в том числе в прежний /var/lib/postgresql/data или в /data) PGDATA остаётся /var/lib/postgresql/18/docker, и данные кластера окажутся вне PVC — в записываемом слое контейнера, то есть пропадут при пересоздании pod'а. Владелец тома и securityContext/fsGroup — в design. Образ задаёт STOPSIGNAL SIGINT, локаль только en_US.utf8 — проверки в design (см. «Ограничения и открытые вопросы»).
Node.js (только build-стадия)24.21.0build Сборка SPA (образ node:24.21.0-trixie-slim); в образе app Node нет. LTS-линия 24: поддержка до 2028-04-30 (Maintenance с 2026-10-20); Node 26 станет LTS 2026-10-28 — возможный переход позже.
.NET SDK (только build-стадия)10.0.401build Сборка и publish backend (образ mcr.microsoft.com/dotnet/sdk:10.0.401).
Постоянные тома (PersistentVolumeClaim)—storage PVC у stateful-нагрузок: данные PostgreSQL у db (монтаж только в /var/lib/postgresql); вложения на файловой системе за IBlobStore (абстракция — на Complication Approval в design) и резервные копии — отдельные PVC. StorageClass, режим доступа (RWO/RWX) и ёмкость определяет кластер организации (Q5). Шифрование данных в покое — на уровне инфраструктуры (шифрование диска/тома/СХД кластера, Q4 решён); приложение данные в БД не шифрует. HA не задана. Раскладка — в design (Q5).
Kubernetes (платформа запуска, внешняя)определяет организацияплатформа Запуск app и db как workload'ов; Secrets/ConfigMaps, пробы, перезапуск, PVC (решение пользователя, Q9). Версия кластера, container runtime, StorageClass и Ingress в контуре не заданы (доставка образов — Q11; TLS — Q8); манифесты поставляются вместе с образами.
Корпоративный SMTP relay (внешний)определяет организациявнешняя зависимость Доставка писем-приглашений и ссылок сброса пароля (MailKit). Параметры — Smtp:*: адрес, порт, режим TLS и отправитель — ConfigMap, логин и пароль — Secret; фактические параметры relay и доверие его сертификату — Q8. Доступность relay при старте не проверяется: отказ виден при отправке (администратору — в ответе, анонимный запрос — только в журнале и логе).

Ограничения и открытые вопросы

  • Нет интернета, CDN и SaaS внутри контура: запущенный сервис ничего не скачивает и не обращается во внешние сети; шрифты, иконки, образы и документация доставляются в контур готовыми. Сборка выполняется вне контура (см. следующий пункт). Источник ограничения — решение пользователя.
  • Только OSS и нулевая стоимость. Допустимые лицензии: MIT, Apache-2.0, BSD, ISC, PostgreSQL, MS-PL. Запрещены AGPL/GPL/LGPL, коммерческие и source-available лицензии, а также лицензии с регистрацией ключа (см. «Рассмотрено / не принято»). Принятые пользователем исключения (спринт 001, 2026-10-06): lightningcss 1.33.0 (MPL-2.0, слабый file-level копилефт) — зависимость сборки Vite 8.3.2, в образ и бандл не попадает; Microsoft.VisualStudio.JavaScript.Sdk 1.0.5984942 и проектные типы Visual Studio (.esproj, .dcproj) — только локальная разработка, в образ, CLI-сборку и тесты не входят. Новые исключения требуют отдельного решения пользователя.
  • Кадровая и оценочная информация (PII/HR): минимум зависимостей (supply chain); значения параметров SQL и персональные данные не попадают в логи; секреты (учётные данные SMTP, строка подключения, ключи DataProtection) — только из Kubernetes Secrets (переменные окружения или смонтированные файлы), несекретная конфигурация — из ConfigMap; не в образе и не в репозитории (в разработке личные учётные данные SMTP — только .NET User Secrets вне репозитория). Пароли пользователей хранятся только в виде хэшей (PasswordHasher), токены ссылок из писем — только как SHA-256; пароли, токены, ссылки, тексты писем и учётные данные SMTP в логи не попадают. Шифрование данных в покое обеспечивается на уровне инфраструктуры (шифрование диска/тома/СХД кластера); приложение чувствительные данные в БД не шифрует; DataProtection используется только для ключей cookie-сессии и antiforgery; сертифицированная криптография (ГОСТ) не заявлена (Q4 решён).
  • Аутентификация — локальная: корпоративный IdP не используется (решение пользователя, окончательное; Q2). Учётные записи и пароли ведёт сам сервис (ASP.NET Core Identity, хранилище — PostgreSQL); OIDC/SAML/Kerberos не подключаются; политика паролей, lockout, сессия и CSRF решены в спринте 001, приглашение и сброс пароля по ссылке из письма — в спринте 002 (см. открытые вопросы).
  • Платформа запуска — Kubernetes (решение пользователя, окончательное; Q9). Топология: два workload'а (app + db); db — stateful-нагрузка с PersistentVolumeClaim (данные PostgreSQL), вложения и резервные копии — отдельные PVC; конфигурация — ConfigMap/Secret; перезапуск и пробы состояния обеспечивает Kubernetes. Решение о двух контейнерах заменило исходное пожелание «один контейнер на весь сервис». Масштабирование и HA не заданы (см. открытые вопросы).
  • Платформа: .NET 10 LTS (до 2028-11-14); версии закреплены точно, обновления патчей — через спринт.
  • Frontend: Node используется только при сборке (multi-stage); SPA — статические файлы Kestrel. TypeScript закреплён на 6.0.x до появления программного API у 7.x (по анонсу — в 7.1; сроки не гарантированы); установка — только точной версией (npm i -D -E typescript@6.0.2), так как dist-tag latest указывает на 7.x. Контракт API — JSON-документ OpenAPI, строящийся при сборке backend (YAML при сборке .NET 10 не поддерживается); типы SPA генерируются из него.
  • Сборка вне контура, в контур доставляются готовые образы (решение пользователя, окончательное). Образы собираются на машине с интернетом вне изолированной сети; в контур переносятся только готовые артефакты:
    • доставка на узлы Kubernetes — через внутренний container registry, если он есть, либо импортом tar-архивов (docker save/podman save → перенос → импорт на узлах; для containerd — ctr -n k8s.io images import); наличие registry — открытый вопрос Q11; манифесты Kubernetes доставляются вместе с образами;
    • целевая архитектура образов — linux/amd64 (подтверждено пользователем, Q10); multi-arch сборка не требуется;
    • образы (app, db) и базовые образы закрепляются по digest (@sha256:…), а не по тегу;
    • до переноса — сканирование уязвимостей и SBOM для каждого образа (по желанию — подпись образов); результаты прикладываются к поставке;
    • в рантайме ничего не скачивается: без CDN — шрифты и иконки antd, кириллические шрифты для PDF внутри образа app; интерактивный UI документации API (Scalar) — только если бандлится офлайн, иначе UI не предоставляется (остаётся сам JSON-документ OpenAPI);
    • регламент обновления (пересборка → сканирование → перенос → развёртывание, привязка к патчам .NET и PostgreSQL) — в разделе «Рантайм / инфраструктура».
  • Гигиена цепочки поставок на сборочном хосте (у него есть интернет): package-lock.json и NuGet lock-файлы в репозитории; npm — только npm ci с ignore-scripts=true; версии NuGet-пакетов закреплены точно, restore — по lock-файлам; lock-файл npm должен содержать нативные optional-бинарники (Vite/Rolldown, lightningcss, Biome) для платформы разработки и для linux-x64 сборки; framework-dependent publish: runtime pack не нужен. Внутренние зеркала npm, NuGet и apt в контуре не нужны (понадобятся, только если сборку когда-либо перенесут в контур).
  • Лицензионная гигиена: прямых ссылок на SixLabors.* не добавлять (Split License: коммерческая лицензия при прямой зависимости у коммерческих организаций с выручкой от $1 млн); транзитивный SixLabors.Fonts от ClosedXML остаётся в диапазоне 1.x (Apache-2.0).
  • Кириллические шрифты для PDF/XLSX/UI поставляются внутри образа app (лицензии OFL/Apache; выбор — в design); никаких CDN-шрифтов и CDN-иконок.

Открытые вопросы (не решения — закрываются на design или у пользователя)

  • Масштабирование и HA не заданы. Требований к масштабированию, отказоустойчивости и целевой нагрузке нет. Старт — один экземпляр app + отдельная нагрузка db. Нужны ли масштабирование и HA и при какой нагрузке — определяется на design, если потребность появится; обязательного ADR не требуется.
  • Q2. Аутентификация — РЕШЕНО. Решение пользователя: без корпоративного IdP; локальные учётные записи (ASP.NET Core Identity, cookie-сессия). OIDC, SAML и Kerberos не используются; отдельного аварийного входа (break-glass) не требуется. Сопутствующие вопросы политики аутентификации — ниже, в пункте для design.
  • Q4. ПДн и криптография — РЕШЕНО (для стека). Решение пользователя: шифрование данных в покое — на уровне инфраструктуры (шифрование диска/тома/СХД кластера); приложение чувствительные данные в БД не шифрует (шифрования полей нет); DataProtection остаётся только для ключей cookie-сессии и antiforgery; сертифицированная криптография/ГОСТ не заявлена. Значения параметров SQL и персональные данные не попадают в логи (см. «Ограничения»). Разделение технического администрирования и HR-доступа и ограничение доступа к зарплатным данным на уровне ролей приложения — вопросы design, не стека (см. ниже).
  • Q5. RPO/RTO и резервное копирование — ОТКРЫТ. Решение пользователя: определим на design. Способ (дамп / снимки тома / архив WAL), расписание, хранение копий вне контейнеров, раскладка PVC. Спринт 001 копирование не вводил; журнал audit_events лежит в той же БД и копируется вместе с ней.
  • Q6. Место сборки и зеркала — РЕШЕНО. Решение пользователя: сборка вне контура на машине с интернетом, в контур доставляются готовые образы. Зеркала npm, NuGet и apt внутри контура не нужны (понадобятся, только если сборку когда-либо перенесут в контур). Наличие внутреннего registry (альтернатива tar-доставке) уточняется в Q11.
  • Q7. Антивирусная проверка вложений — РЕШЕНО. Решение пользователя: в MVP не нужна. Ограничения типов и размера загружаемых файлов — на design; вернуться, если появится требование (см. «Рассмотрено / не принято»).
  • Q8. SMTP и TLS — частично решено в спринте 002. Решено: параметры SMTP задаются конфигурацией — Smtp:Host, Smtp:Port, Smtp:SecureSocketOptions (по умолчанию StartTls; None — только для перехватчика почты), Smtp:UserName и Smtp:Password (из Secret, оба или ни одного), Smtp:From, Smtp:Timeout (по умолчанию 15 с, не больше 49.17:02:47.294 — предела CancellationTokenSource.CancelAfter), Smtp:CheckCertificateRevocation (по умолчанию true); неверное значение останавливает старт с названием ключа. Сертификат relay проверяется всегда; доверие внутреннему CA — шаг развёртывания (SSL_CERT_FILE), проверку отзыва отключает только оператор явным решением, когда CRL/OCSP недоступны из пода (deploy/README.md). Открыто: фактические параметры корпоративного relay (адрес, порт, режим TLS, нужна ли аутентификация, каким CA выпущен сертификат) и где терминируется TLS — Kestrel, Ingress-контроллер кластера (есть ли он) или reverse-proxy. От места TLS зависят флаг Secure cookie (Authentication:Cookie:SecurePolicy сейчас SameAsRequest; когда TLS заканчивается перед приложением — Always) и заголовки X-Forwarded-*, которые приложение не разбирает: за прокси лимиты входа и ссылок из писем (RateLimiting:Login, RateLimiting:PasswordReset) считаются по адресу прокси, то есть общие для всех клиентов, а проверка Origin не сравнивает схему. Адрес ссылок в письмах (App:PublicBaseUrl) задаётся явно и от заголовков запроса не зависит. Ingress и TLS манифесты не задают.
  • Q9. Платформа запуска — РЕШЕНО. Решение пользователя: Kubernetes. app и db — Kubernetes-нагрузки (db — stateful с PersistentVolumeClaim); пробы состояния вместо Docker healthcheck; конфигурация — Secrets/ConfigMaps; перезапуск обеспечивает Kubernetes; доставка — манифесты Kubernetes вместе с образами. Docker Compose и Podman не используются.
  • Q10. Целевая архитектура образов — РЕШЕНО. Решение пользователя: linux/amd64; multi-arch сборка не требуется.
  • Q11. Внутренний container registry. Есть ли в контуре внутренний container registry; если нет — образы доставляются импортом tar-архивов на узлы кластера (на каждый узел, где может запускаться pod, либо с привязкой pod к узлам; imagePullPolicy не должен требовать pull). Влияет на порядок обновлений и закрепление по digest: при tar-доставке соответствие digest после save/load проверяется spike в design. Инструмент манифестов (plain YAML / Kustomize / Helm) выбирается в design и в список стека не добавляется.
  • Локальная аутентификация — РЕШЕНО в спринтах 001 и 002. Пароль: минимальная длина 10 (Identity:Password; SPA узнаёт её из анонимного GET /api/v1/auth/password-policy), прочие правила — по умолчанию Identity, срока действия и 2FA нет. Первый администратор создаётся при старте с паролем из Bootstrap__AdminEmail и Bootstrap__AdminPassword (Kubernetes Secret; локально — launchSettings.json), только если активного зарегистрированного администратора нет; существующий не перезаписывается; развёртывание от почты не зависит. Пользователей приглашает администратор (импорта и саморегистрации нет): учётная запись создаётся без пароля, пользователь задаёт его по одноразовой ссылке из письма (срок 7 дней, AccountLinks:InvitationLifetime). Пароль другим администратор не задаёт: он отправляет ссылку сброса, которую пользователь может запросить и сам на экране входа («Не помню пароль»; срок ссылки 1 час, AccountLinks:PasswordResetLifetime). Перебор: 5 неверных паролей — блокировка на 15 минут (Identity:Lockout), плюс ограничение частоты по адресу — вход 10 запросов в минуту (RateLimiting:Login), «Не помню пароль», принятие приглашения и сброс по ссылке — 10 в минуту одним счётчиком (RateLimiting:PasswordReset). Cookie-сессия: HttpOnly, SameSite=Strict, Secure по настройке (зависит от Q8), скользящий срок 8 часов; от CSRF защищает проверка Origin/Sec-Fetch-Site (см. «Архитектурные принципы»), antiforgery-токены не используются. Ключи DataProtection (только для cookie) лежат в каталоге отдельного PVC app (DataProtection:KeysPath, strategy: Recreate), поэтому сессии переживают перезапуск. Подробности — docs/architecture/user-management.md.
  • Для design — доступ к ПДн и вложениям (не стек; Q4, Q7 решены). Разделение технического администрирования и HR-доступа: в спринте 001 глобальный администратор совмещает оба (решение пользователя — две роли; роли §8 и scope вне спринта), права изолированы в политиках Authenticated и GlobalAdmin для будущего расширения. Ограничение доступа к зарплатным данным на уровне ролей приложения; ограничения типов и размера загружаемых файлов (антивирусная проверка вложений в MVP не нужна).
  • Для design (Complication Approval). Абстракция IBlobStore для вложений на томе; раскладка PVC (данные PG — монтаж только в /var/lib/postgresql у db при объявленном VOLUME образа PG 18; иначе данные окажутся вне PVC; вложения и резервные копии — отдельные PVC), StorageClass и securityContext/fsGroup томов; Scalar.AspNetCore — только если UI полностью бандлится офлайн (spike), иначе UI не предоставляется.
  • Учётная запись БД приложения — ОТКРЫТ (backlog). app подключается как POSTGRES_USER — суперпользователь кластера — и владеет схемой (MigrateAsync при старте, решение пользователя). Триггеры журнала ENABLE ALWAYS закрывают обход через session_replication_role = replica, но DDL (DROP/DISABLE TRIGGER, DROP TABLE) остаётся доступным. Отдельная роль БД (миграции под владельцем схемы, рантайм под ролью без DDL и без прав суперпользователя) — в backlog, в спринт 001 не вошла.
  • Технические проверки: итоги спринта 001 (новых Q не заводится).
    • Закрыто. Порядок сборки и кодогенерация: web/src/api/schema.d.ts генерируется из openapi/openapi.json и коммитится, актуальность проверяет openapi-typescript --check, стадия Node собирает SPA без backend; генерация запускает entry point приложения, поэтому старт не обращается к БД (guard по entry assembly GetDocument.Insider). openapi-typescript и TypeScript 6: точечный overrides. pg_trgm есть в неизменённом образе (расширение trusted, создаёт миграция). Русская collation не нужна: сортировка кириллицы под en_US.utf8 корректна, FTS russian задаётся явно. Остановка db в Docker — STOPSIGNAL SIGINT, fast shutdown без crash recovery (postgres-image-18.6-trixie.md).
    • Остановка db в Kubernetes. Kubernetes по умолчанию шлёт SIGTERM (для PostgreSQL — smart shutdown, ждёт отключения клиентов); учитывается ли образный STOPSIGNAL, зависит от container runtime кластера. Проверить фактическое поведение остановки, fsGroup и startupProbe на кластере (в спринте 001 кластера не было) и подобрать terminationGracePeriodSeconds (иначе — SIGKILL и crash recovery).
    • CSP для antd. Выбор политики Content-Security-Policy: nonce (ConfigProvider csp; для статического index.html от Kestrel nonce на запрос недоступен без шаблонизации ответа), style-src 'unsafe-inline' либо zero-runtime режим antd (zeroRuntime + antd/dist/antd.css).
    • Минимальные браузеры. Vite 8 по умолчанию собирает под Chrome/Edge 111+, Firefox 114+, Safari 16.4+, antd 6 — только современные браузеры. Подтвердить, какие браузеры стоят в контуре; при расхождении — менять build.target (открытый пункт).

Архитектурные принципы

  • Модульный монолит — достаточен на старте; один процесс API, фоновые задачи — BackgroundService в нём же (первая — очередь анонимных запросов сброса пароля в памяти: при перезапуске процесса запросы теряются, решение пользователя); доменные границы задаёт реестр подсистем (docs/architecture/subsystems.md), а не сетевые границы. Правила закреплены проектными ссылками и internal-типами: Competency.Platform не ссылается на модули; Audit, OrgStructure и UserManagement ссылаются только на Platform, кроме UserManagement → OrgStructure; хост Competency.Api собирает всех; наружу модуль выставляет только Add…Module, Map…Endpoints и опубликованные порты (IEmployeeDirectory; IEmployeeAccounts объявлен в OrgStructure и реализован в UserManagement, чтобы OrgStructure не ссылался на него). Один AppDbContext и одна линия миграций; конфигурации сущностей поставляют модули.
  • Платформенное ядро (Competency.Platform и хост Competency.Api; не подсистема, в реестр не входит) — сквозные механизмы для всех модулей. Контракт API: изменяющие запросы требуют If-Match (заголовка нет — 428, слабый ETag — 400, версия не совпала — 412), ETag = Version сущности; все ошибки — ProblemDetails, нарушения уникальности и внешних ключей — 409. Доступ: все эндпойнты требуют аутентификации (fallback-политика), анонимны только пробы, вход, политика паролей (GET /api/v1/auth/password-policy), «Не помню пароль» и задание пароля по ссылке из письма (принятие приглашения, сброс), все кроме проб и политики паролей — под лимитом частоты по адресу; политики Authenticated и GlobalAdmin; без сессии 401, недостаточно прав 403, проверки только на backend; от CSRF защищают SameSite=Strict и проверка Origin/Sec-Fetch-Site на изменяющих методах. Наблюдаемость: JSON-логи в stdout без ПДн и значений SQL-параметров (обработчик исключений пишет тип и код, не сообщение), сквозной request_id (входящий X-Request-Id или новый) в логах и журнале. Запуск: до миграций приложение проверяет настройки почты (Smtp:*) и публичный адрес (App:PublicBaseUrl — абсолютный http(s) URL) и при ошибке не стартует (кроме build-time генерации OpenAPI); схему применяет приложение при старте, пробы /healthz/live и /healthz/ready (готовность проверяет БД) без авторизации и деталей. Почта: MailSender отправляет письмо одним соединением, отказ возвращает признаком и логирует только тип исключения; вызывать после фиксации транзакции, не под блокировкой; ссылки в письмах строятся от App:PublicBaseUrl, не от Host запроса. Общие типы API: пределы страниц и поиска (ListRequest), страница списка (PageResponse<T>) и отказы 409/400 (Rejection) живут в Platform, модули их не копируют. Идентификаторы сущностей — Guid v4, не последовательные.
  • Встроенное вместо сторонних библиотек — локальная аутентификация (ASP.NET Core Identity + cookie), валидация, OpenAPI, health checks (проверка БД — собственный IHealthCheck, без отдельного пакета), JSON-логи, фоновые задачи берутся из ASP.NET Core 10; без Mediator/AutoMapper. Исключение из «встроенного» — dev-пакеты сборки: Microsoft.Extensions.ApiDescription.Server (генерация OpenAPI при сборке) и Microsoft.EntityFrameworkCore.Design (миграции). Меньше supply-chain и лицензионных рисков в изолированном PII/HR-контуре.
  • Сервер — единственный источник истины — права, организационный scope и валидация проверяются на backend; правила antd Form служат только удобству пользователя.
  • Контракт из кода — JSON-документ OpenAPI генерируется при сборке backend из Minimal API (Microsoft.Extensions.ApiDescription.Server), TS-типы генерируются из него (openapi-typescript); DTO на frontend руками не пишутся.
  • Целостность на уровне данных — аудит append-only: SaveChangesInterceptor пишет журнал в той же транзакции, неизменяемость держат триггеры БД ENABLE ALWAYS (остаточный риск DDL — docs/architecture/audit.md); оптимистичная блокировка явным int Version; инварианты, которые должны переживать гонки (дерево без циклов, последний активный администратор, увольнение сотрудника с каскадом), держатся блокировками в БД, всегда в одном порядке — блокировка дерева, затем строки администраторов (docs/architecture/user-management.md); физически удаляется только сотрудник; очереди и outbox в той же транзакционной БД (SKIP LOCKED) — когда понадобятся.
  • Выносимые границы — предпочтение дизайна, не требование: настраиваемая строка подключения, IBlobStore и воркер на outbox оставляют возможность заменить workload db внешней БД (смена строки подключения) или вынести хранилище и фоновые задачи позже, без переписывания домена. Один процесс — один контейнер: независимые перезапуски, без супервизора внутри контейнера.
  • Сборка вне контура, доставка готовых образов — зависимости тянутся только на сборочном хосте под контролем цепочки поставок (lock-файлы, ignore-scripts, точные версии, сканирование и SBOM до переноса); в контур поставляются неизменяемые артефакты, закреплённые по digest; запуск не требует интернета и ничего не скачивает.
