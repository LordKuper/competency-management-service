ADR-1: Подсистема «Рабочий стол» (desk); модули отдают находки через контракт Platform

Context

Стол (AC-2, AC-3, AC-30) собирает находки трёх модулей. Данные career-framework дают виды AC-4, AC-5, 6.1, 6.3/6.4, AC-26, AC-27, AC-29; данные org-structure — 6.2, 28.1–28.4, 28.7; данные user-management — 6.5, 28.5 и состояние учётной записи руководителя из 28.6. Правило «один объект — один пункт» и поглощение работают поперёк модулей (таблица 1 PRD): 6.2 ⊃ 5.3; 28.7 ⊃ 6.2, 6.3, 5.3, 27.3; 28.1 ⊃ 29; 6.5 по учётной записи поглощает причину «приглашена» из 28.6 в пункте подразделения; действие поглощает справочное по тому же объекту. Счётчик равен числу пунктов-действий после слияния, поэтому по модулям отдельно его не посчитать.

Ограничения (stack.html, «Архитектурные принципы»): Platform не ссылается на модули; OrgStructure → Platform; UserManagement → OrgStructure; CareerFramework → OrgStructure, UserManagement; обратных ссылок нет. Наружу модуль выставляет только Add…Module, Map…Endpoints и опубликованные порты; у career-framework опубликованных портов нет. Образец «контракт в Platform, реализация в модуле» уже есть: IAuditWriter. Варианты размещения перечислены в audit.md («Subsystems map», (а)–(г)); новая подсистема — отдельный hard gate (sprint.md, допущение 3), принят пользователем 2026-10-13.

Decision

Каждый модуль вычисляет находки своих видов по своим данным и отдаёт их через контракт в Platform (IDeskSource). Слияние, поглощение, порядок причин, группы и счётчик живут в новой подсистеме desk (модуль Competency.Desk, зависит только от Platform). Она владеет правилами AC-2, AC-3, AC-30 и API стола (ADR-2).

  • Контракт в Platform. Метод IDeskSource.FindAsync(CancellationToken) возвращает IReadOnlyList<DeskFinding> вошедшего пользователя (ICurrentActor). DeskFinding несёт:
    • вид (DeskKind): по члену на вид PRD, а варианты одного вида с разным поглощением — отдельными членами («трек без уровней» и «трек с одним уровнем»; «учётная запись руководителя: нет / приглашена / заблокирована»);
    • объект: тип, id, название, контекст;
    • необязательный «предмет» — объект другого типа, к которому относится находка. Например, учётная запись руководителя в 28.6 или должность пользователя в 29. Он нужен для поглощения поперёк объектов;
    • признак «действие» или «справочно»;
    • момент события — только у событийных видов (AC-2.5);
    • типизированные параметры причины;
    • идентификаторы перехода и встроенного действия: учётную запись и её version для «Отправить приглашение повторно».
  • Источники в модулях. Каждый — внутренний класс модуля, который модуль регистрирует в своём Add…Module.
    • org-structure: 6.2, 28.1, 28.2, 28.3, 28.4, 28.7 — только администратору.
    • user-management: 6.5, 28.5, 28.6 — только администратору. Руководителей подразделений источник берёт из IEmployeeDirectory.
    • career-framework: 4.1–4.4, 5.1–5.3, 6.1, 6.3 (с причиной 6.4), 26.1–26.9, 27.1, 27.3–27.8, 29. Здесь же подавления, которым нужны данные модуля: версия в работе подавляет 4.4, 5.3, 26.5–26.7, даже если о самой версии пользователю ничего не показано (AC-30.9); черновой трек на утверждении получает пометку «утверждать рано» вместо 26.2–26.4 (AC-27.2).
    Источник сам ограничивает область видимости (AC-16.6) и берёт те же функции прав, которыми модуль проверяет действие: ProcessRoles, MatrixRoute, CatalogViewer, правило /drafts. Второй копии правил нет.
  • Слияние в desk. Модуль собирает все IDeskSource и выполняет шаги строго в этом порядке:
    1. убирает повтор одной находки, пришедшей по нескольким ролям (AC-30.5);
    2. применяет явные пары поглощения таблицы 1, в том числе через «предмет»;
    3. применяет общее правило «действие поглощает справочное по тому же объекту» (AC-30.4). Если поменять шаги 2 и 3 местами, не сработает исключение 28.7 ⊃ 6.2;
    4. упорядочивает причины по таблице 2;
    5. определяет группу пункта по первой видимой причине (U-3);
    6. считает пункты-действия.
    Таблицы 1 и 2 занимают одно место в коде desk. Таблиц БД и миграций у desk нет.
  • Регистрация. Хост регистрирует модуль desk вместе с остальными.

ADR-2: API стола и счётчика, доступ и производительность

Context

AC-2 и AC-3 требуют, чтобы счётчик обновлялся после каждого действия, при переходе и при возврате фокуса, без таймера и push. Остальные входы:

  • AC-16 (доступ), AC-30 (дубли), решения UX U-2–U-6 и U-23.
  • Длинные группы (U-4): видно 10 строк, затем «Показать ещё 20», в заголовке — полное число. У администратора группа «Подключить подразделения» бывает на сотни строк, у HR на корне справочных строк тоже сотни. stack.html разрешает отдавать целиком только короткие личные списки.
  • Риски audit.md: MatrixRoute.AwaitingAsync зовёт TurnAsync на каждую версию (3–8 запросов); ProcessRoles.HrUnitsAsync читает поддерево на каждое закрепление; «нет HR» и «нет матрицы» читают цепочку предков на каждое подразделение.
  • custom-coding-rules.md: производительность меряется только у Task с объявленным perf-риском, на переиспользуемом сиде 10 000+ сотрудников.

Decision

Стол вычисляется на сервере при каждом запросе из текущих данных и отдаётся тремя методами desk. Счётчик — та же вычисленная выборка, отданная числом. Источники читают данные наборными запросами с постоянным числом обращений к БД и считают правила в памяти теми же функциями, что проверяют действия.

API (все методы — только аутентифицированному и только про себя)

  • GET /api/v1/desk → { actionCount, groups: [{ group, isReference, total, items }] }. Только непустые группы; в items — первые 10 пунктов (константа U-4).
  • GET /api/v1/desk/items?group=…&group=…&limit= → { items, total }. limit — число строк с начала выборки; «Показать ещё» перечитывает группу с начала на 10 + 20·k строк. total — полное число пунктов выборки. Пункты исчезают по мере выполнения, но пропусков и повторов строк при этом не будет. Очередь «Навести порядок в оргструктуре» (AC-33) — та же выборка по её группам.
    • Предел limit — собственная константа desk, 2 000 строк, а не ListRequest: его 200 строк меньше обычных групп на сотни строк. limit меньше 1 — 400 с ошибкой поля; больше предела — сервер отдаёт предел строк.
    • Предел — документированный потолок стола, а не страница: продолжения выборки нет, и строки группы за пределом на столе недостижимы по построению. Хвост группы действий открывается по мере выполнения пунктов. Объекты справочной группы за пределом остаются доступны в очередях сценариев и вторичных разделах, но не на столе.
    • Perf-Task проверяет на сиде, что самая большая группа каждого из четырёх пользователей замера меньше предела.
    • Если строк пришло меньше и запрошенного, и total, группа усечена пределом: SPA пишет об этом под таблицей и прячет «Показать ещё».
  • GET /api/v1/desk/count → { actionCount }.
  • DeskItem несёт:
    • объект: тип, id, название, контекст;
    • group и isReference;
    • причины по порядку таблицы 2: вид, момент события (только у событийных видов), типизированные параметры;
    • идентификаторы для переходов;
    • встроенное действие: учётную запись и её version для resend-invitation.
    Тексты причин и названия групп SPA рисует по виду из каталога текстов, утверждённого в plan; сервер отдаёт данные, а не фразы. Строки группы идут в устойчивом порядке: момент события по возрастанию (кто ждёт дольше — первым), затем название, затем id.
  • Доступ. Параметра «чей стол» нет — получить чужой стол невозможно по построению (AC-16.3). Состав ограничен областью ролей каждого источника (AC-16.6). Неопубликованное попадает только к тем, кто читает его по правилам career-framework: источники фильтруют через MatrixRoute.ReadableAsync и CatalogViewer.Sees (AC-16.5).
  • Блок «Что можно сделать». Карточки SPA строит по ролям сессии (/auth/me, /career/me), подписи «Ждут вас: N» берёт из total групп. Отдельного API карточек нет.

Вычисление и производительность

  • Снимок оргструктуры на запрос. Новый метод порта IEmployeeDirectory.FindOrgSnapshotAsync (org-structure) одним вызовом отдаёт:
    • все подразделения: id, родитель, руководитель, активность;
    • собственные перечни должностей подразделений;
    • должности: название, активность;
    • число работающих сотрудников по паре «подразделение — должность».
    У записи снимка есть методы-правила org-structure: предки, поддерево, «доступные подразделению должности» (свой перечень и перечни предков). Это правило остаётся у владельца. Реализация порта scoped и запоминает снимок на время запроса, поэтому career-framework и user-management читают его один раз.
  • Одни правила для стола и для действий. Ближайший ответственный HR, согласующий шага 1, «может ли учётная запись руководителя действовать» — чистые функции, вынесенные из ProcessRoles и MatrixRoute. Путь действия вызывает их на прочитанной цепочке предков, путь стола — на снимке. Правило одно, способов загрузки два; так закрыт риск расхождения стола с правами сервера.
  • Данные career-framework: версии в работе и опубликованные, решения, черновики, треки, уровни, связи, закрепления HR, учётные записи руководителей и HR. Их читают несколько наборных запросов на источник, без циклов с запросами внутри.
  • Бюджет на сиде:
    • GET /desk/count — p95 ≤ 300 мс;
    • GET /desk — p95 ≤ 600 мс;
    • замер для четырёх пользователей: администратор, HR с закреплением на корне, руководитель верхнего подразделения, сотрудник;
    • SQL-команд на запрос не больше 25, и их число не зависит от объёма данных.
    Если вычисление длится дольше 1 с, в лог пишется предупреждение: роль, время по источникам, без ПДн.
  • Task с perf-риском (назначает plan): вычисление стола и счётчика. Task создаёт переиспользуемый сид tests/perf/seed-10k.sql — SQL на generate_series поверх пустой мигрированной БД. Состав сида:
    • 10 000 работающих и 200 уволенных сотрудников;
    • около 1 000 подразделений глубиной до 7;
    • около 400 должностей с перечнями;
    • закрепления HR на корне и примерно на 50 подразделениях;
    • около 300 учётных записей, часть из них приглашены с истёкшими ссылками или заблокированы;
    • около 60 треков по 3–6 уровней, связи заведены частично;
    • около 500 матриц с опубликованными и рабочими версиями;
    • около 1 500 компетенций и черновики.
    Замер — в impl-test. Последующие Task с perf-риском берут тот же сид.
  • Кэш. Серверного кэша нет: собственное действие должно сразу менять счётчик (AC-3.4), а сбрасывать кэш по изменениям трёх модулей сложнее, чем пересчитать.
  • Клиент. Ключ ['desk'] в TanStack Query:
    • MutationCache.onSuccess сбрасывает ['desk'] после любой успешной мутации (AC-3.4);
    • смена адреса перечитывает счётчик (AC-3.5);
    • refetchOnWindowFocus включён (значение по умолчанию);
    • опроса по таймеру и push нет (AC-3.6);
    • до первого ответа и при ошибке метки нет (U-2).

Complication Approval (метод порта org-structure)

Что
Метод IEmployeeDirectory.FindOrgSnapshotAsync и публичная запись OrgSnapshot с методами-правилами (предки, поддерево, доступные должности). Записи EmployeeStatus аддитивно получают OrgUnitId и PositionId — для AC-14 и AC-29.
Зачем
Без наборного чтения стол делает N+1 запросов по подразделениям и версиям — главный риск производительности из audit.md.
Обоснование
Это расширение уже опубликованного порта, только чтение, scoped. Снимок используют источники стола career-framework и user-management, экраны AC-12, AC-14, AC-31. Правило «доступные подразделению должности» остаётся у владельца данных.
Альтернативы
Несколько узких методов: больше вызовов, те же данные. Прямой SQL из career-framework к таблицам org-structure: ломает границу модуля.

Consequences

Positive

  • Счётчик по построению равен числу пунктов-действий; второго алгоритма подсчёта нет.
  • Нет хранилища задач и новых таблиц (AC-2.12, AC-2.13).
  • N+1 устранён одинаково для стола и для экранов сценариев; правила действий и стола общие.

Negative

  • Каждый переход пересчитывает стол целиком. Стоимость ограничена бюджетом, но растёт линейно с размером организации.
  • Вынос правил ProcessRoles/MatrixRoute в чистые функции затрагивает пути действий. Риск регрессии закрывают существующие тесты маршрута и ролей.
  • Снимок читает всю оргструктуру на запрос. Для 10 000 сотрудников это приемлемо; при росте на порядок нужна загрузка по поддереву.
  • «Показать ещё» пересчитывает весь стол ради одной группы.
  • Группа длиннее потолка desk показывается на столе не до конца; хвост справочной группы на столе недостижим, пока она длиннее потолка.

Обратимость: лёгкая — контракт аддитивный; кэш или режим «только число» добавляются без смены контракта. Пересмотр: бюджет не выполнен на сиде — тогда короткая память результата на пользователя со сбросом после его мутаций; либо рост организации на порядок; либо группа на сиде или в эксплуатации упирается в предел desk.

Alternatives considered (optional)

  • Хранимые задачи (таблица действий, которую обновляют события модулей) — отклонено: действия вычисляются из данных и не закрываются вручную | binding — AC-2.12, AC-2.13.
  • Отдельный упрощённый подсчёт для счётчика — отклонено: без поглощения между модулями число разошлось бы со списком (AC-3.2, AC-30.6).
  • Весь стол одним ответом — отклонено: сотни и тысячи справочных строк; stack.html разрешает отдавать целиком только короткие личные списки.
  • Страницы со смещением — отклонено: строки исчезают по мере выполнения (U-4), поэтому группа перечитывается с начала.
  • PageResponse с пределами ListRequest (200 строк) и ссылка «Открыть очередь» у каждой большой группы — отклонено: меняет принятый U-4, а справочные строки не исчезают, и без ссылки до хвоста группы не добраться.
  • Готовые фразы причин с сервера — отклонено: тексты жили бы в двух местах; SPA уже рисует статусы и метки по коду.

ADR-3: Связь «должность — карьерный уровень»: таблица, права, блокировки, запреты AC-24/AC-25

Context

Требования — AC-24.1–24.10, AC-25.1–25.7, AC-31. Принятый скоуп отменяет канон career-framework.md «карьерный уровень с должностью не связан»; правка документа — на design-promote. Факты, от которых зависит решение:

  • Должности и перечни подразделений принадлежат org-structure (таблицы positions, org_unit_positions; должность не удаляется, только деактивируется).
  • Зависимость career-framework → org-structure разрешена. Внешний ключ на чужую таблицу задаётся по имени сущности, как career_tracks.owner_org_unit_id.
  • Строки-связи удаляются физически и журналируются: OrgUnitPosition, OrgUnitHr.
  • Изменяющие запросы требуют If-Match.
  • Порядок блокировок: дерево 5001001 → справочники 5003001 → строка матрицы.
  • Правило проекта «Multi-row invariant locking»: каждая блокировка инварианта объявляется со своим местом в порядке и получает детерминированный тест гонки.

Отдельно: новый трек не имеет уровней, а AC-25.6 запрещает делать действующим трек без уровней. Поэтому «создать сразу действующим» (AC-25.1) у хранителей трека — HR и администратора — теперь невозможно ни при каких данных.

Decision

Связь хранит career-framework в таблице career_level_positions: ссылки на свои уровень и трек и на должность org-structure (внешний ключ по имени сущности). Правят связь два метода уровня под блокировкой справочников с If-Match уровня. «Уровень без должности» и готовность трека считает одна функция; ею пользуются запреты, проверка полноты, публикация, стол и экраны.

Данные

  • Колонки career_level_positions:
    • level_id — внешний ключ на career_levels, RESTRICT;
    • position_id — внешний ключ на positions по имени сущности Competency.OrgStructure.Position, RESTRICT;
    • track_id — внешний ключ на career_tracks, RESTRICT. Это копия TrackId уровня, а он после создания не меняется.
  • Ключи и индексы:
    • первичный ключ (level_id, position_id);
    • уникальный индекс (track_id, position_id) — страховка AC-24.2 (в пределах трека должность связана не больше чем с одним уровнем);
    • индекс position_id — для обратного вопроса «в каких треках моя должность» (AC-14.7, AC-26.1, AC-29).
    Колонки Version нет: это строка-связь, как org_unit_positions.
  • Журнал. Сущность CareerLevelPosition помечена [Audited] (уровень, должность, трек). Перехватчик журнала пишет CareerLevelPosition.Created и CareerLevelPosition.Deleted (AC-24.7).
  • Миграция CareerLevelPositions: только схема, связи не заполняются (AC-24.8). Down удаляет таблицу. Опубликованные матрицы и действующие треки не трогаются (AC-25.5).
  • org-structure не меняется. Деактивация должности и исключение её из перечня связь не снимают и не блокируются (AC-24.9). Должности не удаляются, поэтому RESTRICT на positions никогда не срабатывает. Должности, перечни и численность career-framework читает только через порт — снимок оргструктуры, ADR-2.

Методы

  • GET /api/v1/career/tracks/{id}/positions — уровни в порядке трека, у каждого:
    • version;
    • связанные должности: название, активность, число работающих сотрудников в поддереве подразделения трека, признак canUnlink, вычисленный сервером по тому же правилу AC-25.2, что и DELETE (U-16);
    • признак «нет действующей должности».
    Плюс canEdit трека. Читать может тот, кто видит трек; остальным — 404.
  • GET /api/v1/career/tracks/{id}/available-positions?q=&page=&pageSize= — серверные страницы (ListRequest) с числом сотрудников. В выборку попадают действующие должности, которые доступны подразделению трека или любому его дочернему, и ещё не связаны ни с одним уровнем этого трека (AC-24.4, AC-31.3). Доступность — по правилу снимка оргструктуры: собственные перечни поддерева плюс собственные перечни предков подразделения трека.
  • POST /api/v1/career/levels/{id}/positions { positionId }, If-Match уровня. Повтор той же пары ничего не меняет. Отказы:
    • 400 с ошибкой поля positionId — должность неактивна или недоступна треку;
    • 409 — должность уже связана с другим уровнем трека (AC-24.2).
  • DELETE /api/v1/career/levels/{id}/positions/{positionId}, If-Match уровня. 409 по AC-25.2 — если трек действующий и снимается последняя действующая должность уровня; статус самого уровня (черновой, действующий, неактивный) не важен. Тело отказа — PublicationRefusal (ADR-4) с этим уровнем (AC-25.4).
  • Ответ и If-Match. Изменение связи увеличивает Version уровня — так же, как перестановка уровней увеличивает Version трека. Ответ — строка уровня с новым ETag. На 412 действует правило AC-20: перечитать, без автоповтора. Окно трека и сценарий AC-31 вызывают одни и те же методы (AC-24.6).
  • Права — права правки трека (CatalogViewer.CanEdit): хранители всегда, руководитель — черновой трек своего подразделения (AC-24.5). Остальным — 403.
  • Удаление уровня или трека удаляет их связи построчно в той же транзакции; каждая строка — событие журнала.

Готовность трека — одна функция

Функция проверяет уровни трека, кроме неактивных. Результат: «нет уровней», либо перечень уровней без связанной действующей должности (positions.is_active, AC-24.10). Её используют:

  • утверждение и «Вернуть в работу» трека — 409 PublicationRefusal со списком уровней (AC-25.1, AC-25.4, AC-25.6);
  • POST /career/tracks — трек теперь всегда создаётся черновым, у хранителей тоже: у нового трека нет уровней (AC-25.6). Хранитель утверждает его после уровней и связей. Это изменение поведения существующего метода, см. ADR-6;
  • снятие связи — запрет AC-25.2: её проверка «нет связанной действующей должности» применяется к снимаемому уровню любого статуса;
  • проверка полноты версии: «у уровня «X» трека «Y» нет связанной действующей должности» по уровням трека матрицы (AC-25.7, AC-8.15). Значит, запрет действует во всех местах, где полнота проверяется сейчас: отправка, согласование обоих шагов, возврат с правками, принятие правок; и при публикации (AC-25.3, AC-10.9);
  • стол: виды 26.2, 26.3 и пометка 27.2; очередь черновиков (поле readiness, ADR-6); экраны AC-31; шаги 1 и 5 мастера.

Блокировки

  • Все изменения связей идут через store.BeginWriteAsync: дерево разделяемо (5001001), затем справочники эксклюзивно (5003001). Новой блокировки нет; место в порядке — шаг 2 из stack.html.
  • Под разделяемой блокировкой дерева должности и перечни не меняются — org-structure меняет их под эксклюзивной. Поэтому проверки AC-24.4, AC-25.1 и AC-25.2 видят устойчивые данные.
  • Утверждение трека и снятие связи сериализуются блокировкой справочников.
  • Тесты гонок (по правилу проекта):
    1. два параллельных снятия двух последних действующих должностей одного уровня действующего трека — одно из них получает 409;
    2. снятие связи против утверждения того же чернового трека — утверждение видит итог снятия;
    3. одна должность параллельно связывается с двумя уровнями трека — одна попытка получает 409, уникальный индекс страхует.

Consequences

Positive

  • Модель А живёт в одной таблице с ограничениями БД. Направление зависимостей сохраняется: внешний ключ идёт из career-framework в org-structure, а org-structure о связи не знает.
  • Одна функция готовности: запреты, полнота, стол и экраны не расходятся.
  • Новых блокировок и новых шагов порядка блокировок нет.

Negative

  • ETag уровня меняется при каждом изменении связей. Открытая форма правки уровня после этого получит 412 (по правилу AC-20 — допустимо).
  • track_id денормализован и держится на неизменности TrackId уровня.
  • После выката связей нет, и новые версии матриц по существующим трекам не отправляются, пока связи не заведут. Побочный эффект принят пользователем 2026-10-12.
  • У HR и администратора на шаг больше: новый трек — черновик, его нужно утвердить.

Обратимость: умеренная — до заполнения пользователями таблица пуста, после этого это данные. Пересмотр: если понадобится прямая связь сотрудника с уровнем (out of scope) или история связей.

Alternatives considered (optional)

  • Уровень хранится колонкой у должности (positions) — отклонено: должность входит в треки разных подразделений (AC-24.3), а org-structure пришлось бы ссылаться на career-framework | binding — направление зависимостей модулей (stack.html).
  • Связи в jsonb трека — отклонено: нет внешних ключей и уникального индекса; единственность держал бы код, а удаление должностей проверялось бы запросом по документу.
  • If-Match трека вместо уровня — отклонено: каждая связь меняла бы ETag трека и ломала бы сохранение открытого окна трека, которое шлёт If-Match трека при переименовании и перестановке уровней.
  • Отказывать хранителям 409 на POST /career/tracks — отклонено: HR и администратор не смогли бы создавать треки. Запрос «трек сразу с уровнями и связями» — отклонено: новая форма запроса ради одного случая.
  • Отдельная блокировка на трек — отклонено: лишняя ступень в едином порядке блокировок, а эксклюзивная блокировка справочников уже сериализует.

ADR-4: Общее правило публикации: каскад, перечень до подтверждения, отказ 409

Context

Требования — AC-34.1–34.9, AC-8.13 и AC-8.14 (решение C-1 с поправкой скоупа), AC-10.4, AC-10.8, AC-11.7–11.9; решения UX U-10–U-12 и U-21. Что есть сейчас:

  • Утверждение трека утверждает его черновые уровни.
  • Публикация версии делает действующими черновые уровни, компетенции, категории этих компетенций и шкалу (MatrixCatalog.DraftsAsync). Трек в этот набор не входит: матрица допускается только по действующему треку.
  • Утверждение остальных записей ничего за собой не публикует, хотя черновик может ссылаться на собственные черновики автора (IsUsable).
  • Хранитель (HR, администратор) создаёт запись сразу действующей (CatalogViewer.StatusOfNew), даже если она ссылается на его черновики.

Образцы, на которые опирается решение:

  • отказ DeletionRefusal: до 5 видимых мешающих записей и moreCount;
  • EmployeeImpact: подтверждение и исполнение считает один код, поэтому показанное совпадает с выполненным.

Decision

Все публикации идут через одну функцию career-framework. Публикацией считаются утверждение и «Вернуть в работу» записи и публикация версии любым действием из publishingActions (ниже). Создание записи каскадом не публикует (ниже). Функция строит транзитивное замыкание черновых ссылок и проверяет право и условия каждой сущности. Затем она либо публикует всё в текущей транзакции, либо отказывает 409 со списком. Та же функция без записи отвечает на предпросмотр.

  • Ссылки каскада (AC-34.3):
    • версия → трек матрицы и все его уровни; уровни и компетенции содержимого; шкала версии;
    • трек → направление и черновые уровни трека: утверждение трека утверждает их и сейчас (канон career-framework AC-19), правило сохраняется;
    • компетенция → категория, направление, шкала.
    Каскад идёт транзитивно и только по черновым сущностям. Действующие и неактивные ссылки не публикуются; неактивная запись в версии остаётся проблемой полноты, как сейчас. Черновые уровни трека, который утверждается сам, входят в замыкание, перечень, проверки, cascadeTag и исполнение так же, как уровни трека версии.
  • Чьё право «вправе утвердить» (AC-34.4) — решение пользователя 2026-10-13:
    • публикация записи (утверждение, «Вернуть в работу») — право действующего пользователя;
    • публикация версии — право ответственного HR подразделения матрицы (ProcessRoles.ResponsibleHrAsync, согласующий шага HR), чей шаг засчитывается согласованным, — какое бы действие из publishingActions её ни запустило и кто бы его ни выполнил.
    Права этого HR строит тот же CatalogViewer по его учётной записи. Если ответственного HR нет, каждая черновая сущность каскада получает NoRight.
  • Создание записи хранителем (AC-34.1) — решение пользователя 2026-10-13. Создание каскадом не публикует. POST записи, которую StatusOfNew создал бы действующей, вычисляет её черновые ссылки по ссылкам каскада (выше):
    • черновые ссылки есть — запись создаётся черновиком; ответ 201 несёт status = Draft, и SPA предлагает «Утвердить» с перечнем через предпросмотр записи (ниже);
    • черновых ссылок нет — запись создаётся действующей, как сейчас.
    Отдельного предпросмотра для несохранённой записи нет. Трек хранитель всегда создаёт черновиком (ADR-3).
  • Проверки каждой сущности каскада:
    • CanManage того, чьё право проверяется (выше);
    • повтор названия с учётом всего, что публикуется вместе, — через ChangeTracker, как сейчас;
    • у трека — готовность по ADR-3 (AC-25.1, AC-25.6);
    • если корень — версия, сначала проверяется полнота (существующий 409 со строками; он уже включает AC-25.3 и AC-25.7), затем каскад.
  • Исполнение. Всё идёт в транзакции действия под уже взятыми блокировками: у записи — дерево разделяемо и справочники эксклюзивно; у версии — ещё и строка матрицы FOR UPDATE. Новых блокировок нет. Отдельные SaveChanges остаются только там, где они есть сейчас (архивирование прежней опубликованной версии). Отказ откатывает всё (AC-34.8).
  • Журнал. Каждая сущность, опубликованная каскадом, получает своё событие <Тип>.Approved, как сейчас; в Reason — ссылка на корень «каскад <Тип> <id>» (AC-34.9). События корня прежние. Компетенции получают строку истории версий, как при утверждении.
  • Отказ 409 — PublicationRefusal. Это ProblemDetails с полями:
    • blockers — вид (направление, трек, уровень, категория, компетенция, шкала), id, название, причина (NoRight | NoLevels | NoActivePosition | NameTaken), контекст;
    • moreCount.
    Видимых — не больше 5, невидимые пользователю учитываются только в числе, как в DeletionRefusal. detail — русская фраза для заголовка отказа (UX, «Общие состояния», п. 4).
  • Предпросмотр — только чтение, без блокировок:
    • GET /api/v1/career/matrix-versions/{id}/publication → { publishingActions, entries, blockers, moreCount, cascadeTag }. publishingActions — единственный перечень действий, публикующих версию: какие из доступных пользователю сейчас actions версии её опубликуют. Это approve на шаге HR; accept-changes, если версию вернул шаг HR; submit, approve шага 1 и accept-changes после возврата с шага 1, если следующим шагом будет автосогласование HR (автор и есть ответственный HR; MatrixWorkflow.ToHrAsync). SPA этого сама не вычисляет (AC-34.7). Мешающие NoRight считаются по праву из пункта «Чьё право» (выше), поэтому предпросмотр одинаков для любого действия из перечня. Читать может тот, кто читает версию; иначе 404.
    • GET /api/v1/career/{directions|tracks|categories|competencies|scales}/{id}/publication → { entries, blockers, moreCount, cascadeTag }. Невидимая запись — 404; без права утверждать — 403.
  • Совпадение показанного и выполненного. cascadeTag — хэш корня (id, version) и упорядоченных пар (id, version) сущностей перечня. Публикующие методы (approve и activate записей; submit, approve, accept-changes версии) принимают необязательный параметр ?cascade=<tag>. Если тег передан и пересчитанный под блокировками отличается, ответ — 412: SPA перечитывает перечень и показывает его заново, без автоповтора (правило AC-20). Без параметра всё работает как раньше — для старых клиентов. If-Match корня ловит изменения самого корня, тег — изменения вокруг него: новый черновой уровень трека, другую категорию у компетенции.
  • Матрица по черновому треку (AC-8.13, AC-8.14).
    • POST /career/matrices принимает действующий трек своего или вышестоящего подразделения, как сейчас, либо черновой трек, принадлежащий подразделению матрицы.
    • Направление — только действующее (канон AC-36 не меняется).
    • Черновые уровни трека матрицы пригодны для содержимого независимо от автора: уровни этого трека правит и HR.
    • При публикации такой версии каскад делает трек и его уровни действующими либо отказывает с названием трека и его уровнями без должностей.
  • Подтверждение у версии (AC-34.5, AC-34.7). Перед каждым действием из publishingActions SPA показывает перечень и просит инициатора действия подтвердить его. Действие, которого нет в publishingActions, ничего не публикует и перечня не показывает.
  • Существующие разделы (AC-34.6, U-21). Перед утверждением SPA вызывает предпросмотр. Если перечень пуст и мешающих нет — утверждает сразу; иначе показывает окно с перечнем.

Consequences

Positive

  • Один путь кода: предпросмотр совпадает с исполнением, у матрицы и справочников одни правила.
  • AC-25 и AC-34 проверяются при любой публикации, включая автосогласование и «Вернуть в работу».
  • Один формат отказа для прав, уровней без должностей и названий.

Negative

  • Перед каждым утверждением в разделах — лишний GET предпросмотра (U-21).
  • Утверждение записи теперь может опубликовать больше, чем раньше. Это изменение поведения существующих методов, оно описано в ADR-6.
  • Пять методов получают необязательный параметр cascade.
  • Когда публикацию версии запускает не сам ответственный HR, черновики публикуются его правом, хотя он в этот момент ничего не делает. Права HR загружаются отдельно от прав действующего пользователя.
  • Хранитель, чья новая запись ссылается на его черновики, получает черновик и утверждает его вторым шагом.
  • Замыкание читает черновики по цепочке; глубина ограничена тремя ссылками (версия → компетенция → категория).

Обратимость: умеренная. Пересмотр: появятся сущности с длинными цепочками ссылок или понадобится частичный каскад «опубликовать без …» — сейчас его запрещает AC-34.8.

Alternatives considered (optional)

  • Без каскада — просто запрет публикации со ссылками на черновики — отклонено | binding — AC-34.2 (принятый скоуп).
  • Право действующего пользователя и при публикации версии — отклонено: руководитель черновики не утверждает (канон AC-19), поэтому публикация версии, запущенная не HR, при любом черновике в каскаде отвечала бы 409 NoRight вопреки AC-9.4 | binding — решение пользователя 2026-10-13.
  • Каскад при создании записи с предпросмотром несохранённой записи — отклонено: понадобился бы новый метод предпросмотра по телу запроса, а утверждение созданного черновика показывает тот же перечень существующим предпросмотром | binding — решение пользователя 2026-10-13.
  • Отдельные форматы 409 для прав, уровней и названий — отклонено: SPA разбирала бы три вида отказа ради одного окна.
  • Обобщить DeletionRefusal в общий тип — отклонено: переименование схемы контракта ради экономии одного класса.
  • Без тега — публиковать текущее замыкание — отклонено: допускает публикацию того, что пользователь не видел (AC-34.5).
  • Тег в теле запроса или в If-Match — отклонено: у публикующих методов нет тела, а If-Match уже занят версией корня.
  • Перечень каскада в ответе GET версии или записи — отклонено: каждый просмотр считал бы каскад.

ADR-5: Письма-напоминания (AC-15): получатели, отправка после фиксации через фоновую очередь, возврат на цель после входа

Context

Требования — AC-15.1–15.14, решения audit A-4, A-5, A-11, A-12, решения UX U-17–U-19. Ограничения и факты:

  • stack.html: MailSender вызывается после фиксации транзакции и не под блокировкой; ссылки строятся от App:PublicBaseUrl.
  • MailSender синхронный: соединение на каждое письмо, до Smtp:Timeout = 15 с. При недоступном relay переходы версий и создание черновиков тянулись бы 15–45 с (риск из audit.md).
  • Прецедент — PasswordResetQueue: очередь в памяти, потерю при перезапуске пользователь принял. Outbox — non-goal требований user-management.
  • Mail.SendFailed журналируется с видом письма и без адреса.
  • career-framework пока писем не шлёт.
  • SPA: обработчик 401 уводит на /login, не запоминая цель, а LoginPage после входа всегда идёт на /.

Decision

После фиксации действия career-framework определяет получателей по состоянию после действия и кладёт готовые письма в ограниченную очередь в памяти. Фоновый обработчик перед отправкой проверяет, что учётная запись может действовать, отправляет письмо через MailSender и журналирует отказ. Возврат на цель после входа делает только SPA, по проверенному относительному пути.

Других писем нет (AC-15.6).

  • Когда считаются получатели. После CommitAsync, когда блокировки уже сняты. Получатели берутся из состояния после действия: ход и так вычисляется для ответа (StateAsync).
  • Текст и ссылка. Текст — константы, как в AccountMail; тексты утверждаются в plan. Ссылка — App:PublicBaseUrl плюс маршрут SPA (ADR-6): /desk/review/{versionId}, /desk/rework/{versionId}, /desk/drafts/{kind}/{entryId}. В письме нет комментария согласующего, разницы и состава версии (U-17, AC-16.5), нет токенов и адресов.
  • Очередь. Ограниченный Channel на 1 000 писем: при переполнении письмо отбрасывается с предупреждением в лог. Один читатель — BackgroundService в career-framework, письма по одному. Элемент очереди: id получателя, вид, тема, текст, кто совершил действие, request_id исходного запроса.
  • Обработчик работает в своём scope:
    1. перечитывает учётную запись и сотрудника;
    2. отправляет через MailSender.SendAsync;
    3. при false пишет IAuditWriter.WriteAsync(Mail.SendFailed): тип сущности AppUser, id получателя, Reason = MatrixAwaitingApproval | MatrixReturned | DraftAwaitingApproval, Actor — кто совершил действие, RequestId — исходный (AC-15.11; audit.md получает новые виды).
    Исключения ловятся внутри цикла и пишутся в лог типом.
  • Связь с действием. Ответ действия не ждёт SMTP. Отказ SMTP действие не откатывает (AC-15.10): оно зафиксировано до постановки письма в очередь.
  • Возврат на цель (SPA, сервер не меняется).
    • Обработчик 401 переводит на /login?returnTo=<pathname+search> текущего адреса, кроме страниц входа.
    • LoginPage после входа переходит на цель, если она прошла проверку, иначе на /desk. Подсказка на экране входа показывается, только когда цель есть (U-19).
    • Проверка цели: разобрать new URL(value, location.origin). Принимается только тот же origin и путь, который начинается с одного «/» — не «//», без «\» и управляющих символов. Страницы входа (/login, /forgot-password, /accept-invitation, /reset-password) целью быть не могут.
    • Переход идёт по разобранным pathname + search, а не по исходной строке. Запрет «//», «\» и управляющих символов — решение проекта.

Complication Approval (фоновая очередь писем)

Что
CareerMailQueue — ограниченная очередь в памяти и BackgroundService в career-framework.
Зачем
Синхронная отправка держит ответ согласования и создания черновика до 15 с на каждое письмо при недоступном SMTP, а у черновика бывает несколько получателей.
Обоснование
Тот же механизм, что PasswordResetQueue: System.Threading.Channels и встроенный BackgroundService, без пакетов и таблиц. Письмо — только напоминание, источник правды — стол и счётчик (AC-2.12). Потеря письма при перезапуске не теряет действие.
Альтернативы
Синхронно после фиксации — проще, но ответ тянется 15–45 с при сбое relay. Outbox в БД с воркером — гарантированная доставка, но это non-goal, плюс код и таблица. Общая очередь писем в Platform — преждевременно, вызывающая сторона одна.

Consequences

Positive

  • Действия быстрые при любом состоянии SMTP; правило «не под блокировкой и не в транзакции» соблюдено по построению.
  • Получатели и фильтры собраны в одном месте; отказы журналируются по виду письма.
  • Возврат на цель не открывает перенаправление на чужой сайт.

Negative

  • Письма теряются при перезапуске процесса и при переполнении очереди. Риск тот же, что принят для сброса пароля.
  • Пользователь не видит, ушло ли письмо (в отличие от приглашения, AC-6.9).
  • В процессе ещё один фоновый компонент. Тесты ждут письмо в Mailpit асинхронно (MailCatcher).
  • Цель возврата видна в адресе страницы входа.

Обратимость: лёгкая — замена очереди на outbox внутренняя, контракт не меняется. Пересмотр: жалобы на потерянные напоминания или требование гарантированной доставки.

Alternatives considered (optional)

  • Синхронная отправка сразу после фиксации, как у писем администратора — отклонено: 15 с на письмо при недоступном relay на переходах версий и создании черновиков.
  • Outbox в БД — отклонено: гарантированная доставка вне скоупа (non-goal user-management), лишние таблица и воркер.
  • Получатель возврата — AuthorId версии — отклонено: автор — текущий руководитель подразделения матрицы | binding — A-5, канон career-framework AC-44.
  • Хранить цель возврата в состоянии навигации или в sessionStorage — отклонено: состояние навигации теряется при перезагрузке страницы входа, а sessionStorage — скрытое состояние, которое тоже пришлось бы проверять.

Related ADRs (optional)

  • ADR-6: маршруты SPA, на которые ведут ссылки писем.
  • ADR-3: черновые треки хранителей писем не порождают.

    • headAccount, hrAccount — { id, email, state: None | Invited | Blocked | Active, version };
    • positions — { own, inherited };
    • rows — [{ row, status: Ready | Missing | Waiting, reason }].
    Статусы считает сервер по тем же данным и определениям, что виды 6.2, 28.6, 6.3/6.4, 28.2: снимок оргструктуры, ближайшее закрепление HR, UserStatus.IsActive. Пустой перечень отмечается и у подразделения без сотрудников (AC-12.5). UserStatus порта IUserDirectory аддитивно получает Version.
  • GET /me/place → { employee | null, unit (путь), position, head, responsibleHr (свой или унаследованный и откуда), tracks, publishedMatrices, noTrack }:
    • каждый элемент tracks: трек, направление, текущий уровень, следующие уровни — с требованиями из snapshot опубликованной версии матрицы своего подразделения по этому треку либо без требований;
    • noTrack — справочный пункт AC-29;
    • пользователь без привязки получает 200 с employee = null (AC-14.6);
    • только опубликованные версии собственного подразделения (AC-14.3, A-8).
  • GET /tracks/{id}/positions, GET /tracks/{id}/available-positions — см. ADR-3.
  • Шаг мастера (AC-8.11).
    • Колонка matrix_versions.builder_step (smallint, NULL, без журнала: это состояние сценария, а не модели); миграция без заполнения.
    • PUT …/content принимает необязательный ?builderStep=2..6 и сохраняет его даже без изменения содержимого. Version растёт, If-Match — как у правки содержимого.
    • MatrixVersionResponse.builderStep — аддитивное поле. null означает, что версия создана вне мастера; мастер тогда открывает шаг 2.

Контракт API 3.0.0 → 3.1.0

  • Аддитивно:
    • новые методы career-framework и /api/v1/desk*;
    • необязательные поля ответов: builderStep, readiness у /drafts;
    • новые члены перечислений;
    • необязательные параметры ?cascade и ?builderStep;
    • новое тело 409 PublicationRefusal — наследник ProblemDetails;
    • 412 при несовпадении cascade — только если параметр передан.
  • Изменения поведения без изменения формы — они следуют из принятых AC:
    • POST /career/tracks всегда создаёт черновик (AC-25.1, AC-25.6);
    • POST направлений, категорий, компетенций и шкал у HR и администратора создаёт черновик, если запись ссылается на черновики, — status в ответе 201 (ADR-4);
    • approve и activate записей и переходы версии публикуют каскад или отвечают 409 (AC-25, AC-34);
    • полнота включает уровни без действующей должности (AC-25.7): до заведения связей отправка версий по существующим трекам отклоняется;
    • POST /career/matrices принимает черновой трек своего подразделения (AC-8.13);
    • удаление уровня или трека удаляет их связи.
  • Документирование: раздел «Переход на контракт API 3.1.0» в career-framework.md (и в desk.md); OpenAPI строится из кода. Шагов оператора нет: миграции применяются при старте и данных не переносят.

Consequences

Positive

  • Нет транзакций через несколько модулей: экраны собраны из существующих изменяющих методов.
  • Всё, что решает доступность действий, считает сервер: статусы строк AC-12, полнота, публикующие действия, canUnlink.
  • Контракт остаётся обратно совместимым по форме, а клиентам с прежним поведением достаточно не передавать новые параметры.

Negative

  • career-framework получает новые методы чтения (список в Decision). Метод /org-units/{id}/setup описывает готовность подразделения, но живёт в career-framework: только этот модуль видит закрепление HR, оргструктуру и учётные записи.
  • Колонка builder_step хранит состояние сценария в таблице модели.
  • Изменения поведения существующих методов нужно описать в документах подсистемы, а разделы «Карьерная модель» должны вызывать предпросмотр.
  • Адреса из писем трудно менять: старые ссылки остаются в почтовых ящиках.

Обратимость: лёгкая для методов чтения; тяжёлая для адресов из писем. Пересмотр: при появлении внешних потребителей API изменения поведения существующих методов повышают major-версию.

Alternatives considered (optional)

  • Контракт 4.0.0 из-за изменения поведения POST /career/tracks и новых 409 — отклонено: форма запросов и ответов не меняется, 409 у этих методов уже объявлен, единственный клиент — своя SPA. Контракт 3.1.0 принят пользователем 2026-10-13.
  • Шаг мастера в localStorage — отклонено: не переживает смену устройства и не даёт столу текста «остановились на шаге N». Отдельная таблица прогресса — лишняя сущность ради одного числа. Отдельный метод PUT …/builder-step — два запроса на одно «Сохранить и далее».
  • Экран AC-12 из четырёх запросов в SPA — отклонено: статусы строк считались бы в браузере | binding — «Сервер — единственный источник истины» (stack.html).
  • Очередь AC-32 через /desk/items — отклонено: администратору стол не выводит 27.5–27.8 (AC-28.9).
  • Маршруты сценариев без префикса /desk — отклонено: раздел меню «Рабочий стол» не определялся бы по началу адреса (U-22).
