## Requirements
Raw scope and stage (a) answers; stage (c) refines the answers.
- Raw scope: «В этом спринте нужно сделать возможность импорта оргструктуры из excel-файла.»
- Problem: оргструктура (подразделения, должности, сотрудники) ведётся во внешней кадровой выгрузке; сейчас её приходится переносить в систему вручную по одной записи. Нужен повторяемый импорт, который приводит оргструктуру системы к состоянию файла.
- Actors: глобальный администратор и HR (по роли учётной записи) запускают и проводят импорт; остальные пользователи видят результат в разделе «Оргструктура».
- Functional requirements:
  - Повторяемый импорт: каждая загрузка сверяет файл с текущими данными и обновляет их, а не только добавляет.
  - Формат — только `.xlsx`, образец пользователя `FunctionalStructure_clean.xlsx`: один лист, строка заголовков «Подразделение 1-го уровня» … «Подразделение 4-го уровня», «ФИО», «Должность», «Юридическое лицо»; одна строка — одна позиция штатной структуры. Иерархия задаётся путём названий по колонкам уровней; «-» в колонке уровня — пропуск уровня (у строки 703 уровень 2 «-», уровень 3 заполнен); строка без ФИО и без должности объявляет подразделение; строка с должностью и без ФИО — незанятая позиция (в исходной выгрузке такие строки тоже есть); строка с ФИО — сотрудник.
  - Сотрудник сопоставляется с уже заведённым по ФИО.
  - Предпросмотр изменений до применения.
  - Отдельный шаг мастера: полный список сущностей системы, не найденных в загруженном файле; пользователь принимает решение по каждой, по умолчанию «деактивировать».
  - Новый мастер, доступный с рабочего стола, проводит весь процесс: загрузка файла → распознавание → предпросмотр → решения по отсутствующим → применение к оргструктуре.
- Constraints:
  - Всё или ничего: файл, распознанный некорректно, отклоняется целиком с описанием ошибки (что не найдено, где); частичного применения нет.
  - Шаблон файла для скачивания не нужен; объём файла не ограничивается; учётные записи импорт не создаёт и не приглашает.
  - Существующие правила оргструктуры (`docs/product/requirements/org-structure.html`) действуют и для импорта: строгое дерево, руководитель — работающий сотрудник своего подразделения, должность сотрудника — из справочника и перечня подразделения или предков, деактивация подразделения только без активных дочерних и работающих сотрудников, увольнение каскадно (руководство, закрепления HR, блокировка учётной записи), запрет на увольнение последнего администратора.
  - Наблюдения по образцу (1 184 строки данных): 343 подразделения глубиной 1–4, 24 корня; 699 разных должностей; 87 строк с ФИО (все из трёх слов, дублей нет), 961 строка с должностью без ФИО, 136 строк только с подразделением; одноимённые подразделения у разных родителей («Секретариат Генерального директора» — у двух); 55 ячеек с лишними пробелами по краям или внутри; колонка «Юридическое лицо» (5 значений) в модели системы не хранится; руководитель подразделения в файле явно не указан.
- Refined (stage c, ответы пользователя 2026-10-26):
  - Распознавание: «-» в колонке уровня — пропуск уровня, подразделение крепится к ближайшему заполненному уровню выше; подразделение опознаётся по пути названий от корня; значения ячеек нормализуются (крайние и повторные пробелы); переименованное или перенесённое подразделение для импорта — новое, а прежнее попадает в список отсутствующих (принято пользователем).
  - Строка с должностью без ФИО — незанятая позиция: должность попадает в перечень допустимых должностей подразделения; файл целиком задаёт эти перечни. Должность, которой нет в справочнике, создаётся; неактивная возвращается в работу.
  - Руководителей импорт не назначает и не меняет; перевод и увольнение руководителя снимают его по действующим правилам.
  - Юридическое лицо — атрибут назначения сотрудника, а не узел дерева: дерево остаётся функциональным (корни — подразделения 1-го уровня); у одного назначения может быть несколько юрлиц, они показываются на карточке в разделе «Оргструктура».
  - Совмещение: одно ФИО может встречаться в файле несколько раз — это один сотрудник на нескольких должностях. Модель сотрудника меняется: одно основное назначение (подразделение и должность; его читают все действующие правила — «Моё место», матрицы, роли согласования, руководитель, рабочий стол) и дополнительные назначения-совмещения, видимые в оргструктуре. В импорте основное — у нового сотрудника первая его строка в файле, у заведённого — текущее основное, если оно есть в файле; вручную основное меняется. Тёзки с одинаковым ФИО сливаются в одного сотрудника (принятое ограничение ключа ФИО).
  - Сопоставление ФИО — без учёта регистра и лишних пробелов, «ё» равна «е». Строка с ФИО без должности — ошибка распознавания. Найденный сотрудник с другим подразделением или должностью — перевод; уволенный в системе, но присутствующий в файле — возврат на работу; всё видно в предпросмотре.
  - Отсутствующие в файле: подразделения — «деактивировать» (по умолчанию) или «оставить»; сотрудники — «уволить» (по умолчанию) или «оставить»; удаление через импорт не предлагается; должности справочника и строки перечней в список не входят. Увольнение через импорт каскадно, по действующему правилу (руководство, закрепления HR, блокировка учётной записи) — принято пользователем.
  - Права: HR, как и глобальный администратор, проводит импорт и вручную меняет всю оргструктуру — подразделения, сотрудников, перечни должностей.
  - Мастер: вход с рабочего стола у администратора и HR; незавершённый импорт не хранится, выход из мастера отменяет импорт.
- Success criteria: администратор или HR с рабочего стола проходит мастер от загрузки файла до применения, принимает решение по каждой отсутствующей в файле сущности, и оргструктура системы после применения совпадает с файлом с учётом этих решений.

## Findings
- Импорт строится как «предпросмотр → проверка без записи → применение»: предпросмотр и применение используют один разборщик, одни правила и одну логику сопоставления; применение ссылается на пакет, созданный при предпросмотре, а не на повторно загруженные данные, поэтому применяется именно то, что показано; пакет проходит состояния «проверен → применяется → применён» один раз; изменение файла создаёт новый пакет. Для данных, которые должны оставаться согласованными, рекомендуется режим «всё или ничего». — source: https://appmaster.io/blog/safe-bulk-imports-preview-validate-commit
- Предпросмотр показывает, как файл распознан (заголовки, первые строки, служебные строки), до любой записи; итог импорта — сводка, а не молчаливое «готово»; ошибки привязываются к строкам файла. — source: https://blog.csvbox.io/spreadsheet-import-ux/ ; https://www.saasui.design/blog/saas-data-import-mapping-ux-patterns
- В системах сверки штата с кадровой выгрузкой результат раскладывается по группам: новые, изменённые, переведённые, отсутствующие в файле («к увольнению») и строки с ошибками; по каждой отсутствующей записи администратор явно решает — удалить или сделать неактивной; строки с ошибками исправляются в исходном файле и сверка запускается заново. — source: https://help.unifocus.com/help/Content/Reconciling-employees.htm
- Отсутствие человека в выгрузке обычно не деактивирует его автоматически: нужно явное решение человека или дата окончания в источнике. Сопоставление по нестабильному ключу ведёт к дублям и «потерянным» записям; при массовом «отсутствии» стоит заподозрить сбой выгрузки, а не уход людей. — source: https://support.cultureamp.com/en/articles/9322170-how-to-sync-hris-data-from-deel-via-the-merge-api ; https://www.culturemonkey.io/kb/hris-sync-issues/
- Для «всё или ничего» данные сначала разбираются и проверяются отдельно, а в рабочие таблицы попадают одним контролируемым шагом в одной транзакции; одна длинная транзакция держит блокировки, поэтому годится для импортов умеренного размера. — source: https://blink.hexdocs.pm/bulk_imports.html
- Загрузка файлов: допускать только нужное расширение, не доверять Content-Type, проверять сигнатуру; ограничение размера применяется к распакованному содержимому (XLSX — ZIP-контейнер: ZIP- и XML-бомбы), библиотеки разбора держать обновлёнными и настроенными безопасно, имя файла на сервере не использовать. — source: https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html
- Образец пользователя (разбор оркестратором, 1 184 строки): ключ сотрудника — ФИО, в образце дублей нет, но однофамильцы-тёзки в организации на 10 000 человек вероятны, а «ё/е», регистр и лишние пробелы (55 ячеек) дают ложные расхождения без нормализации; ключ подразделения — путь названий от корня, потому что названия повторяются у разных родителей; руководитель подразделения в файле не указан. — source: D:\Downloads\FunctionalStructure_clean.xlsx

## Approaches
- **Пакет импорта на сервере**: загрузка создаёт на сервере пакет импорта; сервер распознаёт файл, хранит распознанную структуру и вычисленный план изменений; шаги мастера читают пакет и сохраняют решения пользователя по отсутствующим сущностям; применение выполняется по идентификатору пакета одной транзакцией с повторной проверкой, что оргструктура не изменилась после предпросмотра; pros: применяется ровно то, что показано; мастер можно прервать и продолжить, в том числе с рабочего стола (незавершённый импорт — пункт стола); один пакет — одна история импорта для журнала; файл любого объёма разбирается один раз; cons: новое хранилище пакетов со своим жизненным циклом (срок жизни, отмена, один активный импорт одновременно).
- **Без состояния, файл отправляется заново**: каждый шаг мастера отправляет на сервер файл (и накопленные решения), сервер каждый раз разбирает его и пересчитывает план; применение получает файл, решения и отпечаток состояния оргструктуры на момент предпросмотра; pros: нет нового хранилища и жизненного цикла; cons: решения живут только в браузере и теряются при перезагрузке — мастер нельзя продолжить с рабочего стола; повторная передача и разбор файла на каждом шаге; совпадение применённого с показанным держится на сверке отпечатков файла и данных.
- **Распознавание в браузере**: браузер разбирает xlsx и отправляет на сервер нормализованную структуру; сервер сверяет и применяет; pros: сервер не разбирает двоичный файл; cons: правила распознавания расходятся между клиентом и сервером, сервер всё равно проверяет присланную структуру заново, во фронтенд добавляется крупная зависимость, ошибки распознавания пользователь видит только в браузере.
- Recommended: Пакет импорта на сервере — единственный вариант, при котором применяется ровно показанное, а мастер, доступный с рабочего стола, можно прервать и продолжить; цена — хранилище пакетов, оправданная многошаговым процессом с решениями по каждой отсутствующей сущности. После stage (c) незавершённый импорт не хранится, главный плюс пакета ушёл, и рекомендация сменилась на «Без состояния»: совпадение применённого с показанным держит сверка отпечатка плана.
- Chosen: Без состояния, файл отправляется заново — выбор пользователя 2026-10-26 на гейте approach choice (по рекомендации после stage c).
