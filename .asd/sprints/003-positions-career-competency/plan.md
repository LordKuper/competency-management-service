# Plan

## Overview

Спринт `lite`: критерии — `sprint.md` AC-1…AC-21 (AC-16 с поправкой 2026-10-09); контекст — `audit.md`, его решения C-1…C-3 и A-1…A-19 и решения plan 2026-10-09 (`decisions-log.md`): новая подсистема `career-framework` утверждена, строки-связи удаляются физически, перечень должностей и HR — модальные окна из меню карточки подразделения, тексты интерфейса утверждаются в этом плане (раздел «Тексты интерфейса»).

Порядок работ (волны — `## Dependencies`):
1. Правила проекта из ретро (Task 1) и справочник должностей целиком — backend, миграция данных, контракт 3.0.0 и экраны (Task 2). Справочник — одна Task, потому что смена входа `/api/v1/employees` ломает типы web: `check:api` и `typecheck` должны оставаться чистыми после каждой волны.
2. Порты для карьерной модели в `org-structure` и `user-management` (Task 3).
3. Каркас модуля `Competency.CareerFramework`: закрепление HR и роли процесса текущего пользователя (Task 4).
4. Справочники карьерной модели backend (Task 5) параллельно с frontend «HR подразделения» и каркасом раздела «Карьерная модель» (Task 6).
5. Матрицы и согласование backend (Task 7) параллельно с frontend справочников (Task 8).
6. Frontend матриц и согласования (Task 9).

Решения, обязательные для всех Task:
- Именование: «должность» — запись справочника `org-structure` (`/api/v1/positions`, `Position`); «карьерный уровень» — уровень трека (`/api/v1/career/levels`, `CareerLevel`). Все endpoints карьерной модели — под `/api/v1/career/…`.
- Модуль `Competency.CareerFramework` ссылается на `Competency.Platform`, `Competency.OrgStructure`, `Competency.UserManagement` (обратных ссылок нет); наружу — только `AddCareerFrameworkModule`, `MapCareerFrameworkEndpoints`. Данные других модулей — только через порты `IEmployeeDirectory` (расширяется в Task 3) и `IUserDirectory` (новый, Task 3); межмодульные FK на `org_units` и `users` — по имени сущности, как `UserManagementEntityConfiguration.cs:59`.
- «Руководитель подразделения» = пользователь, чья учётная запись не заблокирована, зарегистрирована и привязана к работающему сотруднику, который указан руководителем подразделения (AC-7, A-4); вычисляется в момент действия (A-6a). Подразделений под руководством сотрудника может быть несколько (R-9). «Ответственный HR» подразделения = HR, закреплённый за ним или за ближайшим вышестоящим подразделением, если его учётная запись не заблокирована и зарегистрирована; иначе ответственного HR нет (A-5).
- Строки-связи — должность в перечне подразделения и закрепление HR — удаляются физически, событие пишется в журнал; сущности по-прежнему только деактивируются.
- Записи справочников карьерной модели (направление, трек, карьерный уровень, категория, компетенция, шкала) несут `owner_org_unit_id` (null — общая) и статус `Draft` / `Active` / `Inactive`; видимость и права — AC-9 с уточнениями C-2, C-3; уникальность названий — среди нечерновых записей и черновиков своего подразделения в пределах родителя, повторно при утверждении черновика (A-13).
- Версия матрицы хранит содержимое одним `jsonb`-документом на строке версии (уровни, компетенции, блоки, требования, коэффициенты, пороги); If-Match — по `Version` строки версии. Варианты (автор / согласующий) — копии документа; правки согласующего показываются разницей двух документов. При публикации в версию пишется снимок названий и полей уровней, компетенций и шкалы на момент публикации (A-19); опубликованная версия читается только из снимка. Диапазон оклада в снимок не входит (R-8).
- Матрица: одна на пару «подразделение — трек»; версия «в работе» = `Draft`, `OnReview`, `Returned`; `Approved` фиксируется в истории и сразу сменяется `Published` (AC-15). Проверка полноты (AC-15) выполняется при отправке, при возврате с правками и при принятии правок; там же проверяется, что записи версии действующие или черновики подразделения матрицы, а шкала не изменилась.
- Маршрут (AC-16): шаг 1 — руководитель ближайшего вышестоящего подразделения с руководителем-пользователем (нет — шаг пропускается, проверка в момент действия, A-6b); шаг 2 — ответственный HR (нет — отправка 409 с понятной ошибкой; HR = автор — шаг засчитывается сразу; HR = согласующий шага 1 — согласует оба шага отдельно, A-7). «Принять правки без доработки» доступно только при возврате с правками (A-8). Согласование HR делает действующими черновые записи, которые использует версия.
- Доступ: недоступное для чтения — 404, изменение видимого без прав — 403 (A-15). Диапазон оклада — только ответственному HR и глобальному администратору (для общих уровней — только администратору), во всех проекциях, вариантах, разницах и истории (R-8).
- Миграции — в общей линии `src/Competency.Platform/Migrations/`, по одной на Task, генерируются `ef-migration-add`, порядок SQL переноса данных правится вручную (R-1); начальные данные (категории §6.1, базовая шкала §6.3) — фиксированные Guid, без событий журнала.
- Ответы — общие типы `Competency.Platform` (`PageResponse<T>`, `Rejection`, пределы страниц, экранирование LIKE); нарушения уникальности — явный ответ с полем, а не общий 409.
- Документ OpenAPI — `info.version` `3.0.0` (Task 2), путь `/api/v1` прежний; каждая Task с изменением API перегенерирует `openapi/openapi.json` и `web/src/api/schema.d.ts` (`gen-api`), `check:api` чист.

Порядок блокировок (правило `custom-coding-rules.md` «Multi-row invariant locking»; глобальный порядок: дерево (5001001) → справочники карьерной модели (новый ключ 5003001) → строка матрицы → строки активных администраторов → строка учётной записи):
- Справочник должностей, перечни подразделений, закрепление HR, сохранение сотрудника с проверкой должности — блокировка дерева эксклюзивно, первой (как изменения оргструктуры; R-4).
- Создание, изменение, утверждение и деактивация записей справочников карьерной модели — блокировка дерева в разделяемом режиме (`pg_advisory_xact_lock_shared(5001001)`, права HR и руководителя зависят от дерева), затем `pg_advisory_xact_lock(5003001)` (уникальность названий с учётом черновиков, A-13).
- Переходы статуса версии матрицы (отправка, согласование, возврат, решения автора, публикация, создание версии) — дерево разделяемо, затем 5003001 (согласование HR утверждает черновые записи), затем строка матрицы `FOR UPDATE`; публикация архивирует прежнюю версию отдельным `SaveChanges` в той же транзакции (R-7). Правки содержимого `Draft` — If-Match без advisory-блокировок.
- Существующие изменения дерева, сотрудников и учётных записей (смена руководителя, увольнение, блокировка учётной записи) уже берут дерево эксклюзивно первыми — поэтому права, проверенные под разделяемой блокировкой, не меняются до конца транзакции (R-6).
- Инварианты под защитой: одна опубликованная и одна версия в работе на матрицу, одна матрица на пару «подразделение — трек», один HR на подразделение — частичные уникальные индексы как страховка (R-7); у каждого — детерминированный тест гонки в impl-test.
