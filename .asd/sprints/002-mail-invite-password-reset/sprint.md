# Sprint 002-mail-invite-password-reset

## Goal

Подключить отправку почты через SMTP-сервер и перевести управление паролями в подсистеме `user-management` на ссылки по e-mail:

- работа с почтовым сервером — отправка писем через SMTP (MailKit из `docs/architecture/stack.html`), параметры сервера из конфигурации окружения, локальный почтовый перехватчик для разработки;
- регистрация по приглашению — администратор создаёт учётную запись без пароля, пользователь получает письмо с одноразовой ссылкой и сам задаёт пароль;
- «Не помню пароль» — пользователь сам запрашивает ссылку для сброса пароля на экране входа;
- администратор больше не задаёт пароль другим пользователям — ни при создании, ни при сбросе; вместо сброса он отправляет пользователю ссылку для сброса;
- задачи из ретроспективы спринта 001 (P-1, P-3, P-4, P-5) — правила проекта и вынос общих вспомогательных типов в `Competency.Platform`.

Принятые решения и допущения (источник — ответы пользователя на scope 2026-10-08; допущения проверяются на scope gate):
- Регистрация только по приглашению администратора; открытой самостоятельной регистрации нет (решение пользователя 2026-10-08).
- Вместо «Сбросить пароль» у администратора — «Отправить ссылку для сброса пароля» (то же письмо, что при «Не помню пароль»; пароль при этом не меняется) и «Отправить приглашение повторно» для учётной записи, не завершившей регистрацию (решение пользователя 2026-10-08).
- Существующие учётные записи сохраняют свои пароли; повторная регистрация им не нужна.
- Первый глобальный администратор по-прежнему создаётся из секретов окружения с паролем (`Bootstrap__AdminEmail`, `Bootstrap__AdminPassword`): развёртывание не зависит от доступности почты.
- Смена собственного пароля остаётся без изменений.
- Ссылки в письмах строятся от настроенного публичного адреса приложения, а не от заголовков запроса.
- Срок действия ссылки: приглашение — 72 часа, сброс пароля — 1 час (значения по умолчанию, задаются конфигурацией).
- Для локальной разработки письма перехватывает почтовый перехватчик в dev-стеке (Docker Compose, профиль F5 «Everything»), реальная почта не отправляется; конкретный инструмент и версия выбираются на audit/plan.

## Acceptance

Почта:
- AC-1: Приложение отправляет письма через SMTP-сервер (MailKit 4.18.1 по `stack.html`); адрес, порт, режим TLS, необязательная аутентификация и адрес отправителя задаются конфигурацией окружения, учётные данные SMTP — только секретом (Kubernetes Secret / `launchSettings.json` локально), не в образе и не в репозитории; содержимое писем, токены и учётные данные SMTP не попадают в логи; отказ SMTP-сервера не приводит к потере данных и не роняет запрос с необработанной ошибкой; письмо можно отправить повторно. Понятное сообщение об отказе видит администратор, выполнивший действие (письма по его действиям отправляются сразу после фиксации, с коротким таймаутом); анонимный «Не помню пароль» всегда получает один и тот же нейтральный ответ, письмо по нему отправляется в фоне, а отказ фиксируется только в журнале и логе (решение пользователя 2026-10-08, audit Q-1, Q-2).
- AC-2: Письма на русском языке, с темой и текстом, содержащим ссылку на экран приложения; ссылка строится от настроенного публичного адреса приложения (`App:PublicBaseUrl` или аналог, имя выбирается в plan), заголовок `Host` запроса на неё не влияет.
- AC-3: Локальная разработка: dev-стек (`deploy/dev/docker-compose.yml`, профиль F5 «Everything» из спринта 001) поднимает почтовый перехватчик с веб-интерфейсом просмотра писем; `launchSettings.json` направляет почту в него; Kubernetes-манифесты и `deploy/secret.template.yaml` получают параметры SMTP и публичного адреса.

- AC-17: Значения SMTP по умолчанию для разработки (Mailpit) и публичный адрес хранятся в `src/Competency.Api/appsettings.Development.json`, а не в переменных окружения `launchSettings.json`; разработчик может один раз задать собственные параметры SMTP (например, песочницу Mailtrap) через .NET User Secrets вне репозитория — они переопределяют значения по умолчанию при каждом запуске в окружении `Development` (F5 в Visual Studio, `dotnet run`) без правки файлов проекта; возврат к Mailpit — очисткой user secrets; `deploy/dev/README.md` описывает команды (поправка скоупа, решение пользователя 2026-10-08).

Регистрация по приглашению:
- AC-4: Создание учётной записи администратором (`/api/v1/users`) не принимает пароль: e-mail, роль, привязка к сотруднику; учётная запись создаётся в состоянии «приглашён» (войти нельзя), на её e-mail уходит письмо-приглашение с одноразовой ссылкой ограниченного срока действия.
- AC-5: По ссылке из приглашения пользователь открывает экран задания пароля (без входа в систему), задаёт пароль по действующей политике (`Identity:Password`) и после этого может войти по e-mail и паролю; ссылка одноразовая, истекает по сроку, недействительна после повторной отправки приглашения, смены e-mail учётной записи или её блокировки; недействительная или истёкшая ссылка даёт понятное сообщение без раскрытия причины, по которой учётная запись недоступна.
- AC-6: Администратор может отправить приглашение повторно учётной записи в состоянии «приглашён» (предыдущая ссылка становится недействительной); в списке пользователей состояние «приглашён» видно и доступно для фильтрации.

«Не помню пароль»:
- AC-7: На экране входа есть ссылка «Не помню пароль», ведущая на экран ввода e-mail; запрос (анонимный API-метод) возвращает один и тот же ответ независимо от того, существует ли учётная запись, заблокирована ли она или находится в состоянии «приглашён» (нет перечисления учётных записей), и ограничен по частоте (по адресу и по e-mail); письмо со ссылкой сброса уходит только активной зарегистрированной учётной записи.
- AC-8: По ссылке сброса пользователь задаёт новый пароль по действующей политике; ссылка одноразовая, истекает по сроку, недействительна после смены пароля любым способом и после выдачи новой ссылки; успешный сброс обрывает все действующие сессии учётной записи и снимает блокировку за перебор пароля (lockout), но не снимает блокировку администратором и не позволяет войти уволенному сотруднику.

Пароли других пользователей:
- AC-9: Администратор не может задать или сбросить пароль другой учётной записи: метод `POST /api/v1/users/{id}/reset-password` с заданием пароля и поле пароля при создании удаляются (изменение публичного контракта по `backward_compat: migration` — с описанием перехода в документации подсистемы и `deploy/README.md`; версия документа OpenAPI `info.version` поднимается до `2.0.0`, путь `/api/v1` не меняется — решение пользователя 2026-10-08, audit Q-3); вместо них — действие «Отправить ссылку для сброса пароля» для активной зарегистрированной учётной записи (пароль не меняется, письмо то же, что в AC-7/AC-8).
- AC-10: Журнал `audit` фиксирует: отправку и повторную отправку приглашения, завершение регистрации, запрос сброса пароля для существующей учётной записи (включая инициатора — сам пользователь или администратор), успешный сброс, неудачу отправки письма — без токенов, ссылок, паролей и хэшей.

Frontend:
- AC-11: Экраны «Не помню пароль», «Задание пароля» (по ссылке приглашения) и «Новый пароль» (по ссылке сброса) — без входа в систему, в стиле экрана входа и `docs/ux/DESIGN.md` на уровне токенов, адаптивно desktop/tablet; в управлении пользователями: модальное окно создания без поля пароля, состояние «приглашён» в списке, в меню действий строки — «Отправить приглашение повторно» (для приглашённых) и «Отправить ссылку для сброса пароля» (для активных зарегистрированных) вместо «Сбросить пароль»; после действия пользователь видит, что письмо отправлено или не отправлено.

Задачи из ретроспективы спринта 001 (включены пользователем на scope gate 2026-10-08; P-2 отложена, AC-13 не используется):
- AC-12 (`001-project-init-org-structure#P-1`): раздел «Verification depth in impl» в `.asd/project/custom-coding-rules.md` заменён: отдельного полного цикла ручных проверок перед impl-test нет; проверку ведёт impl-test автотестами (интеграционные тесты API на настоящей PostgreSQL через существующий хост тестов, тесты web на vitest с подменой API); impl — на минимальных проверках; замер производительности — только для Task с объявленным perf-риском, на переиспользуемом скрипте наполнения 10 000+ сотрудников, который создаёт первая Task с объявленным perf-риском (в этом спринте скрипт не создаётся — решение пользователя 2026-10-08, audit Q-4); Playwright и e2e не используются.
- AC-14 (`#P-3`): `.asd/project/custom-coding-rules.md` содержит правило: каждое правило, охраняющее инвариант через несколько строк, объявляет в plan свою блокировку и её место в общем порядке блокировок и получает детерминированный тест гонки в impl-test.
- AC-15 (`#P-4`): `.asd/project/custom-common-rules.md` содержит правило: агенты не выполняют разрушающие команды Docker (`down -v`, `volume rm`, `volume prune`) для dev-стека пользователя и томов с фиксированным именем; временные прогоны используют только собственные именованные тома и удаляют их по точному имени.
- AC-16 (`#P-5`): `.asd/project/custom-coding-rules.md` содержит правило о размещении общих вспомогательных типов в `Competency.Platform`, и текущие копии вынесены туда: ответ постраничного списка (`PageResponse` в `Competency.OrgStructure` и `Competency.UserManagement`, `AuditPageResponse`), отказы с ProblemDetails (`Rejections` в двух модулях), экранирование LIKE, пределы страниц (`MaxPageSize` в трёх модулях) — без изменения публичного контракта API (`openapi.json` не меняется, кроме неизбежных имён схем, если они совпадают — проверяется в plan).
