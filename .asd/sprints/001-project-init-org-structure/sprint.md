# Sprint 001-project-init-org-structure

## Goal

Инициализировать проект по современным стандартам на стеке из `docs/architecture/stack.html` (точные версии, без отступлений) и реализовать три первые подсистемы, поставляемые вместе, потому что пользователи привязываются к организационно-штатной структуре, а все изменения журналируются:

- `org-structure` — управление организационно-штатной структурой (`docs/Постановка.md` §4): дерево подразделений и сотрудники с подразделением и должностью;
- `user-management` — управление пользователями (учётные записи, роли, привязка к сотрудникам); глобальный администратор существует без привязки к оргструктуре;
- `audit` — журналирование: append-only журнал действий (`docs/Постановка.md` §29), включая события входа.

Все три подсистемы регистрируются в `docs/architecture/subsystems.md`.

Принятые решения и допущения (источник — ответы пользователя на scope gate и audit gate 2026-10-05):
- Пользователь (учётная запись) и сотрудник (запись оргструктуры) — разные сущности (`docs/Постановка.md` §39): учётная запись ссылается на сотрудника 1:1; у глобального администратора ссылки нет, у сотрудника может не быть учётной записи.
- Модель доступа: две роли — глобальный администратор (без привязки, управляет пользователями, оргструктурой и читает журнал) и пользователь (привязан к сотруднику). Роли §8, scope-based access и row-level security — вне спринта.
- Подразделения не типизируются; иерархия — строгое дерево, один родитель, без циклов.
- «Штатная» часть сведена к двум полям сотрудника: подразделение и должность (текст). Штатных единиц, ставок и назначений с историей нет; справочник должностей и карьерные треки — Career Framework, вне спринта.
- Статус сотрудника: работает / не работает (допущение, проверяется на audit gate); «не работает» блокирует вход привязанного пользователя.
- Пользователь (не администратор) видит дерево подразделений и для сотрудников — ФИО, e-mail (его учётной записи, если она есть), подразделение, должность; статус видит только администратор. Табельного номера в системе нет (решение пользователя 2026-10-06).
- Схема БД применяется приложением при старте (`MigrateAsync`); учётка БД приложения имеет DDL-права.
- Аутентификация локальная (ASP.NET Core Identity, cookie), корпоративный IdP не используется (`stack.html`, Q2).
- Физическое удаление записей не предоставляется: блокировка пользователя, деактивация подразделения и сотрудника.

## Acceptance

Платформа (каркас):
- AC-1: Репозиторий содержит каркас: backend на C# 14 / .NET 10 (ASP.NET Core Minimal API, модульный монолит с явными границами подсистем), frontend на React 19 + TypeScript 6.0.2 strict + Vite + antd (ru_RU), тест-проекты backend и frontend; версии пакетов закреплены ровно по `stack.html`, лицензии зависимостей допустимы.
- AC-2: `dotnet build` и сборка/линт frontend (Biome) проходят без ошибок и предупреждений; сборка backend не требует доступа к PostgreSQL и генерирует `openapi.json`, из которого строятся TypeScript-типы клиента (openapi-fetch); DTO на frontend руками не пишутся.
- AC-3: Данные хранятся в PostgreSQL 18.6 через EF Core с миграциями; приложение стартует, применяет схему, отдаёт health-пробы liveness/readiness (readiness проверяет доступность БД); строка подключения и секреты берутся из конфигурации окружения, не из репозитория.
- AC-4: Есть воспроизводимая упаковка: multi-stage Dockerfile (Node → SPA, .NET SDK → publish, runtime `aspnet:10.0.12-noble`, непривилегированный пользователь) и базовые Kubernetes-манифесты для workload'ов app и db с PVC, ConfigMap/Secret и пробами; формат манифестов выбирается в plan.
- AC-5: Сквозные механизмы платформы: JSON-логи в stdout без персональных данных и значений SQL-параметров; оптимистичная блокировка (`Version` + ETag/`If-Match`), конфликт возвращается явной ошибкой, а не молчаливой перезаписью; единый формат ошибок API; идентификаторы сущностей не последовательные.

Подсистема `user-management`:
- AC-6: Локальный вход по e-mail и паролю / выход (cookie-сессия, lockout при переборе пароля, хранение паролей только в виде хэшей, защита от CSRF); e-mail — обязательный уникальный (без учёта регистра) атрибут учётной записи, имени пользователя отдельно нет; начальный глобальный администратор создаётся из секретов окружения (e-mail и пароль при развёртывании) и не привязан к оргструктуре; неаутентифицированный запрос к API получает 401, недостаточные права — 403; все проверки прав выполняются на backend; на frontend есть экран входа.
- AC-7: Управление пользователями (`/api/v1/users`): создание (e-mail, пароль, роль, привязка к сотруднику), просмотр, поиск (по e-mail) и фильтрация, редактирование, блокировка/разблокировка, сброс пароля администратором, смена собственного пароля; роль — глобальный администратор или пользователь; нельзя заблокировать, понизить или иначе лишить роли последнего активного глобального администратора.
- AC-8: Привязка пользователя к сотруднику: пользователь с ролью «пользователь» обязан быть привязан к существующему сотруднику, один сотрудник — не более одной учётной записи; глобальный администратор привязки не имеет; привязка и отвязка журналируются; перевод сотрудника в «не работает» блокирует вход привязанного пользователя, в том числе действующую сессию.

Подсистема `org-structure`:
- AC-9: Подразделения: управление по `/api/v1/org-units`; иерархия — строгое дерево произвольной глубины, один родитель, без типов; поля — идентификатор, название, родитель, руководитель, статус активности (дат действия у подразделений нет — решение пользователя 2026-10-06); перенос в другое поддерево запрещает циклы, в том числе при конкурентных переносах; деактивация подразделения с активными дочерними подразделениями или активными сотрудниками отклоняется с понятной причиной.
- AC-10: Сотрудники (`/api/v1/employees`): фамилия, имя и отчество отдельными полями (отчество необязательно; отображаемое ФИО «Фамилия Имя Отчество» собирается автоматически и доступно в ответах как производное только для чтения), статус (работает / не работает), подразделение, должность (текст); табельного номера и e-mail у сотрудника нет (e-mail принадлежит учётной записи пользователя; в данных сотрудника отдаётся e-mail его учётной записи, если она есть); руководитель подразделения — сотрудник; перевод сотрудника в «не работает» при том, что он руководитель активного подразделения, отклоняется с понятной причиной.
- AC-11: Чтение структуры: дерево целиком и поддерево, путь до корня, поиск и фильтрация подразделений и сотрудников по названию/ФИО/должности и статусу (полнотекстовый `russian` + `pg_trgm`), сводка по подразделению с учётом потомков (число сотрудников); на тестовом наборе 10 000 сотрудников обычные операции укладываются в P95 < 2 с.

Подсистема `audit`:
- AC-15: Журнал `audit` append-only (запрет UPDATE/DELETE на уровне БД для учётки приложения) с полями из `docs/Постановка.md` §29 (timestamp, actor, role, action, entity_type, entity_id, old_value, new_value, reason, request_id); в журнал пишутся каждая мутация пользователей, подразделений и сотрудников, а также события входа (успешный, неуспешный, lockout) и выхода — без паролей, хэшей и значений-секретов; чтение журнала — только глобальному администратору через `/api/v1/audit` с фильтрами; пользовательского редактирования журнала нет.

Сквозные требования подсистем:
- AC-12: Прямой доступ по идентификатору без достаточных прав отклоняется на уровне API (защита от IDOR); пользователь с ролью «пользователь» видит только дерево подразделений и ФИО, e-mail, подразделение, должность сотрудников, а мутации и административные данные (статус, учётные записи, журнал) недоступны (403).
- AC-13: Frontend: экран входа; управление пользователями (список, карточка, привязка к сотруднику, блокировка, сброс пароля); иерархия оргструктуры карточками (AC-17); создание и правка сотрудников в модальном окне раздела «Оргструктура» (AC-17); просмотр журнала для администратора; адаптивность desktop/tablet; соответствие `docs/ux/DESIGN.md` на уровне токенов (`docs/ux/accessibility.html` покрывает только токены); при конфликте версий пользователь видит понятное сообщение и может перечитать данные.
- AC-14: Подсистемы `org-structure`, `user-management` и `audit` зарегистрированы в `docs/architecture/subsystems.md` с собственными `docs/architecture/<id>.md`; требования и UX подсистем попадают в `docs/product/requirements/` и `docs/ux/` на design-promote.

- AC-16: Решение открывается в Visual Studio (VS 2022 17.11+ / VS 2026), и профиль многопроектного запуска «Все сервисы» по F5 поднимает локальную БД PostgreSQL 18.6 (Docker Compose-проект, только БД), dev-сервер Vite (JavaScript-проект `.esproj`) и `Competency.Api` под отладчиком без самописных скриптов; строка подключения и данные первого администратора для локальной разработки лежат в `launchSettings.json`; сборка, тесты и Docker-образ не зависят от Visual Studio-проектов (`dotnet build`/`dotnet test` собирают backend без `.dcproj`/`.esproj`).

- AC-17: Раздел «Оргструктура» показывает иерархию карточками двух видов — подразделение и сотрудник: вертикальная вложенность со связями, внутри карточки подразделения сначала карточки дочерних подразделений, затем карточки сотрудников этого подразделения; карточка подразделения показывает одну и ту же информацию (название, статус, число дочерних подразделений, число сотрудников подразделения, руководитель) независимо от того, раскрыта она или свёрнута, и без отдельного запроса на каждую карточку; иерархия свёрнута по умолчанию, дочерние подразделения и сотрудники подгружаются при раскрытии (сотрудники — страницами, «Показать ещё»), так что раздел работает при 10 000+ сотрудников; создание, правка, перенос, деактивация подразделения и открытие/правка сотрудника доступны с самих карточек (для роли «пользователь» — только просмотр); поиск по названию подразделения раскрывает путь к найденным; правая панель деталей и отдельный компонент дерева убираются; адаптивность desktop/tablet; отдельной страницы «Сотрудники» нет: сотрудник открывается (просмотр, для администратора правка: ФИО, должность, подразделение, статус) в модальном окне с карточки; кнопка «Добавить сотрудника» есть на странице раздела и в карточке подразделения (подразделение подставляется); вместо «Добавить корневое подразделение» — «Добавить подразделение» с выбором родителя (родитель подставляется при добавлении из карточки подразделения, корневое — без родителя).

## Out of scope

- Типы подразделений, штатные единицы, ставки, назначения сотрудников с историей и датами, вакансии.
- Справочник должностей, профессиональные направления, карьерные треки (Career Framework).
- Роли из `docs/Постановка.md` §8 сверх двух принятых, роли с областью действия (scope-based access), row-level и field-level security.
- SSO/OIDC/SAML, интеграция с HRIS, корпоративным каталогом, SMTP-уведомления и сброс пароля по e-mail.
- Импорт и экспорт оргструктуры и пользователей (XLSX/CSV/PDF), массовые операции.
- Матрицы компетенций, волны повышения, заявки, оценки, комиссии, рейтинги, решения, обратная связь, апелляции, аналитика.
- Настройки процесса и набор профессиональных направлений на уровне подразделения (зависят от других подсистем).
- Производственный календарь, квартальные оценки; экспорт журнала и аналитика по журналу.
