# Sprint 001-project-init-org-structure

## Goal

Инициализировать проект по современным стандартам на стеке из `docs/architecture/stack.html` (точные версии, без отступлений) и реализовать две первые подсистемы, поставляемые вместе, потому что пользователи привязываются к организационно-штатной структуре:

- `org-structure` — управление организационно-штатной структурой (`docs/Постановка.md` §4): иерархия организационных единиц, штатные единицы, сотрудники и их назначения;
- `user-management` — управление пользователями (учётные записи, роли, привязка к сотрудникам); глобальный администратор существует без привязки к оргструктуре.

Обе подсистемы регистрируются в `docs/architecture/subsystems.md`.

Принятые решения и допущения:
- Пользователь (учётная запись) и сотрудник (запись оргштатки) — разные сущности (`docs/Постановка.md` §39): учётная запись ссылается на сотрудника 1:1, ссылка необязательна (решение пользователя, scope gate 2026-10-05); у сотрудника может не быть учётной записи.
- Модель доступа: две роли — глобальный администратор (без привязки, управляет пользователями и оргструктурой) и пользователь (привязан к сотруднику, читает оргструктуру и свой профиль) (решение пользователя). Роли §8, scope-based access и row-level security — вне спринта; проверки прав на backend изолированы так, чтобы их можно было расширить без смены контрактов.
- «Штатная» часть = штатные единицы внутри организационной единицы и назначения сотрудников на них; справочник должностей и карьерные треки — подсистема Career Framework, вне спринта, штатная единица хранит наименование должности текстом.
- Аутентификация локальная (ASP.NET Core Identity, cookie), корпоративный IdP не используется (`stack.html`, Q2).

## Acceptance

Платформа (каркас):
- AC-1: Репозиторий содержит каркас: backend на C# 14 / .NET 10 (ASP.NET Core Minimal API, модульный монолит с явными границами подсистем), frontend на React 19 + TypeScript 6.0.2 strict + Vite + antd (ru_RU), тест-проекты backend и frontend; версии пакетов закреплены ровно по `stack.html`, лицензии зависимостей допустимы.
- AC-2: `dotnet build` и сборка/линт frontend (Biome) проходят без ошибок и предупреждений; сборка backend не требует доступа к PostgreSQL и генерирует `openapi.json`, из которого строятся TypeScript-типы клиента (openapi-fetch); DTO на frontend руками не пишутся.
- AC-3: Данные хранятся в PostgreSQL 18.6 через EF Core с миграциями; приложение стартует, применяет схему, отдаёт health-пробы liveness/readiness (readiness проверяет доступность БД); строка подключения и секреты берутся из конфигурации окружения, не из репозитория.
- AC-4: Есть воспроизводимая упаковка: multi-stage Dockerfile (Node → SPA, .NET SDK → publish, runtime `aspnet:10.0.12-noble`, непривилегированный пользователь) и базовые Kubernetes-манифесты для workload'ов app и db с PVC, ConfigMap/Secret и пробами; формат манифестов выбирается в design.
- AC-5: Сквозные механизмы платформы: JSON-логи в stdout без персональных данных и значений SQL-параметров; append-only аудит изменений через `SaveChangesInterceptor` с полями из `docs/Постановка.md` §29; оптимистичная блокировка (`Version` + ETag/`If-Match`), конфликт возвращается явной ошибкой, а не молчаливой перезаписью; единый формат ошибок API; идентификаторы сущностей не последовательные.

Подсистема `user-management`:
- AC-6: Локальный вход/выход (cookie-сессия, lockout при переборе пароля, хранение паролей только в виде хэшей); начальный глобальный администратор создаётся из секрета окружения и не привязан к оргструктуре; неаутентифицированный запрос к API получает 401, недостаточные права — 403; все проверки прав выполняются на backend; на frontend есть экран входа.
- AC-7: Управление пользователями (`/api/v1/users`): создание, просмотр, поиск и фильтрация, редактирование, блокировка/разблокировка, сброс пароля администратором, смена собственного пароля; роль — глобальный администратор или пользователь; нельзя удалить или заблокировать последнего активного глобального администратора.
- AC-8: Привязка пользователя к сотруднику: пользователь с ролью «пользователь» обязан быть привязан к существующему сотруднику, один сотрудник — не более одной учётной записи; глобальный администратор привязки не имеет; привязка и отвязка журналируются; блокировка/деактивация сотрудника блокирует вход привязанного пользователя.

Подсистема `org-structure`:
- AC-9: Организационные единицы: CRUD по `/api/v1/org-units` с иерархией произвольной глубины; типы единиц настраиваемы без изменения кода (по умолчанию Организация, Направление, Блок, Команда); поля — идентификатор, название, тип, родитель, руководитель, статус активности, даты действия; перенос в другое поддерево запрещает циклы; деактивация единицы с активными дочерними единицами или занятыми штатными единицами отклоняется с понятной причиной.
- AC-10: Сотрудники и штатные единицы: справочник сотрудников (ФИО, табельный номер, рабочий e-mail, статус занятости), штатные единицы организационной единицы (наименование должности, ставка, даты действия, статус «вакантна/занята/закрыта») и назначения сотрудников на штатные единицы с историей (даты начала и окончания); суммарная ставка сотрудника на одну дату не превышает допустимую; руководитель единицы — сотрудник.
- AC-11: Чтение структуры: дерево целиком и поддерево, путь до корня, поиск и фильтрация единиц/сотрудников по названию и статусу (полнотекстовый `russian` + `pg_trgm`), сводка по единице с учётом потомков (штатных / занятых / вакантных единиц); на тестовом наборе 10 000 сотрудников обычные операции укладываются в P95 < 2 с.

Сквозные требования подсистем:
- AC-12: Каждая мутация пользователей и оргструктуры попадает в audit log (актор, роль, действие, сущность, старое/новое значение, `request_id`); прямой доступ по ID без достаточных прав отклоняется на уровне API (защита от IDOR).
- AC-13: Frontend: экран входа; управление пользователями (список, карточка, привязка к сотруднику, блокировка, сброс пароля); дерево оргструктуры, карточка единицы, список штатных единиц и назначений, управление сотрудниками; адаптивность desktop/tablet; соответствие `docs/ux/DESIGN.md` и `docs/ux/accessibility.html`; при конфликте версий пользователь видит понятное сообщение и может перечитать данные.
- AC-14: Подсистемы `org-structure` и `user-management` зарегистрированы в `docs/architecture/subsystems.md` с собственными `docs/architecture/<id>.md`; требования и UX подсистем попадают в `docs/product/requirements/` и `docs/ux/` на design-promote.

## Out of scope

- Справочник должностей, профессиональные направления, карьерные треки (Career Framework).
- Роли из `docs/Постановка.md` §8 сверх двух принятых, роли с областью действия (scope-based access), row-level и field-level security.
- SSO/OIDC/SAML, интеграция с HRIS, корпоративным каталогом, SMTP-уведомления и сброс пароля по e-mail.
- Импорт и экспорт оргструктуры и пользователей (XLSX/CSV/PDF), массовые операции.
- Матрицы компетенций, волны повышения, заявки, оценки, комиссии, рейтинги, решения, обратная связь, апелляции, аналитика.
- Настройки процесса и набор профессиональных направлений на уровне организационной единицы (зависят от других подсистем).
- Производственный календарь, квартальные оценки.
