# Sprint 004-role-desktop-user-journeys

## Goal

Нужно добавить новый слой пользовательского пути: рабочий стол, который отражает для каждой роли действия, которые ожидает от нее система, а также предлагает основные пользовательские сценарии взаимодействия с системой. По сути, система посредством рабочего стола должна "вести за ручку" пользователя, чтобы он закрыл все свои задачи и потребности. При этом он должен работать не с набором табличных представлений по сущностям, а интерфейсами, сшитыми под конкретный пользовательский путь.

Уточнённо (ответы пользователя на scope 2026-10-12):

- рабочий стол — домашняя страница и первый пункт меню; сценарии ведут пользователя по шагам в собственных экранах; нынешние табличные разделы остаются вторичным доступом для точечной правки;
- рабочий стол есть у всех ролей: руководитель подразделения, HR, глобальный администратор, сотрудник (пользователь без роли процесса); у пользователя с несколькими ролями — объединённый стол;
- список ожидаемых действий и сценариев предлагает оркестратор (ниже), детали шагов — PRD и UX-спецификация;
- о новых ожидаемых действиях система напоминает счётчиком в шапке и письмом.

Допущения (проверяются на scope gate):

- Ожидаемые действия вычисляются из текущего состояния данных в момент запроса, как роли процесса (`career-framework.md`), — отдельного хранилища задач, их назначения и закрытия вручную нет; действие исчезает, как только выполнено или перестало относиться к пользователю (сменился руководитель, снято закрепление HR, заблокирована учётная запись).
- Сценарии используют существующие правила и права подсистем: новых прав и ролей спринт не вводит, сервер проверяет права при каждом действии, как сейчас.
- Где живёт агрегация ожидаемых действий (новая подсистема или модуль внутри существующей) — решение design; новая подсистема — отдельный hard gate.

## Acceptance

Рабочий стол:
- AC-1: После входа пользователь попадает на рабочий стол; «Рабочий стол» — первый пункт меню. Нынешние разделы («Оргструктура», «Карьерная модель», «Администрирование» с вложенными) остаются доступны из меню как вторичный доступ («Справочники» или иная группировка — решение UX); прямые адреса нынешних экранов продолжают работать.
- AC-2: Рабочий стол показывает два блока: «Ожидают вашего действия» — ожидаемые действия пользователя (AC-4…AC-7, AC-26…AC-29), сгруппированные по виду, каждое с объектом, причиной, давностью (только у действий, порождённых событием с датой: решение по версии, создание черновика, срок ссылки приглашения — решение пользователя на audit 2026-10-12, C-2) и переходом прямо в экран сценария, где действие выполняется; «Что можно сделать» — сценарии, доступные пользователю по его ролям (AC-8…AC-14, AC-31…AC-33). Пустой список действий показывает понятное состояние «Всё сделано». Пользователь с несколькими ролями видит объединённый стол без повторов одного действия (правила — AC-30).
- AC-3: В шапке на пункте «Рабочий стол» — счётчик ожидаемых действий пользователя; он обновляется после каждого действия в приложении и при переходе между экранами (без перезагрузки страницы); 0 не показывается.

Ожидаемые действия по ролям:
- AC-4: Руководитель подразделения: версия матрицы его подразделения возвращена с правками (он автор); черновик версии матрицы не отправлен на согласование; версия матрицы подчинённого подразделения ждёт его согласования (шаг 1); у подразделения, которым он руководит, нет ни одной опубликованной матрицы, хотя есть действующий трек его или вышестоящего подразделения.
- AC-5: HR: версия матрицы ждёт его согласования (шаг 2); черновые записи справочников ждут утверждения (те, что он может утвердить по AC-9 спринта 003); подразделение его ответственности без опубликованной матрицы (справочно, со ссылкой на руководителя).
- AC-6: Глобальный администратор: черновые записи справочников ждут утверждения; действующее подразделение без руководителя; подразделение без ответственного HR (ни своего, ни унаследованного закрепления); приглашение не принято (учётная запись приглашена, ссылка истекла или скоро истечёт) — действие выполняется прямо на столе кнопкой «Отправить приглашение повторно» с итогом отправки письма (решение пользователя на audit 2026-10-12, C-3).
- AC-7: Сотрудник (и любой пользователь, привязанный к сотруднику): ожидаемых действий в этом спринте нет, кроме тех, что дают ему роли AC-4…AC-6; блок действий показывает «Всё сделано».

Сценарии:
- AC-8: «Построить матрицу компетенций» (руководитель): пошаговый экран — выбор трека (своего или вышестоящего подразделения; нужного нет — создать черновой трек с уровнями, не уходя из сценария), подбор компетенций из каталога (нужной нет — создать черновую, не уходя из сценария), требования по паре «уровень — компетенция», формула рейтинга и пороги, проверка полноты с указанием, что исправить, отправка на согласование. Сценарий можно прервать и продолжить с того же шага (черновик сохраняется); правила и права — AC-9…AC-18 спринта 003, кроме одного изменения: версию матрицы можно строить и отправлять на согласование по черновому треку своего подразделения; публикация версии подчиняется AC-34 — черновой трек публикуется вместе с ней каскадом, если согласующий вправе его утвердить и трек проходит AC-25, иначе понятная ошибка с указанием трека (решение пользователя на audit 2026-10-12, C-1, уточнено поправкой скоупа 2026-10-12).
- AC-9: «Доработать возвращённую версию» (автор): один экран — комментарий и правки согласующего относительно варианта автора и три решения «Принять правки», «Принять и доработать», «Откатить правки» с объяснением последствий каждого.
- AC-10: «Согласовать версию» (согласующий шага 1 или 2): экран рассмотрения — что изменилось относительно действующей опубликованной версии (для первой версии — вся версия), результат проверки полноты, черновые записи справочников, которые станут действующими при публикации (для HR), решения «Согласовать» и «Вернуть с правками» (с правками и/или комментарием).
- AC-11: «Утвердить черновые записи» (HR, администратор): очередь черновиков с автором, подразделением и матрицами, которые их используют; утвердить или поправить и утвердить, не уходя из очереди; следующий черновик открывается сам.
- AC-12: «Подключить подразделение» (администратор): один экран для подразделения — руководитель, ответственный HR (свой или унаследованный), перечень должностей, учётные записи руководителя и HR — с отметкой, чего не хватает, и действием для каждого пробела на месте.
- AC-13: «Принять сотрудника» (администратор): один сценарий — карточка сотрудника (подразделение, должность с «Добавить должность»), затем по желанию учётная запись с приглашением, привязанная к нему; итог показывает, что создано и ушло ли письмо.
- AC-14: «Моё место в компании» (любой пользователь, привязанный к сотруднику): подразделение, должность, руководитель, ответственный HR и опубликованные матрицы своего подразделения (по трекам и уровням) с переходом к просмотру требований; по связи «должность — уровень» (AC-24) — треки, в которых есть его должность, его текущий уровень и следующие уровни трека с требованиями опубликованной матрицы; должность без трека — справочный пункт AC-29; пользователю без привязки — понятное объяснение (поправка скоупа 2026-10-12).

Напоминания:
- AC-15: Письмо уходит пользователю, когда у него появляется ожидаемое действие: версия матрицы пришла на его шаг согласования; его версия возвращена с правками; для ответственного HR подразделения автора — появилась черновая запись справочника на утверждение. В письме — что ждёт, от кого и ссылка прямо в экран сценария. Письмо не уходит заблокированной, приглашённой (без пароля) учётной записи и учётной записи уволенного сотрудника; отказ SMTP не откатывает действие, которое породило письмо, и фиксируется в журнале. Тексты писем — в UX-документе стола.

Сквозное:
- AC-16: Доступ: стол, счётчик и сценарии показывают пользователю только то, что он вправе видеть по правилам подсистем; сервер проверяет права при каждом действии сценария, как сейчас; данные стола одного пользователя другому недоступны (403/404 по правилам подсистем).
- AC-17: Экраны в стиле `docs/ux/DESIGN.md`, адаптивно desktop/tablet.
- AC-18: Новый или изменённый публичный контракт API — по `backward_compat: migration`: существующие методы не ломаются; новые методы описаны в документации подсистемы и OpenAPI.

Связь должностей с треками и проверки целостности (поправка скоупа 2026-10-12, решения пользователя):
- AC-24: Связь «должность — карьерный уровень» (модель А): у каждого уровня трека — набор должностей справочника; одна должность в пределах трека связана не больше чем с одним уровнем, но может входить в треки разных подразделений и направлений. Уровню доступны действующие должности, доступные в подразделении трека или в любом его дочернем подразделении (тех, кто может строить матрицу по этому треку). Связи ведёт тот, кто может править трек (AC-9 спринта 003: руководитель — в черновом треке своего подразделения, ответственный HR и администратор — всегда), в форме трека и в сценарии AC-31; изменения — с `If-Match` и в журнале `audit`. Миграция связей не заполняет: у существующих треков связей нет. Деактивация должности и исключение её из перечня подразделения связь не снимают и не блокируются; уровень, у которого остались только неактивные должности, считается уровнем без должности.
- AC-25: Запреты: трек нельзя сделать действующим (утвердить черновой, создать сразу действующим, вернуть в работу), пока хоть у одного его уровня нет связанной должности; у уровня действующего трека нельзя снять последнюю должность; версию матрицы нельзя отправить на согласование, пока хоть у одного уровня её трека нет связанной действующей должности (входит в проверку полноты); версию матрицы нельзя опубликовать (согласование HR), пока хоть у одного уровня её трека нет связанной должности. Отказ — 409 с понятной ошибкой, перечисляющей уровни без должностей. Опубликованные до спринта матрицы и действующие треки остаются как есть, их пробелы видны на столе.
- AC-26: Проверки руководителя подразделения (по подразделениям, которыми руководит; «действие» — в счётчике, «справочно» — отдельной группой вне счётчика): должность из перечня подразделения не связана ни с одним уровнем действующего трека подразделения или вышестоящего — с числом сотрудников на ней (действие, если он может править подходящий трек, иначе справочно со ссылкой на ответственного HR); у трека подразделения нет связанных должностей (действие); у уровня трека подразделения нет связанной должности (действие); у трека нет уровней или один уровень (действие); опубликованная матрица не покрывает текущие уровни трека — уровни добавлены, удалены или переставлены после публикации (действие: новая версия матрицы через AC-8); опубликованная матрица опирается на неактивный трек, направление или компетенцию (действие: новая версия); компетенция изменилась после публикации матрицы (справочно); его черновые записи справочников ждут утверждения HR (справочно, с давностью); его версия на согласовании — у кого и на каком шаге (справочно, с давностью).
- AC-27: Проверки HR (по подразделениям ответственности): проверки связей AC-26 (должность без трека, трек без должностей, уровень без должности) — действие, HR правит треки сам; черновой трек без уровней или с уровнем без должности на утверждении — отметка «утверждать рано» в пункте утверждения, не отдельный пункт; подразделение без руководителя (справочно, со ссылкой на администратора); версия на шаге 1 дольше 7 дней (справочно, с давностью); неиспользуемые записи каталога — компетенция, шкала (не по умолчанию), категория вне любых версий матриц и компетенций, направление без треков (справочно, с переходом в AC-32).
- AC-28: Проверки глобального администратора: должность сотрудника вне перечня, доступного его подразделению; у подразделения есть сотрудники, но пустой перечень должностей; неактивная должность у работающих сотрудников (справочно); должность ни в одном перечне и без сотрудников (справочно); учётная запись роли «пользователь» без привязки к сотруднику; руководитель или ответственный HR подразделения без действующей учётной записи (нет, приглашена, заблокирована); действующее подразделение без сотрудников и дочерних подразделений (справочно). Действия ведут в AC-12 или AC-33.
- AC-29: Проверка сотрудника: должность пользователя не связана ни с одним уровнем действующего трека — справочный пункт «Для вашей должности нет карьерного трека — обратитесь к руководителю».
- AC-30: Без дублей (уточняет AC-2): один объект — один пункт; несколько находок по одному объекту показываются причинами внутри пункта, самая важная первой; поглощаемая находка не показывается, пока видна поглощающая: трек без уровней поглощает «трек без должностей» и «уровень без должности»; трек без должностей поглощает «уровень без должности»; должность без трека поглощает «сотрудники на должности без трека»; подразделение без руководителя поглощает «нет опубликованной матрицы»; находки по одному подразделению в AC-12 (руководитель, HR, перечень, учётные записи) — один пункт «Подключить подразделение» со списком пробелов; справочный пункт не показывается, если по тому же объекту есть действие (A-13). Полная таблица поглощения — в PRD.
- AC-34: Общее правило публикации: сущность нельзя опубликовать (сделать действующей, утвердить, согласовать версию матрицы), если она ссылается на неопубликованные (черновые) сущности, — кроме каскада: публикация публикует вместе с собой все черновые сущности, на которые она ссылается прямо или через другие (версия матрицы — трек, его уровни, компетенции, их категории и направления, шкала; трек — направление; компетенция — категория, направление, шкала), если публикующий вправе утвердить каждую из них и каждая проходит свои проверки (в том числе AC-25); иначе публикация отклоняется (409) со списком мешающих сущностей. Перед подтверждением публикации публикующий видит явный перечень всех сущностей, которые будут опубликованы вместе с ней (в AC-10, AC-11 и при утверждении записей в разделах). Каскад и отказ — в одной транзакции; каждая опубликованная сущность — отдельное событие журнала `audit`.
- AC-31: «Связать должности с треком» (руководитель, HR, администратор — кто может править трек): экран трека — уровни сверху вниз и должности у каждого уровня; должности, доступные треку и ещё не связанные с ним, с числом сотрудников; связать и снять на месте; уровни без должности и запреты AC-25 подсвечены; переход сюда — из пунктов AC-26, AC-27.
- AC-32: «Привести каталог в порядок» (HR, администратор): очередь неиспользуемых записей каталога (AC-27) — удалить по правилам AC-25 спринта 003 или деактивировать на месте; следующая запись открывается сама.
- AC-33: «Навести порядок в оргструктуре» (администратор): очередь находок AC-28 с действием на месте — добавить должность в перечень или сменить должность сотрудника, деактивировать должность, привязать учётную запись, деактивировать пустое подразделение; находки подразделения из AC-12 ведут в «Подключить подразделение».

Правки на приёмке реализации (поправка скоупа 2026-10-13, решения пользователя):
- AC-35: Экраны сценариев компактны: нет заголовка, дублирующего хлебные крошки; предупреждения и подсказки — компактные (строка или компактный алерт, а не крупная плашка); типичный объём данных сценария помещается на один экран без прокрутки на desktop; лишняя информация убрана без потери информативности.
- AC-36: В каждом сценарии можно вернуться на предыдущий шаг: в многошаговых (мастер матрицы, «Принять сотрудника») — кнопка «Назад» без потери введённого; в сценариях с выбором объекта («Связать должности с треком», «Подключить подразделение», очереди, «Согласовать версию», «Доработать возвращённую версию») — возврат к выбору другого объекта.
- AC-38: В каждом многошаговом сценарии (мастер матрицы, «Принять сотрудника») — линейка шагов: сколько шагов всего, их названия, текущий шаг, пройденные и оставшиеся; пройденный шаг открывается щелчком по линейке (поправка скоупа 2026-10-13, решение пользователя).
- AC-37: Сущность «профессиональное направление» карьерной модели называется «профессиональная область» (в интерфейсе коротко — «Область», вкладка «Области и треки») — во всех текстах интерфейса, письмах и пользовательской документации; имена в API и БД (`directions`) не меняются.
